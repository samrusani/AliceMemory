# Public Alpha Known Limitations

This alpha is intentionally limited. This page lists what is limited now in v0.22.0. What an earlier release did, and what a later release fixed, is in the [CHANGELOG](../../CHANGELOG.md) and the [release notes](../release/v0.22.0-release-notes.md). Behaviour that is new in v0.22.0 is marked `From v0.22.0`, and what v0.21.0 changed is marked `From v0.21.0`.

Not built in this alpha: no hosted cloud, no production SLA, and no team accounts, billing, cloud sync, mobile app or hosted deployment (out of scope); no managed Gmail or Calendar OAuth consent or account-linking flow (manual operator-token storage exists); no live email or calendar polling; no Telegram polling, delivery or channel transport.
OCR, PDF OCR and voice transcription execution are not packaged. The scheduler is local, model providers need your configuration, and the Postgres setup is technical (the SQLite install is one command).

- secrets fallback is alpha-grade unless an OS or managed secret provider is configured, and passive memory capture is structured and English-biased, so general conversation is not guaranteed to become memory
- automatic memory promotion is off unless a deployment opts in with `ALICE_MEMORY_PERSONA` ([personas](../memory/promotion-personas.md)), and only a writer whose identity came from an issued agent key gets it; a compromised key can write durable memory (`alicebot vnext memories quarantine` is the command-line-only sweep). Confirming a pending write with `alice_memory_commit` is not a human gate: the confirm step relies on the agent asking the user ([rules](../memory-operations-protocol.md#confirm-and-reject-rules))
- the browser clipper remains a bookmarklet/MVP path, and the user must verify opaque submissions in the Inbox; `/vnext` is the operator console, not the main agent interface: once any agent key exists it needs a dedicated unbound `admin_agent` key entered again for each mounted browser session, and `trusted_local_agent` is not full admin-review parity
- the Markdown and ChatGPT imports read each file whole, so a file over 16 MiB (Markdown) or 512 MiB (ChatGPT export) is refused with `import_file_too_large` unless `--max-file-mib N` raises the limit ([importers](../integrations/importers.md))

SQLite mode (`alice-memory install`, `alice-memory mcp`) is the default single-user path and has extra boundaries:

- most optional legacy tools (`ALICE_MCP_LEGACY_TOOLS=1`) fail or refuse: those that read the continuity store and every `alice_vnext_*` tool except the thirteen that run, the memory-commit family and four reads and captures ([list](mcp-tools.md#legacy-tool-surface)); `alice_vnext_correct_memory` and `alice_vnext_propose_memory` take text of any length, while `alice_memory_commit` refuses a memory over 20,000 characters
- no web console review (use `alice_memory_review` and `alice_memory_correct`), no scheduler, one user per database file, no automatic migration to Postgres. Agent keys exist on SQLite; once one is active, keyless MCP calls are refused, and a key does not stop a process that runs as your OS user from reading the vault file
- tool failures over stdio return a generic code and no detail (`tool_not_found`, `tool_request_failed`, `tool_execution_failed`), except `invalid_request` for a rejected argument or an oversized query, and `not_permitted`, `not_found` and `precondition_failed`, which tell a refusal from a failure ([error codes](mcp-tools.md#error-codes))
- `alice_recall` and `alice_context_pack` refuse a query of more than 499 distinct search terms or 40,000 UTF-8 bytes, and `alice_resume` and `alice_recent_decisions` one over 40,000 bytes; a query inside the limit can still take several seconds on a vault with thousands of sources ([Size bounds](mcp-tools.md#size-bounds))
- exports contain plaintext memory and source content, so protect and encrypt copies; embedding vectors are not exported (run `alice-memory reindex-embeddings` after an import), import never overwrites an existing row, and users, agent identities, API keys and soft-deleted rows are not portable. A vault with JSON text nested about 1,000 levels or more cannot be exported (`export_failed`), and import refuses such text (`restore_failed`) ([Backup and restore](backup-and-restore.md))
- From v0.22.0, with `ALICE_SOURCE_EMBEDDINGS=on` (off by default), the chunks of imported and captured notes go only to an embeddings endpoint on this machine, and for any other endpoint nothing is sent and the chunks stay pending; memory embeddings still go to any endpoint you configure ([Embeddings of source chunks](mcp-tools.md#embeddings-of-source-chunks))
- `sources delete` and `prune` keep source events, hashes, memory text and backups, and freed space keeps text until the VACUUM step ([importers](../integrations/importers.md#list-delete-and-prune-sqlite-sources))

Postgres stack and outbound calls, with the detail in the [threat model](../security/threat-model.md):

- the HTTP API refuses a request body over 4 MiB (32 MiB for connector sync) and a keyless request whose `Host` or `Origin` is not this machine's, the local-folder scan reads at most 2 MiB of a file and stops at 10,000 files or 64 MiB, and no provider, embeddings, reranker or fact-key call follows a redirect
- the body cap is no rate limit, a request with an agent key is not checked for `Host` and `Origin`, the legacy `/v0` routes apply the rule to every request, and a name in `ALICEBOT_ALLOWED_HOSTS` is trusted as this machine
- the local-folder scan still reads a hard link planted inside the watched folder to a file elsewhere, as the importers do
- the embeddings, reranker, fact-key and brain clients can reach a loopback or private address, a request carried by a proxy is not held to the address rule, and a provider response is read whole
- the Postgres doctor (`alicebot vnext doctor`) reads source rows and `raw_text` only, not chunk text, so a credential only in a source chunk is not found there, where `alice-memory doctor` on SQLite reads chunk text
- an unbound `trusted_local_agent` key reads the configured local-folder paths in `config.config_json.paths` of `GET /v0/vnext/connectors/{connector_name}/status`, even when a file under a path is confidential (every other profile and a project-bound key get HTTP 403, and an unbound `admin_agent` key reads them too); the fix has no release set
- `alice_context_pack` removes the id of a memory the caller cannot read from `metadata_json`, but looks only for a 36-character UUID there: an id in another column of a stored row or in another spelling is not removed

Open in v0.22.0, with the detail in the [security note](../release/derived-labels-security-note-draft.md):

- `alice_context_pack` still names the id of an expired memory in `recent_changes`, and its `max_tokens` budget prices the full stored row while the agent receives a compact row. Text that earlier releases sent to an embeddings endpoint, an expired memory's included, cannot be taken back from it
- the cited-source fence has gaps: memory proposals and the agent-output ingest store `source_refs` without checking the ids (v0.20.2 kept an object entry and JSON text whole; from v0.21.0, only a string that is not blank and not JSON text), the owner dependency trace lists the first id of a multi-id ref only, and `provenance_count` counts a withheld link. A memory or open loop saved before v0.20.2 keeps its link, so `alice_explain` fails for it, and an `admin_agent` writer's link makes it fail for keys of a project with a lower ceiling ([Cited sources](mcp-tools.md#cited-sources))
- v0.20.2 returns the ids of rows a key cannot read as stored. From v0.21.0, a key with limits is not shown the id of a memory, a source, an artifact or an open loop it may not read, and the count of a list that lost an id is recomputed or dropped; an id in free text is not looked for, an id that names no row at a position the product does not type is shown as written, and the owner and an unbound admin key keep every id
- a memory made from a captured source keeps its `capture_content_hash` after the source is archived, which the detail mode of `alice_memory_review`, the memory audit and the workspace event feed return; withholding it is planned, with no release set. v0.20.2 also returns the archived members of a derived memory, the `source_id` and `source_event_ids` of a memory and the `artifact_id` of the scheduler's run records; from v0.21.0, a key with limits is not shown those
- a report keeps the words it was made with: the title, text or quote of a row archived after the report was made stays in the report, in a roll-up card and as the digest of a consolidation member, and a key that can read the report reads it; hiding these words is planned, with no release set
- redaction is containment, not removal: the reports and derived rows built from a redacted memory are readable by the owner and an unbound admin key only until they are regenerated without it, but the text stays in them, and removing it is planned, with no release set ([Redacted memories](mcp-tools.md#redacted-memories))
- after a memory is redacted, the owner and an unbound admin key read the rows contained by it by id, in the artifact and project lists, in recent commits and in the dashboard, but not through recall, the context pack or the default context tree; a request that names every sensitivity lists them. An open loop made over a memory with `POST /v0/vnext/open-loops` keeps the title and description its caller typed, so words of the memory stay readable to every key that reads the loop
- a key with limits is judged at most 128 rows of each list (`READABLE_SCAN_CAP`), so a null `last_decision` or `next_action` can mean that the newest 128 matching rows hold none it may read. v0.20.2 does not refill a page after it hides rows: the vector stage of recall and of the context pack and the time stage of the context pack can return fewer results than exist, down to none, and the context tree, the workspace and the project list can return short pages. From v0.21.0, these refill, and a page is short when the hidden rows in front of it number more than 128 minus the rows the list is asked for (118 for `alice_recall` at limit 5)
- the workspace event feed lists the id of a queued task, a person and the charter above the ceiling in the `target_id` of their creation events; a connector keeps one cursor, so a key that syncs can learn whether an item it sent sorts below a cursor it may not read; the legacy `/v0` routes that stay mounted list rows whatever their label while `APP_ENV` is `development` or `test`; and the thread, approval, task and trace list endpoints have no cursor pagination

See [Backup and restore](backup-and-restore.md) before upgrading or moving a store.

Do not describe this alpha as hosted SaaS, production-ready, or automatic memory autopilot.
