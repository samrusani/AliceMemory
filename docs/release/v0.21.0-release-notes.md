# Alice v0.21.0 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.21.0","publication_status":"pending","checksums_status":"pending"} -->

**Take this release if you run `alice_recall` on a SQLite vault, give an agent a key
with limits, or write `source_refs` from your own client. Passage ranking becomes the
default of `alice_recall` on SQLite. A key with limits is no longer shown the ids of
rows it may not read, and it gets a full page when hidden rows sit in front. The
commit, proposal and agent-output doors refuse `source_refs` entries that no producer
writes. A new tool, `alice_what_changed`, reads the decision history of one topic. The
working copy of a killed `alice-memory import` is removed at the next import or open.
There is no migration. See "What to do after upgrading".**

- v0.20.2 returns one passage per document from `alice_recall`. v0.21.0 returns up to
  three on SQLite. `ALICE_SEARCH_QUALITY=off` restores the old ranking.
- v0.20.2 shows a key with limits the ids of rows it may not read when a readable row
  lists them. v0.21.0 withholds them.
- v0.20.2 gives a key with limits a short page, or none, when the nearest rows are
  hidden. v0.21.0 fills the page.
- v0.20.2 stores a `source_refs` entry that is an object, a number, a boolean, null, a
  blank string or JSON text on the commit, proposal and agent-output routes. v0.21.0
  refuses it.
- v0.20.2 has no `alice_what_changed`.
- v0.20.2 leaves the working copy of a killed import in the data directory, and neither
  the next import nor `doctor` removes it. v0.21.0 does.

## What to do after upgrading

1. **Upgrade the copy your hosts run** (`uv tool upgrade alice-memory`, or
   `pip install -U alice-memory` in the environment they use), check it with
   `alice-memory --version`, and restart your hosts.
2. **No migration.** A vault that v0.20.2 wrote opens in v0.21.0, and a vault that
   v0.21.0 has opened opens in v0.20.2. PostgreSQL stays at revision `20261011_0097`.
3. **SQLite recall.** To keep the v0.20.2 ranking of `alice_recall`, set
   `ALICE_SEARCH_QUALITY=off` in the environment of the MCP server.
4. **Check `ALICE_SEARCH_QUALITY`.** Any value other than `off` or `passage`, an empty
   value and `on` included, makes `alice_recall` answer `tool_request_failed`. The
   `alice_recall` of v0.20.2 ignored the variable, so a value left in a script from a
   measurement now fails.
5. **Clients that write `source_refs`** must send strings (see below).
6. **Clients that read ids with a key with limits** now get shorter lists and null
   fields where an id is withheld.
7. **Killed imports.** Nothing to do. `alice-memory doctor` opens the vault, so it
   removes a leftover working copy now. Otherwise the next import into the vault does.

## Passage ranking is the default of `alice_recall` on SQLite

On the SQLite store, `alice_recall` returns up to three passages from one document and
ranks passages across documents, so a short note with one strong match can come before
a long document with several. v0.20.2 returns one passage per document. A passage entry
in `sources` carries `chunk_index`, the position of its chunk in the document counted
from 0, and `source_count` counts entries. Passage mode can also fill its last slots
with whole-document entries, which carry no `chunk_index`. `ALICE_SEARCH_QUALITY=off`
gives document mode, the v0.20.2 ranking, and `passage` asks for passage mode by name.

Passage ranking was measured before it became the default. On 120 questions about two document folders, written and checked outside the team that builds Alice and not shown to it, the first 8 KB of `alice_recall` output held every fact a question needs for 70 questions with passage mode and 46 without it when the question was asked as written (24 improved, none worse), and for 73 against 55 when it was asked as three or four keywords (18 improved, none worse). The rule for switching the default was written down before the measurement: at least 8 more questions on the written form with an exact sign test below 0.05, and no significant loss on the keyword form. The first measurement failed, because the passage stage then ran without the fallback query described below. Adding that fallback was the only change before the second and last measurement. The number of passages per document (3) was not tuned on these questions.

On a SQLite vault of 102,192 passages (13,400 synthetic Markdown files, no embeddings endpoint), a warm `alice_recall` took 0.78 s at the median and 1.56 to 1.58 s at the 95th percentile in passage mode, against 1.54 to 1.56 s in document mode, on an Apple M3 Max laptop. That vault held almost no memories, so a vault that also holds many memories is slower. Importing those 13,400 files took 41 minutes.

The fallback query: when the strict query finds no passage the caller may read, passage
mode retries once with a query that matches any of the question's words, so a long
question that no chunk matches word for word still returns passages. The context pack
and the session brief stay on one passage per document.

PostgreSQL keeps document mode. There, `ALICE_SEARCH_QUALITY=passage` turns passage
mode on for the owner and an unbound admin key, and a key with limits stays on one
passage per document even then.

## Rows a key with limits may not read

A key with limits is any key but the owner's and an unbound admin key, for example a
read-only, project-scoped, trusted or memory-proposal key.

**Hidden ids.** A readable memory or report can list the ids of other rows in
`source_refs`, `derived_from`, `candidate_memory_ids` and similar lists. v0.20.2
returned those ids as stored. v0.21.0 checks every string in an answer to a key with
limits whose whole value is an id, under any field name and at any depth, in any
spelling of a UUID and behind a `memory:`, `source:`, `artifact:` or `open_loop:`
prefix. A list loses the entry, and a count beside a list that lost an entry is
recomputed or dropped. Where a prefix says the id names a row, an id the key may not
read is withheld whether the row is hidden or does not exist, so the key cannot tell
the two apart. Plain labels and URLs stay. The owner and an unbound admin key keep every
id. It applies to HTTP answers, MCP tool results and command output.

**Full pages.** v0.20.2 took the nearest rows and dropped the hidden ones afterwards,
so a key with limits could get fewer results than exist, down to none. v0.21.0 reads up
to 128 rows and gives the first rows the key may read, up to the limit it asked for.
This covers the vector stage of `alice_recall` and of the context pack, the
temporal-anchor stage of the context pack, `GET /v0/vnext/projects`, the context tree
and the workspace lists. The page is still short when the hidden rows in front of it
number more than 128 minus the rows the stage asks for.

## `source_refs` shapes are refused at write time

Producers write `source:<id>`, `memory:<id>`, a bare id or a label such as a URL.
v0.21.0 refuses an object, a number, a boolean, null, a nested array, a blank string
and a string that is the text of a JSON object or array, and writes nothing. The doors
are the memory commit, the memory proposal and the agent-output ingest routes,
`POST /v0/vnext/connectors/agent_output/sync`, their MCP tools, and the `--source-ref`
flag of `alicebot vnext memories commit`.

- The three routes answer HTTP 422 for every shape but a blank string, which gets
  HTTP 400. v0.20.2 answered HTTP 201 and stored them.
- The MCP tools answer `invalid_request` for all of them. v0.20.2 dropped a blank
  entry and stored JSON text.
- The connector sync reports an item with such an entry as failed (HTTP 400 when every
  item failed, 207 when some were imported) and stores none of it.
- A label that starts with `[` or `{` and is not JSON is still accepted.
- Backups made by v0.20.0 and v0.20.2 that hold an object entry still restore.

## What changed

`alice_what_changed` and `POST /v0/vnext/changes` answer the recorded decision history
of one topic. The answer is a list of chains. Each chain has its own `current`,
`upcoming`, `disputed` and `history`, oldest first. A reason is the rationale stored
with the decision, or a quote already stored on its provenance when the caller may read
that source. The read never searches note text for a reason. It judges at most 128
candidates, gives no count and no gap marker, and answers only from decisions the
caller may read. A vault of plain notes answers "No recorded decision history was
found" and names `alice_recall`. The tool is read-only and is on the full tool surface
(`ALICE_MCP_FULL_TOOLS=1`), which now holds 12 core tools. `alice_memory_correct` with
`replacement_body.decision_text` now stores that text. v0.20.2 stored the JSON object.

## Restore working copies

An import builds its staged database in `.<vault file>.restore.<random>.tmp`, with
`-wal` and `-shm` files, in the data directory. Killing the import leaves them. v0.20.2
did not remove them at the next import or at an open. v0.21.0 removes them at the next
import into that vault and at the next open of an existing vault, such as `doctor` or
the MCP server. While an import runs in the data directory, an open leaves its copy
alone and does not wait for it. If a first import into a vault that does not exist yet
was killed, `sources` and `labels check` stop with `vault_not_found` and leave the
copy. `doctor` creates the vault and removes it.

## Behaviour changes an integrator will notice

- `alice_recall` on SQLite: passage mode by default, `chunk_index` on passage entries,
  `source_count` counts entries. Document mode adds no `chunk_index`.
- `alice_recall` answers `tool_request_failed` for `ALICE_SEARCH_QUALITY` values other
  than `off` and `passage`.
- Answers to a key with limits drop ids it may not read, and ids that name no row where
  a prefix says they should.
- Pages for a key with limits are full where they were short.
- `source_refs`: the refusals above.
- `ALICE_MCP_FULL_TOOLS=1` lists 12 core tools, and with `ALICE_MCP_LEGACY_TOOLS=1`
  74, or 77 with `ALICE_LEGACY_SURFACES=1`. The default surface is still three tools.
- `scripts/alice_bench.py` records `ranking_mode` (`document` or `passage`) beside
  `search_quality`, because an unset switch is passage mode on SQLite.

## Docs and tooling

The README is about 12,400 characters, down from about 28,600, and shows no
LongMemEval figure. The known limitations page is about 10,100 characters, down from
about 18,700. The v0.20.2 notes named v0.21.0 for three changes: removing the words of a redacted
memory from reports, hiding the words of archived rows in reports, and withholding
`capture_content_hash`. None is in this release and none has a release set; the v0.20.2
notes carry dated corrections. `scripts/generate_showcase_company.py` writes a
synthetic company of 1,000 or 10,000 Markdown notes, and `scripts/alice_bench.py` gains
`showcase-*` commands that import it and run search arms against it
([harness](../benchmarks/showcase/harness.md)). Vite, a development dependency of the
web console, moves from 6.4.3 to 6.4.4.

The first job of the publish workflow, `build-and-verify`, has a time limit of 180
minutes, up from 120. It reruns the whole unit suite in one process, and that step now
takes about 65 minutes (3,876 s on a runner), while a release step must take less than
half of its job's limit. `publish-recheck-rehearsal.yml` has the same limit.

## What this release does not claim

It does not claim the same gain on other collections: the retrieval measurement used
two document folders and counted facts found in the recall output, not answers an
agent wrote, and the timing used one synthetic vault. It does not claim
that no hidden id is left in an answer. Three limits matter most here, and the rest are
on [the known limitations page](../alpha/known-limitations.md):

- PostgreSQL keeps document mode. The passage default is a SQLite change.
- An id inside free text, such as the text of a readable memory, is not removed.
- Redaction restricts reports and does not remove the words from them.

## Security

This release was checked with automated security scanning and internal adversarial
review, findings triaged and fixed. No one outside the project has audited the code.

The change a security-minded reader will care about is the withheld ids above. In
v0.20.2 a key with limits could read the id of a row it may not read from a readable
row that listed it.
