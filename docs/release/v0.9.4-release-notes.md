# Alice v0.9.4 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.9.4","publication_status":"published","checksums_status":"recorded"} -->

`v0.9.4` is a security and reliability release over `v0.9.2`. It supersedes the
withdrawn `v0.9.3` candidate: an internal hotfix that a follow-up external audit
returned NO-GO on, so it was never published. `v0.9.4` carried the original five
fixes plus attempted all nine P1 remediations from the second audit.

> **Correction (2026-09-27):** the follow-up audit of `v0.9.3`, the second
> audit, and the third audit named in these notes were each an internal
> adversarial review, not an independent or external audit.

> **Post-publication correction (2026-07-13):** a third independent audit found
> that several of those remediations were partial and that configured eval and
> backfill vectors did not carry the new endpoint signature. The v0.9.4 publish
> workflow passed unit, LongMemEval, package, and artifact checks, but did not
> run a successful configured semantic-vector release eval. The immutable tag
> and artifacts are unchanged; the published v0.10.2 corrective record and its
> remediation matrix record the corrective work. Statements below describe the
> intended v0.9.4 changes,
> not current proof that every finding was closed.

## Fixes

- **Supersession cycles (concurrency + depth).** Supersession graph mutation is
  serialized per user with a transaction-scoped Postgres advisory lock, and the
  cycle guard fails closed when it cannot verify acyclicity within its hop
  bound. Two concurrent supersessions on disjoint row pairs can no longer each
  pass an unlocked cycle check and together close a cycle.
- **Project-scoped capture.** Content dedupe is now scope-aware — the content
  hash folds in the project scope — so identical text captured under a different
  project keeps its own scoped source and candidate instead of being skipped as
  a global duplicate. Browser-clip and agent-output proposal paths now propagate
  project scope onto the captured source and candidate memory.
- **Hard people/time filters.** People and time-window scope filters run over
  ranked candidates, so the retriever now deepens the scan (bounded) until
  enough scoped rows survive, instead of dropping a valid row ranked behind a
  full window of non-matching candidates.
- **Embedding vector-space fingerprint.** The persisted embedding signature now
  includes an endpoint fingerprint, so two endpoints that share a provider/model
  label but serve different coordinate spaces are never pooled or compared.
- **Consolidation / roll-up embedding presence.** Consolidation and semantic
  roll-ups determine which selected rows have stored vectors by an exact read of
  those row IDs, not a global nearest-neighbor probe, so embedded rows are no
  longer missed when unrelated neighbors dominate the query.
- **Roll-up membership.** Roll-up cards persist their full authoritative
  membership rather than the truncated display subset, so a group larger than
  the per-card instance cap no longer re-proposes a revision on every run.
- **Filtered vector search.** Filtered PostgreSQL vector search enables
  iterative HNSW scan, so lifecycle/scope/signature filters no longer silently
  under-return valid rows.
- **Release eval fail-closed behavior.** The eval runs with `--release-gate`:
  a run that never exercises the vector stage reports `pass_fts_only` and exits
  non-zero, and eval failure propagates to the process exit code — the gate
  cannot be green without measuring semantic retrieval quality. The later audit
  found that the configured seed path did not persist production-compatible
  signed vectors, so v0.9.4 did not produce valid positive vector evidence.
- **Honest release finalization.** Release notes carry one machine-readable
  publication/checksum state immediately below their exact title. Candidate
  validation requires `pending`/`pending` with no checksum file; finalized
  validation requires `published`/`recorded` with the expected checksum file.
- Plus the original five: the central lifecycle transition table, expire/unexpire
  row-locking, and the migration-`0083` identifier-repair migration `0084`.

## Upgrade

`alembic upgrade head` applies migration `0084` (idempotent; safe to re-run).
SQLite databases correct themselves on next open. Because embedding signatures
gained an endpoint fingerprint, run `alicebot vnext memories backfill-embeddings`
after upgrade to re-embed existing vectors under the new signature; until they
are re-embedded those rows fall back to full-text retrieval. No other operator
action is required.

## Verifying this release

Alice publishes to PyPI through GitHub Trusted Publishing. Once published, the
wheel and source distribution carry PyPI's integrity attestations, which bind
each file to this repository, the release tag, the publishing workflow, the
exact commit, the release event, and the protected `pypi` environment —
verifiable on the project's PyPI page. Their exact SHA-256 digests are recorded
in `docs/release/v0.9.4-checksums.txt` by the post-publication commit.

## Not included

At the time, the v0.10.0 remediation cycle tracked incomplete P1 fixes and the
P2 backlog: full package type checking (mypy), web test typechecking,
packaged-README PyPI links, backup/restore hardening, N+1 retrieval fan-out,
and related items. The later v0.10.2 corrective record superseded that cycle.
