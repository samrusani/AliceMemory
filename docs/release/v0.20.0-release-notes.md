> **Correction (2026-10-05):** these notes do not say that a derived summary, report or copy kept the label its inputs had when it was made, or that a report could show a key bound to one project rows of other projects or with no project. Both are in v0.20.0 and are listed under known limitations.

Unreleased (on main, not in v0.20.0): four older operator or legacy readers still expose withheld information: source GET returns titles and raw text, graph neighborhood returns edge explanations, doctor returns label-check counts, and legacy `alice_vnext_review_items` lists derived memories for a declared restricted identity. See the [draft security note](derived-labels-security-note-draft.md) for the remaining boundary and the SQLite retirement limits.

**Take this release if you run the Postgres stack's HTTP API, use an embeddings
endpoint (above all a hosted one), import ChatGPT or Markdown files, use the
Hermes provider, or call `alice_context_pack` with a small `max_tokens`. It acts
on the six findings from the internal security review of v0.19.0 that v0.19.2
left open (DB-005, DB-006, DB-008, DB-009, DB-010 and DB-011), each with a fix
and the limits of the fix stated below. It sends less text to the embeddings
endpoint, and it fixes several failures that users hit. It adds no tool or
command and changes no schema. It adds one option, `--max-file-mib`, and four
settings, and it has upgrade steps. See "What to do after upgrading".**

- v0.19.2 can answer a context pack with nothing in it at a small `max_tokens`,
  because one large item ranked first and every item after it was dropped.
  v0.20.0 skips an item that does not fit and tries the next one, and cuts one
  item's text to fit when none fits whole. A committed memory costs about 710
  tokens before any of its text, so the pack can still be empty at the tool's
  500-token minimum. See "Context pack at a small budget".
- v0.19.2 sends the text of a memory to the embeddings endpoint when it is written,
  and reindex and backfill send every memory with no current vector, whatever its
  status. A pending, candidate, forgotten, rejected or expired memory is sent too.
  v0.20.0 sends only what recall can return, and sends a pending memory when it
  becomes active. See "What the embeddings endpoint receives".
- v0.19.2 sends a memory of any length to the embeddings endpoint, and one memory
  that the endpoint refuses fails its whole batch of 128. v0.20.0 cuts the text
  to `ALICE_EMBEDDINGS_MAX_INPUT_CHARS` (8,000 by default), isolates a refused
  memory and names it.
- v0.19.2 follows a redirect from a provider, embeddings, reranker or fact-key
  endpoint and sends its `Authorization` header on to the target. v0.20.0
  follows none. See "Security".
- v0.19.2 reads a request body of any size on the Postgres stack, and a keyless
  API answers whatever `Host` header a request carries. v0.20.0 refuses a body
  over 4 MiB with HTTP 413 and a keyless request that does not name this machine
  with HTTP 401. See "Security".
- v0.19.2 fails a whole ChatGPT import for one long conversation, reads any file
  whole whatever its size, and reads a local-folder file by path after it has
  checked the path. v0.20.0 imports a conversation of any length, refuses an
  oversized file before it reads it, and reads each local-folder file through an
  open descriptor. See "Importers and backups" and "Security".
- v0.19.2 answers HTTP 500 for a JSON request body with a lone surrogate, for a body
  nested about 975 levels deep, and for a body that is not UTF-8 and has no JSON
  content type. v0.20.0 answers HTTP 422. A Hermes turn that carries a lone
  surrogate is saved with plugin 0.5.3.
- The LongMemEval numbers (64.6%, 79.4% and 81.2%) carry a published known issue.
  The benchmark harness showed the reader model each session's id, and the id of
  every evidence session starts with `answer_`. No number changed. See
  "Benchmarks".

## What to do after upgrading

1. **Upgrade.** With pip: `pip install -U alice-memory==0.20.0`. With uv, run
   `uvx alice-memory@0.20.0 --version` once; it prints the version the hosts
   get. Restart the hosts afterwards.
2. **Hermes:** the provider is copied into Hermes by its installer and is not in
   the wheel. An existing install keeps plugin 0.5.2 until you run
   `./scripts/install_hermes_alice_memory_provider.py --force` from a v0.20.0
   checkout, with the Python environment where Hermes is installed (or pass
   `--destination-root`). Without `--force` the script stops with `destination
   already exists`. A `--symlink` install follows the repository. The installed
   `plugin.yaml` says `version: 0.5.3` for the fixed provider.
3. **A provider that redirects must be configured with its final URL.** This
   covers the model provider helpers, response generation, the embeddings,
   reranker and fact-key clients, the vNext brain model client, and the Gmail and
   Calendar clients. A 301, 302, 303, 307 or 308 answer is now an error that
   says `redirects are not followed; set base_url to the final URL`, and the
   target is never contacted. If your endpoint upgrades http to https, or moves
   under another path, put the final URL in `base_url` or in
   `ALICE_EMBEDDINGS_BASE_URL`. A memory written while its embeddings endpoint
   redirects is saved without a vector, `alice-memory doctor` counts it under
   `memories without a current vector`, and `alice-memory reindex-embeddings`
   makes the vector once the URL is right. A proxy that you route calls through
   still works, and a redirect from behind it is refused too.
4. **A development API reached by a LAN name or any other non-loopback `Host`
   needs `ALICEBOT_ALLOWED_HOSTS`.** While no agent key exists, the Postgres
   stack's API answers HTTP 401 `authentication_failed` to a keyless request
   whose `Host` is not `localhost`, `127.0.0.1` or `::1` (any port, any case),
   on `/v0/vnext`, on `/v1` and on the legacy `/v0` routes that development
   serves. Name each extra host in `ALICEBOT_ALLOWED_HOSTS`, comma separated and
   exact: no wildcard, port or scheme, and an entry with one stops the settings
   from loading. A request with an agent key on `/v0/vnext` or `/v1` is not
   checked, so keyed clients and the Caddy topology (which requires a key before
   it starts) do not change. An `Origin` header on a keyless request must be an
   exact `CORS_ALLOWED_ORIGINS` entry or the request's own origin.
5. **Operators who run their own Caddyfile:** add `request_body { max_size 4MB }`
   as `packaging/cloud/Caddyfile.example` does. `scripts/
   run_single_tenant_deployment_smoke.py` now fails with
   `caddy_request_body_limit_missing` for a Caddyfile without it. The cap also
   applies to connector sync through Caddy, which Alice itself allows up to 32
   MiB, so raise it for those paths if you send large documents that way.
6. **Clients that send a large body:** the API refuses a body over 4 MiB
   (`ALICEBOT_MAX_REQUEST_BODY_BYTES`) with HTTP 413 and `request_too_large`.
   `POST /v0/vnext/connectors/{name}/sync` is allowed 32 MiB
   (`ALICEBOT_MAX_CONNECTOR_SYNC_BODY_BYTES`). Split a larger payload. A body
   nested more than 256 levels is refused with HTTP 422.
7. **Embeddings (SQLite and Postgres):** nothing is re-embedded by the upgrade
   itself, and the signature version stays 2. But Alice now cuts the text it
   sends to `ALICE_EMBEDDINGS_MAX_INPUT_CHARS` (default 8000, allowed 256 to
   1,000,000), and the first `alice-memory reindex-embeddings` after the upgrade
   makes the vector again for each memory whose embedded text (its title, text and
   summary) is over the cap and whose vector carries no cut label, which is every
   vector that v0.19.2 made for such a memory. The summary of a committed memory
   is the first 280 characters of its text, so with a short title its embedded text
   is about 300 characters longer than the text, and a memory with text of about
   7,700 characters or more can be over the default cap. Memories at or under the cap are
   not touched. `alice-memory doctor` shows how many that is as
   `memories without a current vector`, before you run anything. On a SQLite
   vault of five memories committed under v0.19.2 with a recording endpoint (texts
   of 100, 600, 7,900, 8,800 and 15,000 characters, so embedded texts of 117, 899,
   8,199, 9,099 and 15,299 characters), the doctor showed 3 right after the
   upgrade and made no request. The first reindex sent one batch of 3 texts of
   8,000 characters each, and the second reindex sent nothing. On a hosted
   endpoint the cost is at most the cap in characters for each such memory, which
   is about 2,000 tokens of English prose at the usual four characters to a
   token (your provider's tokenizer decides). A vault in which no memory's embedded text is over
   8,000 characters pays nothing. If your model takes a larger window, set the cap
   before the first reindex: with `ALICE_EMBEDDINGS_MAX_INPUT_CHARS=20000` the
   same vault showed 0 and sent nothing, and with 12000 only the memory whose
   embedded text was over 12,000 characters was sent, cut to 12,000. A model with a small window needs a
   lower cap, for example 1500 for one that takes 512 tokens. `alicebot vnext
   memories backfill-embeddings` on Postgres applies the same rule, and was not
   run for this check.
8. **Importers:** `alice-memory import-markdown`, `alice-memory import-chatgpt`,
   `alicebot vnext sources import-markdown` and `alicebot vnext sources
   import-chatgpt` refuse a file over 16 MiB (Markdown) or 512 MiB (ChatGPT
   export) with `import_file_too_large` and exit 1, before they read any of it
   and with nothing written. `--max-file-mib N`, a whole number of at least 1,
   changes the limit for that run, and there is no value for no limit. A script
   that passes `--max-file-mib` needs v0.20.0: v0.19.2 answers it with
   `invalid_request` and exit 2. The limit is per file, not per folder.
   `alicebot vnext sources capture-file`, `alicebot vnext connectors
   browser-clipper capture --file` and `alicebot vnext agents ingest-output
   --file` take the same 16 MiB limit and the same option.
9. **Local-folder connector (Postgres stack):** the scan reads at most 2 MiB of a
   file, stops at 10,000 files or 64 MiB of text, and lists at most 100,000
   directory entries. These limits are fixed in code and are not settings. A file
   over the limit, a file that is not UTF-8 text, a file that cannot be read, and
   a file or directory that is swapped for a link during the scan are skipped on
   their own and counted in `refused_count`, and the rest of the folder still
   scans. `truncated` is true when a limit stopped the scan. A source that an
   earlier sync stored from a file that is now refused is not changed or removed
   by the scan. A folder named like a default ignore (`node_modules`, `.git`,
   `.venv` and the rest of the list, without regard to case) is no longer
   entered, so its files stop counting in `ignored_count`.
10. **Callers of `alice_resume` and `alice_recent_decisions`** on SQLite: handle
    `invalid_request`, and keep the query to 40,000 UTF-8 bytes or less. A query
    of 40,001 to about 50,000 bytes was taken by v0.19.2 and is refused now.
11. **Backups:** an import can now refuse a backup with `restore_failed` and one
    line that names the file line, the table and the column. If a vault already
    holds JSON text nested about 1,000 levels or more, which a v0.19.0 or v0.19.2
    import could store, `alice-memory export` of that vault ends with
    `export_failed`. With `--out` it writes no file, and to standard output it
    leaves a partial stream that import refuses. See "Importers and backups".
12. **Claude Code plugin:** the marketplace file pins the v0.19.2 tag commit until
    a change after this release moves it, so the marketplace install runs v0.19.2
    code and carries none of these fixes. See "Claude Code plugin".

> **Update (2026-10-02):** v0.20.0 is published, and the marketplace file on `main` now pins the v0.20.0 tag commit, so the marketplace install runs v0.20.0. The copy inside the v0.20.0 tag still pins v0.19.2, so add the marketplace from the repository, not from a checkout of the tag.

## Context pack at a small budget

`alice_context_pack` no longer comes back empty at a small `max_tokens` because
one large item ranked first.

- An item that does not fit is skipped and the next one is tried. When nothing
  fits whole, the first item that can be cut to fit has its text cut to the budget
  and ending in `…`, the mark a trimmed excerpt line already carries. The budget
  report then adds `cut_item_count: 1`, and the `token_report` that
  `alice_context_pack` returns forwards it. Packed items keep their ranking order
  and `token_estimate` never exceeds `max_tokens`.
- An item's ids, scope and metadata are priced and never cut. A budget below the
  cost of the cheapest item with its text removed still returns no item. For rows
  written by `alice_capture` and `alice_memory_commit`, about 320 tokens for a source
  and about 710 for a memory were measured while the change was built, so a vault of only
  committed memories can still return an empty pack at the tool's 500-token
  minimum.
- Checked on SQLite with one 12,900-character memory that ranks first and one
  short memory. In v0.19.2 the pack held no memory at `max_tokens` of 500, 1,000,
  2,000 and 4,000. In v0.20.0 it holds none at 500 and 700, and the short memory
  from 800 up.
- No stored data changes. The one new field is `cut_item_count`, which appears in
  the budget report only when an item was cut. See "Known limitations" for how the
  budget is priced.
- On SQLite the default tools are `alice_memory_commit`, `alice_recall` and
  `alice_resume`. `alice_context_pack` and `alice_recent_decisions` are listed and
  callable only with `ALICE_MCP_FULL_TOOLS=1`.

## What the embeddings endpoint receives

Alice sends the text of a memory to the embeddings endpoint only when recall can
return it: its status is `active` or `accepted`, and its `valid_to`, if it has one,
has not passed.

- **At write time.** A write that waits for confirmation (`confirmation_required`,
  status `needs_review`), a proposal that waits for review (`review_required`,
  status `candidate`) and the candidate memories that `alice_capture` and the
  connectors write are not embedded when they are created. Each is embedded once,
  when it becomes active: `alice_memory_commit` with `confirmation_action:
  confirm`, `alicebot vnext memories confirm` (an edit sends only the edited
  text), approve, edit and approve, supersede with a replacement through
  `alice_memory_correct` or `alicebot vnext memories correct`, and accepting a
  consolidation candidate. The HTTP review routes and the project update review
  make a memory active through the same step. A rejected memory is never sent. In
  v0.19.2 the text of each was sent at creation, whether or not anyone accepted
  it, and a confirmed or approved memory was sent a second time. On a SQLite
  vault with a recording endpoint on 127.0.0.1, `alice_capture` of a note with one
  candidate memory sent one text in v0.19.2 and sends none now.
- **At reindex and backfill.** `alice-memory reindex-embeddings` and `alicebot
  vnext memories backfill-embeddings` list only active and accepted memories whose
  `valid_to` has not passed. A superseded (forgotten), rejected, candidate,
  `needs_review`, `private_only`, archived, stale or expired memory is skipped: no
  vector is made for it, and none is replaced. A memory that becomes active later,
  or whose `valid_to` is cleared with the unexpire action, is listed by the next
  run. A vector that a skipped memory already holds is kept. Checked on SQLite
  with one active, one forgotten and one expired memory and no vectors: reindex
  sent 3 texts in v0.19.2 and has no doctor count, and in v0.20.0 the doctor counts
  1 and reindex sends 1.
- **The doctor line, new in this release.** `alice-memory doctor` prints `memories
  without a current vector`, the count of active and accepted, unexpired memories that have no
  vector or a vector that is not today's, with `(no embedding provider
  configured)` after it when no provider is set. Reindex works from the same test,
  so the count is the number of memories reindex embeds.
- **One function.** Every text goes out through `prepare_memory_embeddings`, which
  withholds any input that is not recallable and names it in `withheld`, whichever
  caller offered it. A new write path that offers a pending row sends nothing.
  `list_memories_missing_embeddings` takes a required keyword argument `statuses`
  on SQLite and on Postgres, so a caller that leaves it out gets a `TypeError`.
- **What an endpoint already holds.** Text that v0.19.2 and earlier sent cannot be
  recalled: Alice has no way to take a text back from an endpoint once it is sent.
  A user of a hosted endpoint should check that provider's retention terms and
  deletion options for memories they had forgotten, rejected or never accepted.

The input cap and the refused-memory handling work like this.

- **The cap.** Each memory text, and each recall query, is cut to
  `ALICE_EMBEDDINGS_MAX_INPUT_CHARS` characters before it is sent. The default is
  8000, which fits a model that takes about 8,000 tokens even at one token per
  character. A model with a 512-token window needs about 1500. A memory whose
  embedded text, its title, text and summary, is over 8,000 characters is embedded
  from its first 8,000 on a model that could take more, and full-text search still
  reads all of it, so a vault of long memories on a large-window model can raise
  the cap. A
  value outside the range is ignored with a warning. A vector made from a cut text
  carries `truncated_to_chars` in its signature, set to the cap, and the digest in
  the signature is still that of the whole text, so an edit past the cut is still
  seen. After a change of the cap, reindex re-embeds exactly the rows whose
  embedded text changes. Re-running Hermes `install`, or OpenCode `install` on
  an `opencode.jsonc` or an `opencode.json` that is not strict JSON, keeps
  `ALICE_EMBEDDINGS_MAX_INPUT_CHARS` in an existing entry, where v0.19.2 refuses
  an entry that holds it. A strict `opencode.json` kept every key that install did
  not write in both versions.
- **A refused memory.** When the endpoint answers a batch with HTTP 400, 413 or
  422, Alice sends a one-text probe. If the endpoint accepts the probe, Alice
  splits the batch in half and retries each half, down to single texts, so the
  texts the endpoint accepts get vectors and the refused ones are named. A failure
  that is not about the text (a refused connection, a timeout, 401, 404, 429, a
  5xx, or a probe the endpoint also refuses) is not split. Checked against a local
  endpoint that refuses any text over 3,000 characters, with five memories and one
  of 6,000 characters: v0.19.2 failed all 5 with no id and no reason, and v0.20.0
  embedded 4, failed 1, named it in `failed_ids` and gave the reason
  `embeddings endpoint returned HTTP 400: input too long for this model`.
- **Output.** `alice-memory reindex-embeddings` and `alicebot vnext memories
  backfill-embeddings` print `failed_ids` (at most 100, with `failed_ids_omitted`
  for the rest), `failure_reasons` (the most common, with counts),
  `input_cap_chars` and `truncated_inputs`. Each failure carries the endpoint's
  status and at most 300 characters of its error message. The message is replaced
  by a fixed sentence when the credential check flags it, and the configured API
  key is replaced by `[redacted]` when the endpoint echoes it back as it was sent
  (a copy the endpoint alters, with a space inserted for example, is not matched).
  The reason is printed in reindex output and the process log. It is not written
  to the event log, which still gets fixed text and now the status number. An id
  that is longer than 128 characters, holds a control character or is
  credential-shaped prints as `(id withheld)`.
- **A changed memory.** SQLite reindex counts a memory whose text changed while its
  vector was being made as failed, names it and exits 1, and the next run makes
  its vector. In v0.19.2 it counted that memory as embedded and stored no vector
  for it. The Postgres backfill already counted it as failed.
- **A recall query over the cap** is cut to the cap before it is embedded. In
  v0.19.2 a query over the endpoint's limit turned the vector stage off with
  `query_embedding_failed`.

## Memory ids behind the read fence

Three memory id defects that the v0.19.0 and v0.19.2 fences left are fixed.

- **The correction label.** `current_memory_id` on a corrected passage names an id
  only when the walk ends on a memory that is not retired, is inside the caller's
  fence, has no closed validity window and is not reached through a loop. When the
  memory it reaches was forgotten, undone, rejected or expired, or the passage's own
  memory was forgotten or undone, no id is named. `derived_memory_corrected` stays
  true, so an agent still does not quote the passage as current. A chain whose last
  memory was forgotten names nothing, and does not fall back to the memory before
  it, because that memory is itself superseded. A loop of `superseded_by` pointers,
  which the supersession check refuses to record but a direct patch can make,
  names no id. `alice_memory_manage` with `action: expire` sets `valid_to` and
  leaves the status `active`, so a successor closed that way used to be named
  although `alice_recall` and `alice_context_pack` do not return it. In v0.19.2
  the label named the forgotten, undone, rejected or expired memory, and the
  memory a loop came back to, to every caller that could read it. A deleted
  successor already named no id.
- **Pack `validity`.** The context pack keeps `validity.superseded: true` on a
  memory whose `superseded_by` pointer names a memory the caller cannot read, and
  names no id, exactly as `alice_recall` does. In v0.19.2 the pack dropped the
  pointer first and worked out `validity` afterwards, so a memory that was still
  active and carried such a pointer had no `validity` in the pack.
- **`metadata_json`.** An id of a memory the caller cannot read that was copied into
  a stored memory's `metadata_json` is no longer returned. In v0.19.2 an
  `alice_context_pack` call with `debug: true` returned it for decision, procedure
  and belief memories, to the keyless owner under the default sensitivity ceiling
  and to a read-only key. The pack now looks at every UUID-shaped string in the
  `metadata_json` of the memories it returns, as a value, a list item or a key, and
  applies the same sensitivity, domain, project, person and time fence as the
  memory reads to the memory each one names. A string that is only such an id, with
  or without a `memory:` prefix, is removed with its key or list slot. An id inside
  a longer string is replaced by `(id withheld)`. An id that names no memory is
  kept, as an unscoped pack keeps a pointer that names no row. A source id or a
  chunk id is kept because it names no memory. Metadata nested deeper than 64
  levels is cut at that depth, because it cannot be read safely. The fence runs
  where `compile_context_pack` builds the pack and is a required keyword argument,
  so every section that holds the stored rows is covered. The HTTP route, the CLI
  and the legacy `alice_vnext_context_pack` tool return the same compiled pack and
  were not run. An id in a column other than `metadata_json`, or one that is not a
  36-character UUID, is not looked for. This closes DB-012.

## Security

These are the findings of the internal security review of v0.19.0 that v0.19.2
left open. The review was automated security scanning and internal adversarial
review, findings triaged and fixed. No one outside the project has audited the
code. DB-005, DB-006, DB-009, DB-010 and DB-011 concern the optional Postgres
stack. DB-009 also covers the embeddings endpoint you configure on SQLite. The
SQLite install, `alice-memory mcp` and the hook run no HTTP API and no
local-folder connector.

- **DB-005, the keyless API did not check the Host header.** A keyless request on
  `/v0/vnext`, on `/v1` or on a legacy `/v0` route is refused with HTTP 401
  `authentication_failed` unless its `Host` is `localhost`, `127.0.0.1` or `::1`
  (any port, any case) or an exact name in `ALICEBOT_ALLOWED_HOSTS`. A missing,
  repeated or malformed `Host` is refused, nothing is matched by prefix or suffix,
  and `X-Forwarded-Host` and `Forwarded` are not read. The legacy `/v0` routes take
  no key, so every request to them gets this rule whatever `Authorization` header it
  carries, and a CORS preflight is not refused by it. An `Origin` on such a request
  must be an exact `CORS_ALLOWED_ORIGINS` entry or the request's own origin (the
  same host and port as its `Host`); `null` is refused and a `*` entry does not
  count. The browser-clipper capability capture route is exempt. A request with an
  agent key on `/v0/vnext` or `/v1` is not checked. In v0.19.2 both gates checked
  the peer address only and the legacy routes checked nothing, so a hostname that
  resolves to 127.0.0.1 reached a keyless API under its own name, and a cross-origin
  form post reached the two `/v1` routes that read no body, `POST
  /v1/workspaces/bootstrap` and `POST /v1/evals/runs`. Checked with raw requests to
  a running API: v0.19.2 answered the same for every `Host`, and v0.20.0 answers
  HTTP 401 for `lan-box.example` and `attacker.invalid` and passes the gate for
  `localhost` and, once it is listed, for `lan-box.example`. A browser attack
  through the old behaviour was not reproduced, and the new rule was not tried from
  a real browser.
- **DB-006, a request body of any size was read before authentication.** A body over
  4 MiB (4,194,304 bytes, `ALICEBOT_MAX_REQUEST_BODY_BYTES`) is refused with HTTP 413
  and `detail` `{"code": "request_too_large", "message": "The request body is too
  large"}` before any layer reads it, on every route, whoever the caller is. A
  declared `Content-Length` over the cap is refused before a byte is read. A
  chunked or undeclared body is counted as it arrives and refused as soon as it
  crosses the cap, and the refusal carries `Connection: close`. The cap counts
  bytes as sent, so text written with `\uXXXX` escapes counts six bytes a
  character. The connector sync routes take lists of whole documents that no model
  bounds, so `POST /v0/vnext/connectors/{name}/sync` has its own cap of 32 MiB
  (`ALICEBOT_MAX_CONNECTOR_SYNC_BODY_BYTES`). The `/v0/vnext` gate now refuses a
  keyless request from another peer, or with a `Host` or `Origin` that is not this
  machine's, before it reads the body, as the `/v1` gate already did. A JSON body
  nested more than 256 levels is refused with HTTP 422 and one error of type
  `json_too_deep` with `loc` `["body"]`, with nothing from the body in it. The
  check reads the bytes and never parses the body, so its cost grows in step with
  the size of the body, which the cap bounds. In v0.19.2 a body nested about 975
  levels deep or more answered HTTP 500, one nested 257 to about 974 levels reached
  the route, and a body with an integer of more than 4,300 digits answered a false
  401 `authentication_failed` on `/v0/threads` and `/v0/vnext/memories/commit`
  (checked), where v0.20.0 answers HTTP 400 on `/v0/threads` and lets the other
  through to its route. Checked with raw requests to a running API: a
  5 MiB body to `/v0/vnext/memories/commit` and to `/v0/threads` answered HTTP 413
  in v0.20.0, where v0.19.2 has no cap and reads the whole body, and a body nested
  2,000 levels answered HTTP 422 `json_too_deep` where v0.19.2 answered HTTP 500.
  A
  request inside the cap still costs memory and time, and the cap is no rate limit.
- **DB-009, provider calls followed redirects.** Every provider, embeddings,
  reranker, fact-key, brain, Gmail and Calendar call goes through one function,
  `open_provider_url` in the new `provider_http` module, which opens
  its own opener, speaks only http and https and follows no redirect: the redirect
  target is never contacted, so an `Authorization` header or an API key is not sent
  on to it. Its `enforce_public_peer` argument has no default. The provider helpers,
  response generation, Gmail and Calendar pass `True`, so they dial only an address
  the outbound policy allows (not loopback, private, link-local, multicast or
  otherwise non-global), resolved when the connection is made. A name that was
  public when the base URL was checked and is loopback when the connection is made
  (DNS rebinding) is refused before a connection is opened, over http and https.
  The embeddings, reranker, fact-key and brain clients pass `False`, so a loopback
  endpoint such as the `http://localhost:11434/v1` that the README gives for
  `ALICE_EMBEDDINGS_BASE_URL` still works, and only redirects are refused. A
  request carried by an HTTP or HTTPS proxy skips the address check, because the
  peer is then the proxy. Checked with two local servers and an embeddings
  endpoint that answers 302: v0.19.2 followed it with a bodyless GET to the second
  server and sent the `Authorization` header with it, and v0.20.0 did not contact
  the second server and named the redirect in the failure reason. The response body
  of a provider call is still read whole. One call is outside the function: the
  reachability probe of `alicebot vnext alpha check --headless` opens the
  `--api-url` and `--web-url` you give it with a plain `GET` that carries no
  credential, and it follows redirects.
- **DB-010, the local-folder scan could read a file swapped for a link.** The scan
  opens the watched folder, each directory below it and the file one at a time,
  each relative to the one before and with `O_NOFOLLOW`, checks on the open
  descriptor that it is a regular file, and takes the text, size and modification
  time from that descriptor. A file or directory swapped for a link, a FIFO and a
  device are skipped and counted in `refused_count`. In v0.19.2 the scan checked
  that a file was inside the watched folder and then read it by path, so a swap
  between the two steps was read from outside the folder, a FIFO put in its place
  hung the scan, and a link to `/dev/zero` was read without a limit. A hard link
  planted inside the watched folder to a file elsewhere is still read, as in the
  importers, because a hard link is the file itself. The attack needs someone who
  can write to the watched folder during a sync. Checked by swapping the file after
  the containment check: v0.19.2 returned the text of a file outside the folder for
  a link, and hung (killed after 15 seconds) for a FIFO and for a link to
  `/dev/zero`; v0.20.0 skipped each one and counted it in `refused_count`.
- **DB-011, the local-folder scan had no size or count limit.** The scan reads at
  most 2 MiB of one file, stops at 10,000 files or 64 MiB of text in all, and lists
  at most 100,000 directory entries, as "What to do after upgrading" says. In v0.19.2
  it listed and sorted the whole walk and read every matching file whole, and one
  file that was not UTF-8 text, or that the process could not read, ended the sync
  with an error. `refused_count` and `truncated` are written to the
  `connector.local_folder_scan` event and shown as `last_scan` in the health output
  of the connector, and `alicebot vnext connectors local-folder sync` and `watch`
  print them (in each run for a polling `watch`), also when the batch ends
  `partial` or `failed`. The scan does not enter an ignored folder, so a watched
  folder with a large `node_modules` is no longer cut short before its notes are
  reached. A folder that only starts like an ignored name, such as `.github`, is
  entered. Checked by calling the scan on a folder with a 3 MiB file, a file that
  is not UTF-8, a link to a file outside the folder and a `node_modules` folder:
  v0.19.2 read the 3 MiB file whole, counted the `node_modules` file as ignored, and
  ended the scan with a `UnicodeDecodeError` while the invalid file was present;
  v0.20.0 returned the small note, skipped the other two and reported
  `refused_count` and `truncated`. The command line was not
  run, because it needs Postgres.
- **DB-008, two scheduled CI jobs held issue-write authority while they installed
  packages.** This concerns two scheduled jobs of this project, the weekly real-host
  canary and the nightly archive maintenance, and not the package. In v0.19.2 one
  job installed the current host CLIs with `npm install ...@latest` and `pip install
  hermes-agent` and held `issues: write`, and its checkout kept the job token
  available to later steps, so a compromised package that ran in that job could use
  the token to open, edit and comment on issues. Archive maintenance had `issues:
  write` for the whole workflow, and its job ran `pip install --upgrade pip` and
  installed the dev extras by version range. The canary job and the archive
  maintenance job now hold `contents: read` only and their checkouts keep no
  credentials. A separate job in each workflow, `canary-alert` and `archive-alert`,
  holds `issues: write`, checks out nothing, runs no shell, installs nothing, and
  opens the `[ops]` alert issue when the first job fails; `archive-alert` reads the
  schedule it names from the event that started the run, not from a value the
  installing job wrote. What the two jobs run, and when they alert, are unchanged.
  A test fails when a job that holds a write scope names a package in a pip or npm
  install command without an exact version.

DB-007 is a documentation fix from v0.19.2 and stays one: confirming a pending
write is not a human gate. DB-001 to DB-004 were fixed in v0.19.2, and DB-012 is
closed above. The credential check is a pattern check, as v0.19.2 said.

## Importers and backups

- **A long ChatGPT conversation imports.** The `mapping` of a conversation was
  walked with one recursive call per message, so a conversation whose messages form
  one chain of about 1,000 replies overran the interpreter's recursion limit. The
  command answered `alice_memory_failed` (`command_failed` on `alicebot vnext
  sources import-chatgpt`) with exit 1 and nothing imported, from that conversation
  or from any other. The walk is a loop over an explicit stack now and returns the
  same order. Checked with an export of one 1,500-message chain and one short
  conversation: v0.19.2 failed with `alice_memory_failed`, and v0.20.0 imported
  both with status `ok`. A chain of 3,000 messages and a chain of 100,000 import.
- **One bad conversation no longer sinks the import.** A conversation whose
  transcript still cannot be built is counted as failed and named by its position,
  as `conversation 2 refused: conversation_unreadable` in `errors`, and the others
  import, so the status is `partial`, as it is for a conversation whose capture
  fails, and `failed` when every conversation is refused. A refused conversation
  keeps its position, and a credential skip inside it is not reported. It is logged
  as one line with its position, the code and the name of the error type, with no
  traceback and none of the error's text. A `MemoryError` ends the import. Checked
  with three conversations, the middle one with a `create_time` that is an integer
  too large for a float: v0.19.2 failed the whole import, and v0.20.0 imported the
  other two with exit 0. A file nested too deeply for the JSON decoder is refused
  with `ChatGPT export is nested too deeply to read`, where v0.19.2 answered
  `alice_memory_failed`.
- **Size limits.** See "What to do after upgrading", step 8. The message names the
  file (its name, not its path, and withheld if the credential check flags it) and
  both sizes, for example `import source file is too large: big.md is 17825808 bytes
  (17.00 MiB), the limit is 16777216 bytes (16.00 MiB). Raise the limit with
  --max-file-mib, or import a smaller file.` The size is taken from the open
  descriptor before the read, the read stops one byte past the limit so a file that
  grows or reports a size of zero is refused too, and a file swapped for a link
  after the path was resolved, a FIFO and any other file that is not a regular
  file are refused. A file that is not UTF-8 is refused by its name and not by a
  byte offset. The text read is the same as before. A ChatGPT export is one JSON
  file that the importer must parse whole. On synthetic exports, measured while the change was built, peak memory was about
  80 MB plus 5.7 MB for every MB of export (377 MB at 52 MB), or 8.7 MB for every MB
  when one character outside the Basic Multilingual Plane is in the file (535 MB at
  52 MB), so 512 MiB needs about 3 to 4.6 GB, and about 11 to 16 minutes at the 1.3
  to 1.9 seconds for every MB that were measured.
  A 16 MiB Markdown file peaked at 335 MB and took about 15 to 23 seconds. The defaults come
  from those measurements and not from a survey of real exports. A folder is still
  held in memory whole, so the limit is per file and not per folder. The loaders
  `load_markdown_payload`, `load_chatgpt_payload`, `load_openclaw_payload`,
  `import_markdown_source`, `import_chatgpt_source` and `import_openclaw_source`
  take `max_file_bytes` with the same defaults and raise `ImportFileTooLargeError`,
  a `ValueError`. Checked with a 17 MiB Markdown file (refused, no source written),
  a 2 MiB file with `--max-file-mib 1` (refused) and with `--max-file-mib 3`
  (imported), and `--max-file-mib 0` (`invalid_request`, exit 2).
- **Named files.** `alicebot vnext sources capture-file`, `alicebot vnext connectors
  browser-clipper capture --file` and `alicebot vnext agents ingest-output --file`
  read their file once, bounded, and with a link refused at the open. The path is
  resolved first, so a link the caller types is followed as before and the source's
  identity does not change. In v0.19.2 the three read the whole file with no limit,
  followed a link put in place of the file after the path was resolved, and waited
  on a FIFO. These three commands were not run, because they need Postgres.
- **Deep JSON in a backup.** `alice-memory import` refuses a backup with JSON nested
  too deeply for it to read, with `restore_failed`, before anything is written. That
  is `metadata_json` on every record type that has it, `payload_json` on events, and
  `value`, `source_event_ids`, `previous_value`, `new_value`, `candidate` and
  `aliases` where a record has them. JSON text nested more than 256 levels in
  `previous_value`, `new_value`, `source_event_ids` or `candidate` of a memory
  revision, in `value` or `source_event_ids` of a memory and in `aliases` of an
  entity is refused too, which is the limit the key claim walk already applied to
  `metadata_json` and `payload_json`. A record whose JSON is a mapping or list
  nested about 1,000 levels or more, a line nested too deep to decode and a header
  whose extra key is nested past what the digest line takes are refused the same
  way. Import prints one line before the error record, for example
  `alice-memory: line 12: event_log column payload_json is nested too deeply for
  import to read`. The line names the file line, the table and the column and never
  a value. A text column that is not a JSON column is not read as JSON: a source
  chunk's text or a memory title made of 10,000 brackets is restored as the text it
  is. In v0.19.2 every refusal ended with the generic `alice_memory_failed` and no
  reason, except the 256-level and `agentic_memory` ones, which gave `restore_failed`
  and no reason, and revision text that the decoder could read (up to about 10,000
  levels) was stored. Checked with three edited backups: a 20,000-level text in an
  event's `payload_json` ended with `alice_memory_failed` in v0.19.2 and with
  `restore_failed` and a line naming `event_log` and `payload_json` in v0.20.0; a
  400-level text in a revision's `previous_value` was stored by v0.19.2 and is
  refused now; a 300-level `metadata_json` ended with `restore_failed` in both, and
  with the reason line in v0.20.0.
- **Export of a vault that holds deep text.** `alice-memory export` of a vault that
  already holds such text, for example one written by a v0.19.0 or v0.19.2 import,
  ends with `export_failed` after one line that names the table and the column. With
  `--out` it leaves no output file. To standard output it has already written
  records by then and stops with no footer, so a shell redirect keeps a partial
  file that import refuses, and that file should not be kept. In v0.19.2 it ended
  with `alice_memory_failed`, and its standard output was partial in the same way.
  Checked with a revision `previous_value` of 3,000 levels: with `--out` there was
  no file, and a redirect of standard output held 10,854 bytes in four lines and no
  footer, which `alice-memory import` refused with `import_validation_failed`. The
  text cannot be exported, and nothing in this release rewrites it.
- **`--mode skip` accepts legacy rows.** The schema bootstrap fills a few columns of
  a row from the rest of the row each time a vault is opened: a source's
  `dedupe_key`, a memory's `created_by_agent_id` and `run_id`, and, for a memory that
  keeps its project scope only under `agentic_memory`, the canonical
  `project_scope` in `metadata_json` and `project_id`. A file from an older vault or
  a hand-made one can leave such a column empty, or not carry it at all. Import stores
  the row as the file gives it and the next open of the vault fills the column in, so
  in v0.19.2 a second `--mode skip` import of the same file stopped with
  `restore_failed`. Skip no
  longer compares a column the file row does not carry, and it compares a memory or a
  source whose derived column the file gave empty as the bootstrap will fill it. A
  column the file gives with a value is compared as before, so a row that really
  differs (other text, another agent, a stored agent or dedupe key that the row's own
  metadata or content does not give) is still refused, and `--mode fail` still stops
  on any existing id. The comparison runs only for a row that does not match as it
  is, on a scratch in-memory database that never touches the vault.

## Hermes provider

Plugin 0.5.3 replaces each lone surrogate in the user text, the assistant text, a
mirrored memory write and the prefetch query with U+FFFD before it queues or sends
them, so a turn that carries one is saved. A high surrogate directly followed by a
low one is joined into the one character it stands for. The plugin logs and counts
nothing about a replacement.

- In plugin 0.5.2, which is in v0.19.2, the surrogate was sent and the server's
  HTTP 500 dropped the turn, `on_memory_write` raised `UnicodeEncodeError`, and
  `prefetch` raised it while building the request URL.
- The server side is fixed too. See "Request bodies".
- The provider is not in the wheel: see step 2 above. A `--symlink` install picks up
  the change.

## Request bodies

- **A lone surrogate.** A JSON request body that holds a lone surrogate, for example
  the escape `"\ud800"`, is refused with HTTP 422 on every route that takes a POST,
  PUT, PATCH or DELETE, as long as the JSON decoder can parse the body. The error is
  the usual validation error, a `detail` list of `type`, `loc` and `msg`, where `loc`
  says where the text is and nothing from the body is repeated. The check looks
  everywhere in the JSON: a string field, a value inside a dict or list that a route
  takes as any value, and an object key, which shows as `[key]` in `loc`. It reads a
  body sent as `application/json`, as `application/*+json` or with no content type.
  A valid pair written as two escapes, such as `"\ud83d\ude00"`, is one character
  and is not refused. A path with no route keeps its 404 and a path whose route does
  not take the method keeps its 405. In v0.19.2 pydantic refused a surrogate in a
  string field or in an unknown top-level key and the handler that writes the error
  then raised `UnicodeEncodeError`, so the answer was HTTP 500, which is what
  dropped a Hermes turn sent to `POST /v0/continuity/captures/candidates`. A
  surrogate in a dict, a list or a key inside one was not checked and reached the
  route.
- **A body that is not UTF-8.** A request body that is not valid UTF-8 and has no
  JSON content type, for example UTF-16 or UTF-32 JSON or arbitrary bytes sent with
  no `Content-Type` header or with `text/plain`, is answered with HTTP 422 and one
  validation error of type `model_attributes_type`, with `loc` `["body"]`, the
  message `Input should be a valid dictionary or object to extract fields from` and
  no `input`. The answer is the same on every route that takes a body, except the
  browser-clipper capture route, which keeps its own fixed `value_error` and answers
  400 for a `text/plain` body it cannot parse. A body that is valid UTF-8 is answered
  as before. With `Content-Type: application/json` the answer is unchanged. In
  v0.19.2 the same request answered HTTP 500: the framework hands a route the raw
  bytes of a body with no JSON content type, pydantic puts them in the `input` of
  the validation error, and the handler that renders the error decoded them as UTF-8
  and caught only `UnicodeEncodeError`. It now catches both, cuts an error whose
  input cannot be decoded to `type`, `loc` and `msg`, and encodes each error on its
  own, so another error in the same response keeps its `input`. The fix is in the
  renderer, so it covers every content type that is not JSON and every route a later
  release adds. Checked with raw requests to a running API: a UTF-16 body with no
  content type, a non-UTF-8 body sent as `text/plain` and a body with `"\ud800"` to
  `POST /v0/threads` each answered HTTP 500 in v0.19.2 and HTTP 422 in v0.20.0.

## Recall, the context pack and `alice_resume`

- **Recall and the pack read the memories that reference their packed sources in one
  lookup per request.** They use the lookup to label a packed excerpt whose derived
  memory was corrected or superseded. The labels, the `current_memory_id` fence and
  every other field are unchanged. A new store method,
  `list_memories_referencing_sources`, does the batched read on SQLite and Postgres
  and returns the rows the one-source method returns, in the same order and under the
  same cap. In v0.19.2 recall and the pack asked the store once for each packed
  source (51 asks for 50 sources, counting the provenance hop), and each ask parsed
  the JSON of every stored memory, so the cost grew with the number of sources packed
  times the number of memories stored. On a synthetic SQLite vault of 4,000 captured
  sources (one 2 KB chunk each), 1,000 memories and 19,000 events, built and timed
  with `scripts/measure_recall_source_lookup.py` (median of seven, one development
  machine), `alice_recall` with the default `limit` of 8 took 93 ms in v0.19.2 and 76
  ms now, `alice_recall` with `limit` 50 took 226 ms and 86 ms, and
  `alice_context_pack` took 97 ms and 76 ms. With 5,000 memories in place of 1,000,
  `alice_recall` with `limit` 50 took 893 ms and 143 ms. Repeated runs differ by a
  few milliseconds, and by up to about 10% with the load on the machine; the ratio
  between the versions held. On Postgres the method saves the round
  trip per source and not the scan, and that side has not been timed.
- **`alice_resume` and `alice_recent_decisions` refuse a query of more than 40,000
  UTF-8 bytes before they read anything**, and the tool error names the limit. The
  bytes are counted as sent and again after each backslash, `%` and `_` in the query
  is escaped with a backslash, so 20,001 underscores is over the limit and 20,000 is
  not. The answer is `invalid_request` with a message such as `query is 50399 UTF-8
  bytes; the limit is 40000. Use a shorter query.` The query is never cut to fit. It
  is the limit and the error `alice_recall` and `alice_context_pack` already use.
  These two tools match the query as one literal substring, so the limit on distinct
  search terms does not apply to them. The four SQLite reads behind them refuse such
  a query themselves, so no other caller of them reaches SQLite's `LIKE or GLOB
  pattern too complex`. In v0.19.2 a query of 49,999 plain bytes or more, or 25,000
  underscores or more, answers `tool_execution_failed` with no detail from
  `alice_resume` once the vault holds an active memory of any type or an open loop,
  and from `alice_recent_decisions` once it holds a stored decision. A query of
  40,001 to 49,998 plain bytes is taken there, and so is a query of any size on a
  vault with none of those. Those are refused now, because the check looks at the
  query alone. Checked on SQLite with one active decision: queries of 45,000 and
  50,500 bytes answered `invalid_request` from both tools in v0.20.0; v0.19.2 took
  45,000 and answered `tool_execution_failed` at 50,500. The HTTP API reads the
  Postgres store, which has no such limit, and no HTTP route reaches the SQLite
  store, so neither is changed. `alice_resume` is one of the three default SQLite
  tools. `alice_recent_decisions` is listed and callable only with
  `ALICE_MCP_FULL_TOOLS=1`.

## Benchmarks

- **The LongMemEval numbers carry a published known issue.** In the LongMemEval_s
  data the id of every evidence session starts with `answer_` and no filler session
  id does, and the benchmark harness showed the reader model each session's id, so
  the model could see which sessions held the evidence. We have not measured how
  much this helped, so the numbers (64.6%, 79.4% and 81.2%) may be overstated by an
  unknown amount. The README, the benchmark README and the honesty kit say so, and so
  does each page that states one of the numbers. The release notes of v0.8.0, v0.9.2,
  v0.13.1, v0.15.7 and v0.16.0 gain a dated correction paragraph and are otherwise
  unchanged. The honesty kit also lists the replication run's fingerprint digest,
  which it had left out, and calls the 81.2% replication the headline instead of the
  79.4% single run. No number changed and no benchmark evidence file was edited.
- **Harness 1.1 hides session ids by default.** It writes a label instead, `S` plus
  ten hex characters of an HMAC-SHA256 over the question id and the session id (key
  id `lme-anon-v1`, a constant experiment key), in the stored source title, the first
  paragraph of each session's text, the source metadata, the header above every
  excerpt, the JSON excerpt record and the checkpoint rows. The label-to-id mapping
  goes in a sidecar file next to the checkpoint and nowhere else, and a label
  collision inside one question stops the run before it starts. `--raw-session-labels`
  restores the old behaviour for reproducing earlier runs. The fingerprint and every
  checkpoint row now record the session label mode, the excerpt source, the promotion
  mode, the surface and the harness version, and `--resume` refuses to mix rows that
  differ in any of them. Until now the excerpt source was not recorded: a
  pack-excerpts run and a store-chunks run from the same commit had the same
  fingerprint digest. Three new options: `--excerpt-source` (the environment variable
  still works), `--promotion-mode sources_only`, which leaves capture's candidate
  memories unpromoted as after a real import (the default, `all_candidates`,
  force-accepts every candidate as every earlier run did), and `--surface recall`,
  which hands the reader the text the shipped `alice_recall` tool returns instead of
  a rendered context pack. The fingerprint digest of a 1.1 run never equals that of a
  1.0 run, so compare per-question rows, not digests. The notes are in
  `docs/benchmarks/longmemeval/REPRODUCTION-NOTES.md`.
- **The harness embeds like the product.** It used to embed each candidate at capture
  and promote it without embedding again. It now embeds each memory when it promotes
  it, in batches, so the memories that have vectors, and the text each vector is made
  from, are the same as in the product, and under `--promotion-mode sources_only` it
  embeds nothing.
- No benchmark was run for this release, and no published number changes. The next
  LongMemEval result is planned to hide the session ids, use the `pack_excerpts` mode
  and replace these numbers.

## Behaviour changes an integrator will notice

- **HTTP.** HTTP 413 with `request_too_large` for a body over the cap. HTTP 422 with
  type `json_too_deep` for a body nested more than 256 levels, and HTTP 422 where
  v0.19.2 answered HTTP 500 for a lone surrogate (any JSON body, or a key) and for a
  body that is not UTF-8 and has no JSON content type. HTTP 401 `authentication_failed`
  for a keyless request whose `Host` or `Origin` does not name this machine.
- **Redirects.** A provider, embeddings, reranker, fact-key, brain, Gmail or Calendar
  call that is answered with a 301, 302, 303, 307 or 308 fails with a message that
  names the status, where v0.19.2 followed up to ten of them and turned a POST
  answered 301, 302 or 303 into a bodyless GET.
- **MCP errors.** `alice_resume` and `alice_recent_decisions` answer `invalid_request`
  for a query over 40,000 UTF-8 bytes, as `alice_recall` and `alice_context_pack`
  already did.
- **Context pack.** `token_report.cut_item_count`, only when an item was cut. An item
  that does not fit no longer drops the items after it. `current_memory_id` can be
  absent for a retired, expired or looped successor. A pack memory keeps
  `validity.superseded` when its `superseded_by` pointer names a memory the caller
  cannot read. `metadata_json` ids of memories the caller cannot read are removed or
  replaced by `(id withheld)` in a `debug: true` pack.
- **Embeddings.** `alice-memory reindex-embeddings` and `alicebot vnext memories
  backfill-embeddings` print `failed_ids`, `failed_ids_omitted`, `failure_reasons`,
  `input_cap_chars` and `truncated_inputs`. A memory is embedded when it becomes
  active, not when it is written. A forgotten, rejected, pending or expired memory is
  not embedded, listed or counted. `alice-memory doctor` prints `memories without a
  current vector`. A vector of a cut text has `truncated_to_chars` in its signature.
  `list_memories_missing_embeddings` requires `statuses`.
- **Importers.** The error code `import_file_too_large`, the option `--max-file-mib`,
  and a ChatGPT import that ends `partial` with `conversation N refused:
  conversation_unreadable` in `errors` where v0.19.2 failed whole.
- **Backups.** `restore_failed` with a line naming the file line, the table and the
  column for the cases listed above, and `export_failed` for a vault that holds
  text too deep to write. `--mode skip` accepts a legacy row.
- **Local-folder connector.** `refused_count` and `truncated` in the
  `connector.local_folder_scan` event, in the health output as `last_scan`, and in the
  output of `sync` and `watch`. `ignored_count` no longer counts files inside an
  ignored folder.
- **Settings.** `ALICEBOT_ALLOWED_HOSTS`, `ALICEBOT_MAX_REQUEST_BODY_BYTES`,
  `ALICEBOT_MAX_CONNECTOR_SYNC_BODY_BYTES` and `ALICE_EMBEDDINGS_MAX_INPUT_CHARS`, in
  `.env.example`.
- **Benchmark harness.** Harness 1.1 changes the fingerprint digest, and its
  per-question rows carry new fields.

## Schema and migration

There is no schema change: no new Alembic revision, no SQLite table or column change,
and no new runtime dependency. No dependency pin in `pyproject.toml` moves. A v0.19.2
SQLite vault opens on v0.20.0 as it is, and upgrading does not rewrite stored rows or
re-embed a memory. A vault written by an earlier import that holds JSON text nested
about 1,000 levels or more cannot be exported, as the step above says.

## What this release does not claim

This release was checked with automated security scanning and internal adversarial
review, findings triaged and fixed. No one outside the project has audited the code.

The internal review of v0.19.0 recorded twelve findings, DB-001 to DB-012. v0.19.2
fixed DB-001 to DB-004 and most of DB-012, and its DB-007 fix was documentation. This
release acts on DB-005, DB-006, DB-008, DB-009, DB-010 and DB-011 and closes DB-012.
It does not make the HTTP API safe to expose without a key, a proxy and the topology in
`docs/deployment/single-tenant-self-hosted.md`, and it does not claim to have closed
every way to reach a provider from the server: the embeddings, reranker, fact-key and
brain clients can still reach a loopback or private address that the operator
configured, a request carried by a proxy is not held to the address rule, and a
provider response is read whole. The new `Host` and `Origin` rule was checked with raw
requests and in process, not from a real browser.

The credential check is a pattern check, as v0.19.2 said. It misses some formats and
refuses some harmless notes, and it checks new writes: it does not clean stored
sources, and reads do not filter them. `docs/memory/promotion-personas.md` lists the
gaps. Instruction-shaped notes are not refused, and no catch rate against instruction
attacks has been measured.

Codex and Claude Code were run against what install and the plugin write only in CI, on
Linux, at the pinned versions (codex-cli 0.158.0 and claude 2.1.281). The weekly canary
is set up to run the same tests at the latest release, and it has not run the Codex or
plugin tests yet. No other version or platform was run. The Codex hook was run through
`codex exec` against a loopback mock, not a real model.

The API edge tests run the real app in process with a fake store, and the local-folder
and named-file command lines have unit tests with fakes. The Postgres paths of the
embedding list, backfill and input cap and of the batched source lookup also have
tests in `tests/integration`, which CI runs against a live database. The recall lookup
was not timed on Postgres.

## Known limitations

Open from the internal security review of v0.19.0, with the limits of the fixes above:

- **A request inside the body cap still costs memory and time (DB-006).** The cap is 4
  MiB (32 MiB for connector sync), and it is no rate limit.
- **The Host and Origin rule was not tried from a browser (DB-005).** A name that you
  list in `ALICEBOT_ALLOWED_HOSTS` is trusted as this machine. A request with an agent
  key on `/v0/vnext` or `/v1` is not checked.
- **Some provider clients can still reach a local or private address (DB-009).** The
  embeddings, reranker, fact-key and brain clients are not held to the outbound address
  rule, because a local Ollama endpoint is a documented setup. A request carried by an
  HTTP or HTTPS proxy is not held to it either, and a provider response body is read
  whole. The reachability probe of `alicebot vnext alpha check --headless` does not go
  through the outbound function; it sends no credential and follows redirects. Any
  valid key can register a provider on `/v1`, which authenticates and does
  not authorize.
- **The local-folder scan still reads a hard link (DB-010).** A hard link planted inside
  the watched folder to a file elsewhere is read, because a hard link is the file
  itself. The limits (2 MiB a file, 10,000 files, 64 MiB, 100,000 directory entries) are
  fixed in code and are not settings.
- **Confirming a pending write is not a human gate (DB-007).** `alice_memory_commit`
  with `confirmation_id` updates the one pending row it names, and the confirm step
  relies on the agent asking you. Alice cannot tell whether it did.

Open in recall, the brief and embeddings:

- **The session brief, `alice_resume` and `alice_recent_decisions` still show an
  expired active memory.** `alice_memory_manage` with `action: expire` sets `valid_to`
  and leaves the status `active`. Recall and the context pack do not return such a
  memory, as in v0.19.2, but these three list memories by status and do not check
  `valid_to`. Checked
  on SQLite with one expired decision: `alice_recall` returned nothing and `alice_context_pack` returned no memory (its
  `recent_changes` still named the memory's id through its creation and expire
  events, as in v0.19.2), and `alice_resume`, `alice_recent_decisions` and
  `alice-memory brief` named it. They do not read vectors.
- **Consolidation and the roll-up semantic tier can send an expired memory's text to
  the embeddings endpoint.** For clustering they embed memories that already hold a
  vector, and they do not check `valid_to`. Embedding at write time, reindex, backfill
  and the doctor do check it.
- **The roll-up pass reads accepted roll-up cards without checking `valid_to`.** The
  lookup that finds the accepted card for a roll-up key (`list_accepted_rollup_cards`)
  has no expiry test, so a card whose `valid_to` has passed still counts as the
  accepted card for its topic when the pass looks for one.
- **Promoting a reviewed artifact into a memory does not embed it.** The new active
  memory has no vector until the next `alice-memory reindex-embeddings` or `alicebot
  vnext memories backfill-embeddings`, so recall finds it by full text only until
  then.
- **The `max_tokens` budget prices the full stored row, and the agent receives a
  compact row.** On SQLite, one short committed memory at `max_tokens` 800 was priced
  at `token_estimate` 784, and the compact payload the tool returned was
  `serialized_token_estimate` 443. The pack was empty at 700. A budget therefore
  leaves room unused and can return nothing for a memory that would fit in compact
  form.
- **A vector made from a cut text represents only the head of the memory.** A query
  that matches only the part past the cut is found by full-text search, which reads all
  of the memory, and not by vector search. How long a memory can be depends on the door.
  The Postgres HTTP commit routes take up to 20,000 characters of text, and
  `alice_memory_commit` on SQLite has no length limit: a 2,000,000-character memory was
  stored whole, in v0.19.2 as well.
- **A long query is slower than a short one.** Against a synthetic vault of 4,000
  captured sources (one chunk of about 2 KB each), 1,000 memories and 19,000 events, the
  median of three runs of `alice_recall` on one development machine was 3.9 seconds at
  499 distinct terms taken from the vault's own words, 8.9 seconds at 499 terms that
  occur nowhere in the vault, and 0.07 seconds for a two-word query. v0.19.2 took the
  same 3.9 and 8.9 seconds, and 0.09 seconds for two words, so this release did not
  change it. The limit refuses a query
  that SQLite cannot take. It does not stop a query within the limit from taking
  several seconds on a vault with thousands of sources.
- **Text already sent to an embeddings endpoint cannot be taken back.**

Open in importers and backups:

- **A folder is held in memory whole.** The size limit is per file, not per folder, and
  a ChatGPT export needs several times its size in memory.
- **A vault that already holds deep JSON text cannot be exported.** See step 11 above.
  Nothing rewrites the stored text. An export to standard output that fails has
  already written part of the stream, with no footer, so a redirect leaves a partial
  file that import refuses.
- **The continuity-store loaders for ChatGPT still recurse over the nesting of a
  message's content** and fail at about 480 levels, which neither import command
  reaches.

Open in the plugin packaging:

- **The marketplace install runs v0.19.2.** Until a change after this release moves
  the pin in `.claude-plugin/marketplace.json`, `claude plugin install
  alice-memory@alicememory` installs plugin 0.19.2, which pins
  `alice-memory==0.19.2` and carries none of the fixes in this release.

> **Update (2026-10-02):** v0.20.0 is published, and the marketplace file on `main` now pins the v0.20.0 tag commit, so the marketplace install runs v0.20.0. The copy inside the v0.20.0 tag still pins v0.19.2, so add the marketplace from the repository, not from a checkout of the tag.

Carried over from v0.19.2:

- **The commit routes trust the role a client sends.** On
  `POST /v0/continuity/captures/commit` and `POST /v1/memory/operations/commit` the
  role is the field that carried the text. A candidate labelled as a user explicit
  prefix is auto-saved.
- **Install exits 0 when it finds no launcher.** It warns, and writes entries that run
  `uvx`.
- **A refusal reaches an MCP client as `tool_request_failed`,** with no detail. This
  includes a refused `alice_capture`. The oversized query on `alice_recall`,
  `alice_context_pack`, `alice_resume` and `alice_recent_decisions` is the one typed
  exception.
- **No command removes a stored source on SQLite.** Doctor lists flagged sources and
  exits 0.
- **One credential in the assistant reply drops the whole Hermes turn.**
- **Every capture refusal is a generic `invalid_request`.** A client cannot tell a
  credential refusal from another bad request.
- **OpenCode has no SessionStart hook.** Run `alice-memory brief` instead.
- **The credential checks do not all agree.** The memory commit door, source capture,
  the Markdown and ChatGPT imports and the SQLite source doctor use the commit door's
  verdict. Backup import refuses a memory row on the credential floor alone and lists
  what the floor flags in the other records without refusing them. Memory approvals,
  review edits and corrections, among others, use the floor alone. A low-entropy key
  shaped like an AWS access key id is therefore refused by the first group and
  accepted by the second.
- **Codex skips the hook until you trust it,** and skips it again each time a re-run
  changes its command. Install cannot trust it for you.
- **A `config.toml` that already defines hooks gets no hook from install.** It prints
  the hook and exits 1 until you add it.
- **Install checks Alice's Codex entry and the number ranges in
  `docs/integrations/codex.md`.** It does not check every rule Codex applies to the
  rest of the file.
- **No test drives a Codex approval prompt.** The tool hints follow Codex's default rule
  as recorded in this repo, and that rule is Codex's to change.
- **Project and local plugin scopes are invisible to install,** and the plugin needs
  `uv` on `PATH`.
- **A Hermes `alice` block with a comment is edited by hand** whenever install has a
  change to make.
- **The brief cut can split some characters:** Devanagari conjuncts, Thai and Lao SARA
  AM, and Prepend characters. Tag-sequence flags and Hangul jamo stay whole.
