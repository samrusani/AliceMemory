# Alice v0.15.5 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.15.5","publication_status":"published","checksums_status":"recorded"} -->

**Two install-path defects, both found by running Alice for real rather than by reading it.**

Take this release if you run Alice from an MCP host, and especially if you import
your own notes. Both fixes came out of one Hermes install and one Obsidian
vault import, and neither would have surfaced in a test suite or a code audit.

There is no schema change, no migration, and no configuration change.

## A host's PYTHONPATH could stop Alice from starting at all

`uvx` installs Alice into an isolated environment, but Python still honours
`PYTHONPATH` from the parent process and places those entries near the front of
`sys.path`. An MCP host launched from inside a conda environment or a virtualenv
leaked its own site-packages into our interpreter, and a NumPy built for a
different Python ABI shadowed the one we installed.

The result was a hard failure on startup, before the server accepted a single
request, with a traceback naming NumPy rather than anything of ours:

```
File ".../site-packages/alicebot_api/sqlite_store.py", line 32, in <module>
    import numpy as np
ImportError: <foreign build, wrong ABI for this interpreter>
```

Both `alice-memory --version` and `alice-memory mcp` were affected.

Alice now puts its own installation ahead of anything `PYTHONPATH` injected. It
**reorders and never removes**, so anything your host provides that Alice does
not ship still resolves exactly as before, and only a shadowing copy of a
dependency Alice ships itself loses. A source tree you deliberately placed on
`PYTHONPATH` is left alone.

If you were working around this by unsetting `PYTHONPATH`, `VIRTUAL_ENV` and
`CONDA_PREFIX` before launching, you no longer need to.

## Correction, 2026-08-16: the chunking fix below does not reach `alice_capture`

**Added after publication. The section that follows overclaims and is left in
place rather than rewritten.**

The chunking change is real and works when `chunk_text` is called directly. It
does **not** fix an import performed through the `alice_capture` MCP tool, which
is the path the reported symptom came from.

The cause is upstream of the chunker and was not found until v0.15.5 was verified
against the published artifact. `mcp/arguments.py` collapsed every whitespace run
in `raw_text` to a single space before capture saw it, so a document with 17
newlines was stored with 0. `chunk_text` splits on blank lines, so a flattened
document is one paragraph and gets cut on word count instead. The heading rule
below never has a boundary to act on.

Verified by capturing a markdown vault through `alice_capture` on the published
0.15.5 and reading the rows back out of SQLite: `chunk_count: 1`, identical to
0.15.4.

`v0.15.6` fixes the real cause. **Do not re-import notes on this version.**

The `PYTHONPATH` fix in this release is unaffected and was confirmed against the
published artifact.

## Importing notes produced memories that spanned unrelated notes

Chunking split text on blank lines and then packed paragraphs together up to
2400 characters, treating a markdown heading as ordinary prose. Notes are
usually far shorter than that, so a whole-vault import collapsed many unrelated
notes into one chunk, and the candidate memory extracted from it spanned all of
them.

The user-visible symptom: import a quotes library, then search for a quote you
know is in it, and get nothing back. The text was present, but no memory
corresponded to it cleanly enough to match.

Markdown headings and thematic breaks now end a chunk. A vault of quotes under
their own headings becomes one self-contained chunk per note, and an exact
phrase lands in exactly one of them.

The rule is deliberately narrow. Prose with no headings still packs to the full
budget, the character budget is still enforced within a section, and a `#`
mid-line, as in "ticket #42", is not a heading.

## If you already imported notes

**Re-import rather than approving what is already in review.** Candidates
extracted before this release were produced by the old chunker and are
note-spanning by construction; approving them stores the same problem
permanently. Delete them, then import again on this version.

## Compatibility

No database migration. No schema change. No configuration change. No tool was
added, removed or renamed, and the core tool count is unchanged at eleven.

Both changes are internal. Existing memories, sources and provenance are
untouched, and nothing about an existing database needs rebuilding. Chunking
affects only text captured from this version onward.

## Known limitations

Unchanged from `v0.15.4`:

- **`/v1` authenticates but does not authorize.** Any valid key can do what any
  other valid key can on those routes, and `/v1` writes record no agent, so a
  quarantine sweep by key cannot reach them. Keep `/v1` loopback-only.
- **Importers trust the directory you point them at.** A local actor with write
  access inside a selected import root can reach content outside it.
- **Archived import evidence is decoded text, not a byte image.** CRLF sources
  archive as LF.
- **Tool failures return a generic code and no detail.** The server reports
  `tool_not_found`, `tool_request_failed`, or `tool_execution_failed`. The
  message does not say why, so an agent cannot distinguish a bad argument
  from a missing record. The server log carries the real reason.

New in this release, and worth stating plainly:

- **Chunking improvements do not reach already-captured text.** There is no
  re-chunk migration. Content captured before this version keeps the chunk
  boundaries it was given.

pip install alice-memory==0.15.5
