# Alice v0.10.3 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.10.3","publication_status":"published","checksums_status":"recorded"} -->

> **Correction (2026-09-27):** the audits and review passes named in these notes were internal adversarial review, not an independent or external audit.

`v0.10.3` is a correctness, reliability, scale, and release-process release.
It remediates the fourth external audit's 13 confirmed release-blocking
findings on the published `v0.10.2` baseline, plus the independent-review
correction passes and final punch-list. `v0.10.2` itself remains sound and
published; nothing in this release invalidates its artifacts or provenance.

## Correctness

- **Project isolation.** Agent project scope is enforced end to end: the
  brain, connection, contradiction, and project-automation request paths,
  scheduler workflows, and store queries all honor the caller's effective
  project scope. Consolidation clusters partition by row-level project scope
  even on unscoped runs, and accepting a cross-project consolidation proposal
  is rejected. An explicitly empty `project_scope: []` is authoritative and
  suppresses every legacy fallback.
- **Consolidation dedup.** Accepting a dedup proposal retires every cluster
  member — including the survivor — leaving exactly one active
  representative. Legacy `v0.10.2`-era proposals are repaired to the coherent
  transition on acceptance, so no supersession edge ever points at an active
  row.
- **Review coherence.** Artifact promotion creates its memory target
  atomically or fails; a locked transition table makes `promoted_to_memory`
  and `archived` terminal everywhere; accepted project updates cannot later
  be rejected on any review surface (dedicated, generic HTTP, or MCP);
  resolved confirmations leave the actionable pending queue.
- **Retrieval fidelity.** Inferred query domains are disclosure-only ranking
  hints matched on word boundaries; they can no longer silently filter out
  correctly tagged results (caller-supplied domains remain hard filters).
  Scoped contradiction, recent-change, and temporal stages push predicates
  into the store or deepen fail-closed rather than truncating at a fixed
  200-row prefix, and chunk ranking dedupes by parent source before limiting
  so one long document cannot crowd out other sources.
- **ChatGPT import.** Imports follow the conversation mapping graph in true
  message order, preserve roles and branch-aware timestamps, and create one
  source per conversation with stable identity — no global text dedupe, no
  raw-export duplication.

## Reliability

- Best-effort embedding persistence and read-only grounding probes contain
  store failures instead of failing the memory write or context-pack build;
  cancellation and process-exit signals still propagate.
- Scheduler execution uses per-user claims with fenced durable leases,
  heartbeats, and a reaper; workflow domain writes publish only inside the
  transaction that revalidates and finalizes the exact claim fence. Process
  ownership uses a stable identity token, failed one-shot runs exit nonzero,
  and background `--once` propagates to the child process.
- Response generation is durable: mandatory caller idempotency keys, request
  fingerprints, leases, terminal replay before provider work, and fail-closed
  unknown outcomes prevent duplicate user turns and duplicate provider
  charges across retries.
- Provider discovery/testing/invocation, Telegram polling, folder traversal,
  embeddings, and scheduled generation no longer hold open database
  transactions during external I/O; provider configuration changes use
  revision/fingerprint compare-and-swap, so concurrent stale writers receive
  409 rather than silently clobbering.

## Scale

- Workspace and trace endpoints return bounded samples with authoritative
  counts and truncation metadata instead of materializing entire corpora.
- Capture dedupe uses indexed content-hash lookups (migration `0087`,
  online-safe concurrent indexes with invalid-index retry).
- Candidate embeddings run outside open transactions, and PostgreSQL access
  goes through a connection pool.

## Release and gate integrity

- Publication is draft-first and transactional across GitHub and PyPI: bytes
  are verified before any public release state exists, and the exact-byte
  `finalize-existing-draft` / `resume-pypi-and-finalize` recovery modes
  verify tag/version consistency and can never push unverified bytes.
- The publish gate audits live branch-protection rulesets against the
  workflow's actual check names.
- Control-document truth is mode-aware: published versions must be described
  as published (verified against structured release records and checksum
  receipts), candidates as candidates; stale "latest" claims fail closed.
- Python coverage is attributed to the canonical `alicebot_api` package with
  a per-file floor for `main.py`; web coverage floors rose with per-file
  minimums covering the previously untested approval, Gmail, and app-shell
  surfaces; a pinned-manifest check replaced the skippable LongMemEval
  dataset assertion.
- All 294 OpenAPI operations carry per-operation, source-verified success
  contracts.

## Upgrade

`alembic upgrade head` applies migrations `0087`, `0088`, and `0089`
(idempotent; online-safe; safe downgrades; `0084`–`0086` unchanged).
Migration `0088` backfills provider fingerprints and remains compatible with
previous-binary writes during rolling deployment. Callers of `/v0/responses`
and `/v1/runtime/invoke` must send a stable `Idempotency-Key` per logical
invocation and treat HTTP 202 as an active response job to poll. Durable
scheduler execution requires PostgreSQL; SQLite remains supported for local
memory workflows. No other operator action is required.

## Verifying this release

Alice publishes to PyPI through GitHub Trusted Publishing. Once published,
the wheel and source distribution carry PyPI's integrity attestations, which
bind each file to this repository, the release tag, the publishing workflow,
the exact commit, and the protected `pypi` environment — verifiable on the
project's PyPI page. Their exact SHA-256 digests will be recorded in
`docs/release/v0.10.3-checksums.txt` in this repository as part of the
post-publication commit.
