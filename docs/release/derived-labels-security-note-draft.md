# Security note: derived labels

From v0.20.2, the derived-label fixes tighten recorded-input inserts, restricted report inputs, exact reads, operator lists, and repair. This note describes them. This release was checked with automated security scanning and internal adversarial review, findings triaged and fixed. No one outside the project has audited the code.

From v0.20.2, source GET keeps the operator gate: only the owner and unbound trusted or admin keys reach the lookup; other profiles and project-bound keys receive 403. Behind that gate, source GET and legacy `alice_vnext_review_items` apply the caller's domain, sensitivity and locked project fence, including effective labels of recorded inputs. Graph neighborhood returned edge explanations outside that ceiling in v0.20.0 and baseline main 48873b03; it now lists only the edges whose ends the key may read (see the paragraph on redacted memories). Doctor's aggregate derived-label check counts are new in this set, absent from v0.20.0 and baseline main 48873b03. `GET /v0/vnext/doctor` and `POST /v0/vnext/doctor/run` now omit their content diagnostics for callers with limits: the owner and an unbound admin key receive the flagged-source ids and the derived-label counts, and a trusted key receives both checks as skipped, with no id, count or message taken from the vault. The flagged-source ids were returned to trusted keys in v0.20.0 and baseline main 48873b03. The five corrected screens and these two readers do not establish that every operator route observes the same ceiling.

From v0.20.2, source review and delete now apply the caller's limits, with the source GET. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/sources/{id}/review` (the actions review, update, assign_project and archive) and `DELETE /v0/vnext/sources/{id}` on a source above its sensitivity ceiling and read the whole source (its title and `metadata_json.raw_text`), and could also change it without authority: rename it, assign it to a project, archive it or delete it. The review answer also embedded a trace that carried the text of memories, artifacts and open loops above the ceiling. The exposure covers disclosure, unauthorized modification and unauthorized deletion. It is the same one the source GET closed, reachable one verb away, and it is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. Now both routes answer the same HTTP 404 as the GET for a source above the caller's ceiling or one that does not exist, leave the source and every row around it unchanged, and apply the caller's identity to the embedded trace. The preview that a project move returns before `confirm_label_hide` also counted every derived row that names the source, including the ones above the caller's ceiling, so a trusted key could learn how many confidential rows hang off a source it may read, and whether any do; the count now covers only the rows the caller may read, and a source whose dependants are all above the ceiling moves with the answer a source with none gets. The owner and an unbound admin key are unchanged and see the exact count. Read-only, proposal and project-bound keys keep HTTP 403, and source regeneration stays refused to every key but the owner and an unbound admin. The routes keep the operator gate before the check, so only the owner and unbound trusted or admin keys reach it. The SQLite install has no HTTP route for these verbs. A refused call that the operator gate answers with HTTP 403 still records the gate's own policy event, as before; the HTTP 404 answers record nothing. Graph neighborhood is not covered by this change; the rule that fences it is described in the paragraph on redacted memories, and it keeps an edge that starts at a source above the caller's ceiling out of the answer.

From v0.20.2, belief review and graph edge review now apply the caller's limits, like the source routes above. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/beliefs/{id}/review` on a belief whose memory is above its sensitivity ceiling, and `POST /v0/vnext/graph/edges/{id}/review` on a graph edge that joins such a memory, because neither route took the key into account after the operator gate. The belief answer held the whole belief, its claim included, and the edge answer held the whole edge, its explanation included, which is made from the text of the rows the edge joins. Both calls also changed the stored row: the key could retire, challenge, reinforce or supersede the belief, and accept or reject the edge. The exposure covers disclosure and unauthorized modification. The route code is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. It was found by calling every door that takes a row id with the id of each kind of row a key may not read, which is the check behind the next paragraph. Now both routes answer the same HTTP 404 they give for a missing id when the belief's memory is above the caller's limits, when the belief it would be replaced by is, when either end of the edge is, and when an end of the edge no longer exists, and they change nothing. A missing belief or edge, and an id that is not a well-formed id, now answers HTTP 404 for every caller, where it raised a server error. The owner and an unbound admin key are unchanged. Read-only, proposal and project-bound keys keep the HTTP 403 of the operator gate. The graph neighborhood route lists only the edges whose ends the key may read, by the rule in the paragraph on redacted memories.

From v0.20.2, the event feeds follow the rows they name. The workspace `recent_events` and `agent_activity`, the context tree and the dogfooding view show an event, and the workspace event count counts it, only when the caller may read every labelled row the event names: the row it is about, the two ends of a graph edge it is about (an entity end has no label), and the ids in its payload (`source_id`, `source_ids`, `memory_id`, `candidate_memory_ids`, `replacement_memory_id`, `artifact_id`, `belief_id`, `project_id` and the other fields that hold the id of a labelled row). An id that a client sent and the event repeats (the id of a project in capitals, or with spaces round it) is read as the row it names, and text that is not the id of a stored row cannot be shown to be readable, so it hides the event. A chunk of a source has no label, so its `source_chunk.created` event takes the label of the source its payload names, and a chunk event that names no source, or one that is not stored, is not shown to a caller with limits. An edge with an end of another kind, or an end that is not stored, cannot be shown to be readable and is not shown to a caller with limits either. Until this change every caller was shown these events, one per chunk, with the id of a source above the ceiling of the key, and the event count included them. The owner and an unbound admin key are not limited and still see them. The ids of rows without a label (an entity, a task, a scheduler run, a provenance link, a revision) are not judged, and the `changes` that a `memory.updated` or `project.updated` event copies from a row list the same ids as the row (the `superseded_by` of a corrected memory is one), which the next paragraph describes. A test captures a confidential source through the API, reads the workspace as an unbound trusted key, and checks that no event names the source or its chunks and that the count grows only by the events that name none of its rows; a second test lists every event type the code writes, follows each payload through the variables and helper functions that build it, and fails when a new target type or a new id field is not classified.

From v0.20.2, the source trace follows the rows its events name. `GET /v0/vnext/traces/sources/{id}` and the trace that `POST /v0/vnext/sources/{id}/review` embeds show an event, to a caller with limits, only when the caller may read every labelled row the event names: the row it is about and the ids in its payload, by the rule of the paragraph on the event feeds above. The trace lists the events that target the source or a row of the trace, and until this change it kept them without reading their payloads, so the correction of a memory (`memory.reviewed`) named the memory that replaced it in `replacement_memory_id` after that memory was made confidential, to an unbound trusted key that could not read the memory itself. The events that target a row the trace does not list are still left out, `summary.event_count` counts the events shown, and the owner and an unbound admin key keep every event of the source. A caller with limits is read the newest 2,000 events that the trace asks for, the reach of the event feeds, and no further, so the cost of the read does not grow with the number of events the caller may not read. Only the events the caller can be shown count against that reach: the store reads the events aimed at the source or at a row the trace lists, so an event that merely names the source in its payload (the chunk events of a source, which are aimed at the chunk, and an entity mention) is not read for a caller with limits at all, and a source with more than 2,000 chunks still lists its own events. When events lie beyond that reach and fewer than 500 were shown, `sampling.collection_complete.events` and `sampling.trace_complete` are `false`, and the events older than the reach are not listed. The owner and an unbound admin key are read as before, 501 events at a time. Only those callers and an unbound trusted key pass the operator gate to this route, and a profile handed to the loader inside the process that the gate would refuse is answered as a missing source. The trace still lists the ids that sit in the metadata of the rows it shows, which the paragraph on hidden ids in metadata describes, and the `superseded_by` that a `memory.updated` event copies in its `changes`. A test corrects a memory through the correction tool, makes the replacement confidential, and reads the trace as an unbound trusted key, an unbound admin key and the owner; a second test runs the cases of the event feed against the trace, a third checks that more events than the trace holds, all naming a hidden row and newer than three readable ones, leave the three, a fourth checks that the read of a caller with limits stops at the reach and says so, and a fifth that more chunk events than the reach, all newer than the events of the source itself, leave those events listed and the trace complete for an unbound trusted key.

From v0.20.2, the policy event of an explain of a continuity object is not shown to a caller with limits. `alice_explain` with `continuity_object_id` records a `policy.decision` event with the target type `continuity_object` and the id of the object, and no other path writes one. A call with no key, and a call that declares a permission profile without a key, never reach the recording, a key-bound caller whose policy would not allow the object is stopped before anything is recorded and leaves what a call on an id that is not stored leaves, and a key-bound caller that the policy allows leaves one event, so no caller leaves an event that names an object it may not read. The event is read by other callers, though, and it holds the id of the object and the domain and sensitivity the decision judged (`requested_domains` and `requested_sensitivity_allowed`, and the project scope). A continuity object keeps those labels in its provenance and body in the legacy store, and the label guard reads the labels of sources, memories, open loops, artifacts, projects, beliefs and the ends of edges only, so it cannot show that a reader with narrower limits than the writer may read the object. Until this change the event was shown to every reader in the workspace `recent_events` and `agent_activity`, the context tree, the dogfooding view and the policy telemetry, and counted in the workspace `event_count`. It is now left out of all of them for a caller with limits, as an edge with an end the guard cannot read is, and the owner and an unbound admin key still see it. That holds in the context tree too, where it needed care: the tree filters by a selection of sensitivities and domains, the owner's default selection leaves out the confidential levels, and a selection is not a limit. The tree therefore judges the labels it can read against the selection for every caller, and leaves out an event about a continuity object only for a caller that has limits, whatever it selected; the owner and an unbound admin key keep the event under every selection. The route, the tool and the command line each tell the tree whether the caller has limits, and a tree built by code that does not say is built for a caller with limits. A key therefore does not read its own explains of continuity objects in its telemetry. No writer in the code puts a domain, a sensitivity or a project into a continuity object, so an object is read as the unknown domain and sensitivity with no project unless its row was written another way. Judging the event by the labels of the object, which would show a key its own explains, needs the guard to read the legacy store and is not done. The test that lists every event writer now reads a target type through the functions that hand it on, since the policy events are written by `append_policy_events`, which its callers give the type, and it fails when a target type is neither judged, nor listed as unlabelled, nor listed as withheld here, or when a type is written through an expression it cannot resolve and is not listed with the rows it can be.

From v0.20.2, rows a key can read may list in their metadata the ids of rows it cannot read. In v0.20.2 this was a known exception, not a way of meeting the requirement to filter hidden ids, and the paragraph after this one says what main does now. The ids sit in the lists a producer writes (`candidate_memory_ids`, `derived_from`, `input_summary`, `source_ids`, `memory_ids`, `source_refs`, `stale_marked_memory_ids` and the per-item fields of connection and contradiction reports), in the consolidation lists `cluster_member_ids` and `member_ids`, and in the `content_markdown` that prints them. Beside a member id a consolidation candidate stores that member's status, its update time and a 16-character digest of its title, text, summary and value (`member_snapshots`), and a roll-up proposal stores its topic label and scores; none of these is the member's text. A readable report names a row it cannot read in two cases. The report does not depend on the row, as with the candidate memory a weekly synthesis makes and names, so the owner can make the candidate confidential after the fact. Or the row was taken out of reads after the report was made, as with an archived source. A report that depends on a row is stored at least as strict as that row, so an input made confidential makes the report confidential too, and the report stops being readable. The artifact get and artifact trace routes return these lists as stored to any key whose limits admit the report, a read-only, project-scoped or project-bound key included. The artifact list, source trace, workspace and project dashboard are operator routes and return them to the owner, an unbound admin key and an unbound trusted key. The detail modes of `alice_explain` and `alice_memory_review` return them for a derived memory, such as a project update that lists the sources it was made from, and the list modes of the other memory tools return none of them. The memory audit route (`GET /v0/vnext/memories/{id}/audit`) returns the same lists for a readable derived memory as stored: `consolidation.cluster_member_ids`, `derived_from.memories`, `source_refs` and `value.rollup.member_ids` on the memory, the same fields in its revisions (`previous_value` and `new_value`), and the same fields in the `changes` of its events, so the ids of archived members stand there too. A derived memory that recorded a redacted memory as a member is read by the owner and an unbound admin key only. A memory made from a captured source also keeps the `source_id`, the `source_event_ids` (the source and its chunk) and the `capture_content_hash` it was made with after the source is archived. The hash is the SHA-256 of the source's whole captured text with its project scope. It is not the text, but it tells a caller who holds a text whether it is the one the source had. The detail mode of `alice_memory_review` and the memory audit return these three fields, and the workspace returns them in its event feed, in the `changes` that the events of the memory copied from its metadata, where it also names an archived source by the `target_id` of the source's own events. `alice_explain` returns them while the source can be read and answers the memory of an archived source as unavailable. The scheduler's run records, in the workspace (`scheduler.recent_runs` and `scheduler.last_success_by_workflow`) and in the dogfooding view (`last_successful_scheduler_run`), carry the `artifact_id` of the report a run made, also after that report was made confidential. The scheduler status route (`GET /v0/vnext/scheduler/status`, in `recent_runs` and `last_success_by_workflow`) and the runs route (`GET /v0/vnext/scheduler/runs`, in `items`) list the same run records, and the workspace lists a queued task with the id of the result report it made, in `tasks[].output_artifact_id` and `tasks[].metadata_json.artifact_id`. These carry the id of a report that the answer of a run or of `POST /v0/vnext/queue/process-next` left out because the caller may not read it. The routes admit the owner, an unbound `admin_agent` key and an unbound `trusted_local_agent` key, and refuse every other key HTTP 403, so the unbound trusted key can read the id there. The ids are random UUIDs, or a `source:` or `memory:` reference to one, with no name, path or title in them. They reveal that the row exists and how a report links to it. They grant no access. A key with limits that names such an id to a read, explain, history, trace, export, review, correct, manage, archive, delete, assign or cite door is answered exactly as for a missing id: the same status and body, or the same tool error, and no stored row changes. Two answers show a little more, and they belong to this exception. The recall, context-pack, resume and recent-decisions tools take the id as query text and show nothing of the row, but a query is also read for dates, so their results are not compared with a missing id's. And a memory commit whose `source_refs` names an id under a prefix other than `source:` (such as `artifact:`) has that entry left out of its answer when the id names a source the key cannot read, which tells a key whether an id it already holds names such a source and nothing more. Ids are not the only thing a report keeps. A report is written once and keeps the words and values it was made with, so the words of a row that was archived or redacted after the report was made stay in it. The `content_markdown` of a daily brief, a weekly synthesis, an open-loop review and a project update prints the lines of the rows it used. The `explanation` of a connection holds the title and shared terms of a source, the `quote_new` of a contradiction holds its text, and the `suggested_current_state` of a project update holds its claim. A roll-up card keeps the text, label and amounts of every memory it rolled up (`value.rollup.instances`), and a consolidation candidate keeps the 16-character digest of each member's title, text, summary and value as it was when the candidate was made (`member_snapshots`). Redacting a memory scrubs the memory, its revisions, its events, its quoted provenance and the project update artifacts coupled to it, and does not rewrite the reports and cards that printed or copied it, so a redacted memory's text stays in them. A key reads the words of an archived row as it read them in the report: a report is stored at least as strict as the rows it used, so the key could read the row when the report was made, and archiving restricts nothing. The words of a redacted memory are not read that way: a report that recorded a redacted memory is read by the owner and an unbound admin key only (see the paragraph on redacted memories), so no other key reads them. That is containment and not removal, and removing the words is planned for v0.21.0. The words of archived rows are a known exception, not a way of meeting the requirement to filter hidden ids, and withholding them for a caller with limits is tracked for v0.21.0. Tests run every profile against every door on PostgreSQL through the mounted application, and every tool on SQLite, with each kind of row hidden for each reason: above the ceiling, in a restricted domain, in another project, unverified and archived.

Unreleased (on main, not in v0.20.2): a key with limits is not shown the id of a memory, a source, an artifact or an open loop that it may not read, in any answer of a `/v0/vnext` route, a tool or a command, and the owner and an unbound admin key keep every id. The step runs after the answer is made, for the user the key was authenticated for (not the `user_id` of the query or the body, which only some deployments rewrite), with the whole read ceiling and project binding of the key, and it opens a connection only when the answer holds an id. It checks every JSON string value whose whole value is an id, wherever it sits and under any key, in any spelling `uuid.UUID` takes (any case, hyphens in any place, braces, `urn:uuid:`) and behind a `memory:`, `source:`, `artifact:`, `open_loop:` or `alice://` prefix, and it checks every dict key that is an id. A list drops the entry, a field that holds one id becomes null, a dict key goes with its value, and an entry of a roll-up card (`instances`) or of a consolidation candidate (`member_snapshots`) whose row the key may not read goes whole, with its text, label, amounts and digest. Inside a string the step looks for an id token only in an entry of a list or in the value of a field that a producer writes ids into (`candidate_memory_ids`, `source_ids`, `memory_ids`, `member_ids`, `cluster_member_ids`, `stale_marked_memory_ids`, `source_refs`, `artifact_id`, `output_artifact_id`, `source_id`, `memory_id` and the rest) and in the `content_markdown` of a report; it finds a token by its shape (32 hex digits with hyphens anywhere), compares its canonical form, and removes it as it was written. An id inside free text (a title, a note, a quote, the words a report copied) is not looked for: it is the writer's text, and the label of its own row governs it. At a position that a field name or a prefix types as the id of one of these rows (the lists and fields above, an entry of `source_refs`, an id inside a `source_refs` entry under a field the product reads as a reference such as `memory_id`, `source_id`, `id` or `ref`, and a prefixed reference anywhere) an id that does not resolve to a row the key may read is withheld whether the row is hidden or does not exist, so a key that holds the id of a candidate cannot tell a hidden row from a missing one by what a report or a stored commit repeats of it. At any other position the step cannot tell the id of one of these rows from the id of an event, a task or a chunk, so it withholds only the id of a row that exists and that the key may not read, and an id that names no row stays as it was written. An id the caller supplied is an exemption nowhere. It stays only where the answer repeats the input that held it: at a key named like a path parameter, a query parameter the route declares, a field of the JSON body the route declares or an argument of a tool, reached from the top of the answer through objects and not through a list of rows, and only the ids that input held; a path parameter also repeats at the `id` of the object it names. A query parameter or a body field the route does not declare supplies nothing, so a key cannot confirm that an id belongs to a report by adding the id to the request, and the same id at any other key, in a list of rows or in the metadata of a row is judged like any other id. A prefixed reference under a field the product does not write inside a `source_refs` entry (`origin`, `evidence`) is dropped with its field for a missing row, as the saved-quote reader drops it for a hidden one, also when the caller sent it. A count beside a list that lost entries is recomputed (`derived_from.counts`, `input_summary.counts`, `input_counts`, `member_count`, `instance_count`, `displayed_instance_count`, `instances_truncated`, the `expired_marked` and `unconfirmed_marked` of the stale sweep, and a bare `count`), and a count that the step cannot recompute, because it cannot tell which of several counts the dropped entry was in, is dropped. What a producer computed over its inputs stays like the words it copied: the `aggregation` of a roll-up group, `grouping_input_count` and `grouping_input_total`, and the counts of rows by status in the dogfooding view are values the report keeps and not counts of a list the step shortens. The `capture_content_hash` of a memory made from an archived source also stays. Some answers still differ between a hidden row and a missing row, as in v0.20.2: the search tools, which take the id as query text; a commit answer that leaves out an entry naming a source under a prefix other than `source:`; and an id in a `source_refs` entry that may name a chunk or a session (a bare id under a field such as `origin` or `chunk_id`, an id in a sentence or after a `#`), which the saved-quote reader holds to the rule for rows that exist, and so does the step. The ids of beliefs, edges and projects are not judged. A source archived after an open loop was made from it blanks the loop's source list and leaves its count, in the stored row, so the count of that list is stored and not shortened by the step. Tests run the filter over every door of the mounted application on PostgreSQL, with the unbound admin key as the control that shows each hidden id was there to be withheld, and over every tool on SQLite.

From v0.20.2, the doors that act on one row by id answer a row above the caller's limits as a row that does not exist. In v0.19.2 and in v0.20.0 these doors built a policy decision from the labels of the row and, when it blocked, answered HTTP 403 with that decision (a tool answered with the policy error). The decision repeated the row's domain, sensitivity and project scope, named the reason the row was out of reach, and for a key bound to a project carried the id of a project outside its binding, so a key that held an id learned that it named a row and what kind of row. That disclosed labels, not text. The doors are the artifact get, trace, review, feedback, quality-rating and export routes, the project-update review route, the memory audit, review, correct, expire, forget, redact, undo, unexpire and accept-consolidation routes, the open-loop review route, and the tools `alice_memory_review` (detail), `alice_memory_correct`, `alice_memory_manage` and `alice_open_loops` (close, edit, snooze, reopen). For a key with limits (a read-only, proposal, project-scoped or project-bound key, or an unbound trusted key) a row it may not read now gets the status and body of a missing row, or the tool's not-found error, and the call writes what a call on a missing id writes, which is nothing. That includes the policy events and the agent record: a key reads them back in its own policy telemetry, so a count that moved would tell it that the id named a row. The `alice_explain` tool stops at the same point for each row it would expand and keeps its single opaque answer. An archived or redacted memory is read by no door but redact, and it is outside the limits of every key that has any, so a refused redact of one is answered and written exactly as a redact of a missing id is: HTTP 404 or the tool's not-found error, and no policy event and no agent record. A refusal for a row the key may read is recorded and answered as before, and it repeats only labels the key can read. The owner and an unbound admin key are unchanged. A confirmation is named by its token and not by the id of a row, so a refused confirm keeps its refusal. A memory audit whose replacement chain holds a row the key may not read answers as a missing memory, and an undo that names a successor the key may not read answers as a successor that does not exist. Tests call each of these doors with every kind of hidden row for every profile and compare the answer, and every row each call adds to or removes from a stored table (the event log and the agent records included), with those of a missing id, and read the key's own telemetry before and after.

From v0.20.2, `POST /v0/vnext/open-loops` holds `project_id` to the caller's project binding. In v0.19.2 and in v0.20.0 a key bound to one project could file an open loop under a project outside its binding by naming it in `project_id`, because only the request's `project_scope` was judged, and a `project_id` that named no project was a database error (HTTP 500). A project outside the binding, a project that does not exist and an id that is not well formed now all answer HTTP 404 with `{"detail": "vNext project was not found"}` and write nothing. The owner and a key with no binding may file a loop under any stored project.

From v0.20.2, `POST /v0/vnext/open-loops/extract` judges the loops it returns on the caller's limits, a loop found again by its digest included. The thirteen-route change below cut the request's sensitivities and domains down to the key's own, so a source above the ceiling is not read. It did not judge a loop that was already stored under the digest of a candidate, which the route returned as it stood. The case: an `admin_agent` key extracts open loops from a confidential source and the loop is stored as confidential; the owner edits the description of the loop and lowers only the source to public; an unbound `trusted_local_agent` key (ceiling `public`, `internal`, `private` and `unknown`) then asks for the same extraction and is answered HTTP 201 with the loop and the description, while `POST /v0/vnext/open-loops/{id}/review` answers HTTP 404 for it. The row that the insert returns after a unique-digest conflict, which happens when the project or person column of the stored loop no longer matches the request, was returned the same way. The exposure was disclosure of an open loop and its text above the ceiling, in v0.19.2 and in v0.20.0. Now every loop is judged on its effective labels (the stored label raised to every input) by the guard of the caller: one the key may not read is left out of `open_loops`, out of `created_count` and out of the `created_count` of the `open_loop.extraction_completed` event, so the key cannot learn from either count that the loop exists, and nothing about it is returned. The owner and an unbound `admin_agent` key are shown the loops they were. The service takes the guard as a required argument. The legacy tool `alice_open_loop_extract` is refused whenever an agent key is configured and advertises no identity, and `alicebot vnext open-loops extract` takes none, so both run for the owner. The other doors that return a stored row found by a digest were run once with an unbound `admin_agent` key and then with an unbound `trusted_local_agent` key over a vault that holds a confidential source: the daily brief, the weekly synthesis, the connection report, the contradiction report, the project update candidate and the four scheduler workflows made by `run-now`. Each digest holds the identity of the caller and the rows it read, so the trusted key was answered with its own artifact or run every time and never with the admin key's. The project a loop is filed under, named in `options.project_id` or in the scope of its source, is judged on the caller's limits as well: a project that is hidden, not stored, a free-form name or a malformed id gets no loop, and a hidden and a missing project are answered alike.

From v0.20.2, an open loop made with `POST /v0/vnext/open-loops` over a memory keeps the title and description its caller typed, so words of the memory that the caller put there stay readable to every key that reads the loop after the memory is redacted. That text is not a copy the system made, so redaction does not contain it, and the `memory_id` of the loop reads `null` once the memory is redacted. A loop that a producer made from the memory records it as an input, is a copy, and is contained with the reports. A test pins both.

From v0.20.2, an unbound `trusted_local_agent` key reads the configured local-folder paths in `config.config_json.paths` of `GET /v0/vnext/connectors/{connector_name}/status` even when a file under a path is confidential, which is the same on v0.20.0, while every other profile and a project-bound key get HTTP 403 on that route and an unbound `admin_agent` key still reads the paths, and a fix is planned with the hidden-ids work in v0.21.0.

From v0.20.2, after a memory is redacted the owner and an unbound `admin_agent` key read the rows contained by it by id, in the artifact list and the project list, in the recent commits list and in the project dashboard, but not through recall, the context pack or the default context tree, because the default sensitivity filter of those three reads an unverified row as regulated. A request that names every sensitivity lists them: the `sensitivity_allowed` argument of `alice_recall` and of the context pack, and the `sensitivity_allowed` query of the context tree.

From v0.20.2, after the upgrade, a derived row whose inputs are confidential is labelled confidential, and a derived row with no record is unverified. Either one leaves the owner's default recall, pack and resume, like any confidential row did in v0.20.0. The owner still reads it by id, with a request that names every sensitivity, and through `labels check`, which lists unverified rows.

From v0.20.2, the update candidate that the project update scan writes for a project that is itself contained is not contained. A project is contained when its state was copied from a memory that is then redacted. The scan that asks for the default levels (`public`, `internal`, `private` and `unknown`) no longer reaches a contained project. A scan that names every sensitivity, run by the owner or an unbound admin key, still reaches it. The candidate that scan writes records the sources and memories of the project as its inputs and not the project, so the candidate is readable like any report whose inputs are readable, and its title and body name the project. The state of the project is not printed in it. An unbound `trusted_local_agent` key reads the name of the contained project in the artifact list. A permanent test marks this as an expected failure, and it fails on the day a candidate takes the containment of its project.

From v0.20.2, a derived row is raised to the labels of its inputs when it is stored, and a row that an earlier version stored is repaired when you upgrade. A PostgreSQL database is repaired by migrations `20261004_0095`, `20261005_0096` and `20261011_0097`, which must run before serving requests as the NOSUPERUSER NOBYPASSRLS table owner. A SQLite vault is repaired on its next open and again before a restore is published. `alicebot vnext labels check` and `alice-memory labels check` list the rows that are below their inputs or unverified, and `labels repair` raises the rows that are below their inputs. Each row the repair raises gets one `memory.labels_raised` event (`open_loop.labels_raised` for an open loop and `artifact.labels_raised` for an artifact), which holds the old and new labels and no text or ids, and which has the cause `repair_v4` on SQLite. After the upgrade, a derived row whose inputs are confidential is labelled confidential, and a derived row with no record is unverified. Either one leaves the owner's default recall, pack and resume, like any confidential row did in v0.20.0. The owner still reads it by id, with a request that names every sensitivity, and through `labels check`, which lists unverified rows. An approved weekly-synthesis memory that v0.20.0 wrote on PostgreSQL stays readable, because the read uses the weekly report that names it in `candidate_memory_ids`, and a memory that no report names is unverified. On SQLite there is no report table, so a weekly-synthesis memory there can only arrive by import or a direct insert; it has no report to name it, stays unverified and is listed by `labels check`. A row that `labels repair` cannot fix, such as one with a missing or a redacted input, is listed as unverified, and the remedy is to restore or regenerate it.
