# Draft security note: derived labels

Unreleased (on main, not in v0.20.0): the derived-label fixes tighten recorded-input inserts, restricted report inputs, exact reads, operator lists, and repair. This draft is for review before a release is tagged.

Unreleased (on main, not in v0.20.0): source GET keeps the operator gate: only the owner and unbound trusted or admin keys reach the lookup; other profiles and project-bound keys receive 403. Behind that gate, source GET and legacy `alice_vnext_review_items` apply the caller's domain, sensitivity and locked project fence, including effective labels of recorded inputs. Graph neighborhood still returns edge explanations outside that ceiling; that behavior predates this set. Doctor's aggregate derived-label check counts are new in this set, absent from v0.20.0 and baseline main 48873b03. `GET /v0/vnext/doctor` and `POST /v0/vnext/doctor/run` now omit their content diagnostics for callers with limits: the owner and an unbound admin key receive the flagged-source ids and the derived-label counts, and a trusted key receives both checks as skipped, with no id, count or message taken from the vault. The flagged-source ids were returned to trusted keys in v0.20.0 and baseline main 48873b03. The five corrected screens and these two readers do not establish that every operator route observes the same ceiling.

Unreleased (on main, not in v0.20.0): source review and delete now apply the caller's limits, with the source GET. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/sources/{id}/review` (the actions review, update, assign_project and archive) and `DELETE /v0/vnext/sources/{id}` on a source above its sensitivity ceiling and read the whole source (its title and `metadata_json.raw_text`), and could also change it without authority: rename it, assign it to a project, archive it or delete it. The review answer also embedded a trace that carried the text of memories, artifacts and open loops above the ceiling. The exposure covers disclosure, unauthorized modification and unauthorized deletion. It is the same one the source GET closed, reachable one verb away, and it is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. Now both routes answer the same HTTP 404 as the GET for a source above the caller's ceiling or one that does not exist, leave the source and every row around it unchanged, and apply the caller's identity to the embedded trace. The preview that a project move returns before `confirm_label_hide` also counted every derived row that names the source, including the ones above the caller's ceiling, so a trusted key could learn how many confidential rows hang off a source it may read, and whether any do; the count now covers only the rows the caller may read, and a source whose dependants are all above the ceiling moves with the answer a source with none gets. The owner and an unbound admin key are unchanged and see the exact count. Read-only, proposal and project-bound keys keep HTTP 403, and source regeneration stays refused to every key but the owner and an unbound admin. The routes keep the operator gate before the check, so only the owner and unbound trusted or admin keys reach it. The SQLite install has no HTTP route for these verbs. A refused call that the operator gate answers with HTTP 403 still records the gate's own policy event, as before; the HTTP 404 answers record nothing. Graph neighborhood is not covered by this change and keeps the limit named above: it applies the operator gate and no label fence, and returns the stored explanation of edges that start at a source above the caller's ceiling.

Unreleased (on main, not in v0.20.0): SQLite retirement uses the saved-quote reader's reference rules. Repeated JSON object keys are decoded with the last value retained, and quote subtrees are omitted by that reader. Retirement can consequently retain a loop that an older raw JSON scan would blank. The product does not write those two forms, but an imported or hand-edited row can contain them.

Unreleased (on main, not in v0.20.0): capture overhead has only a few percentage points of headroom below the 15 percent budget. The earlier relabel measurements scale at roughly 2.4 ms per dependant over the measured sizes. Repeat those measurements on a quiet machine before tagging; the read budgets measure a separate path.

Unreleased (on main, not in v0.20.0): memory full-text retrieval refills after effective admission until its limit is met or candidates are exhausted. A legacy adapter that cannot prove exhaustion within 16,384 rows returns a completeness error. Consolidation clustering and staleness sweeps can still under-fill when hidden or shared rows consume their candidate window; their defaults are 2,000 embedded memories and 500 staleness rows. Complete effective-label counts use the full population.

Unreleased (on main, not in v0.20.0): open-loop metadata withholding follows canonical saved-quote parsing for source ids. Its wider pass is source-only: irregular or non-ASCII memory-prefixed ids inside longer text, `alice://sources/` whitespace forms and equivalent imported spellings can retain the id. The product does not write these forms. Unknown trace ids and the loop's free-text columns remain as stored. At 20,000 loops the canonical reverse lookup costs about ten times the earlier scan in the external fixture; SQL text prefiltering is deferred because it must retain JSON escapes and every canonical parser spelling.

Unreleased (on main, not in v0.20.0): redacting a memory now restricts reports and derived rows built from it to the owner and an unbound admin key until they are regenerated without it. In v0.19.2, in v0.20.0 and on main until now, redaction replaced the memory's text and left the reports and cards made from it as they were. A daily brief, weekly synthesis, project update, connection report, contradiction report, consolidation report, roll-up card, weekly candidate, promoted copy or project state keeps the words it copied (the printed lines, the `quote_new` of a contradiction, the titles and shared terms of a connection, the text, label and amounts of each roll-up instance, and the digest of each consolidation member), and every key whose limits admitted the report read those words. This is temporary access containment, not removal: the text stays in those reports and the owner and an unbound admin key can still read it. Full removal of redacted text from reports is planned for v0.21.0. A derived row that recorded a redacted row as an input is now unverified, with the reason `input_redacted`, exactly as a row with a missing input is, and so is every row built from it. The kernel, the per-origin guard and its shared memos, the reduced rank proof, the bulk count and the SQL prefilters all decide it, and a differential test over random graphs with a redacted row at every depth holds the four paths to one answer. A key with limits is refused the row at every door that returns a report or a memory, and its lists, counts and events follow the rows it may read. A belief keeps the claim it copied from its memory, so a belief whose backing memory is redacted is read as a derived row with a redacted input is: by the owner and an unbound admin key only. The graph edges are the exception: they have no label, and a connection edge keeps the explanation it was made with, which can hold the title of a memory redacted since, for the owner and an unbound admin or trusted key; that predates this change and is tracked for v0.21.0. Regenerating a report through its normal route makes a new report that reads no redacted memory and is readable again; the old report stays restricted until it is deleted. Archiving keeps reports' historical content and does not restrict them: an archived memory or source is not redacted, and a report built from one is read as before. `alicebot vnext doctor`, `alice-memory doctor` and `labels check` count these rows as unverified and say to regenerate or delete the reports built from a redacted memory, because `labels repair` cannot fix them.
