# Draft security note: derived labels

Unreleased (on main, not in v0.20.0): the derived-label fixes tighten recorded-input inserts, restricted report inputs, exact reads, operator lists, and repair. This draft is for review before a release is tagged.

Unreleased (on main, not in v0.20.0): source GET keeps the operator gate: only the owner and unbound trusted or admin keys reach the lookup; other profiles and project-bound keys receive 403. Behind that gate, source GET and legacy `alice_vnext_review_items` apply the caller's domain, sensitivity and locked project fence, including effective labels of recorded inputs. Graph neighborhood returned edge explanations outside that ceiling in v0.20.0 and baseline main 48873b03; it now lists only the edges whose ends the key may read (see the paragraph on redacted memories). Doctor's aggregate derived-label check counts are new in this set, absent from v0.20.0 and baseline main 48873b03. `GET /v0/vnext/doctor` and `POST /v0/vnext/doctor/run` now omit their content diagnostics for callers with limits: the owner and an unbound admin key receive the flagged-source ids and the derived-label counts, and a trusted key receives both checks as skipped, with no id, count or message taken from the vault. The flagged-source ids were returned to trusted keys in v0.20.0 and baseline main 48873b03. The five corrected screens and these two readers do not establish that every operator route observes the same ceiling.

Unreleased (on main, not in v0.20.0): source review and delete now apply the caller's limits, with the source GET. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/sources/{id}/review` (the actions review, update, assign_project and archive) and `DELETE /v0/vnext/sources/{id}` on a source above its sensitivity ceiling and read the whole source (its title and `metadata_json.raw_text`), and could also change it without authority: rename it, assign it to a project, archive it or delete it. The review answer also embedded a trace that carried the text of memories, artifacts and open loops above the ceiling. The exposure covers disclosure, unauthorized modification and unauthorized deletion. It is the same one the source GET closed, reachable one verb away, and it is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. Now both routes answer the same HTTP 404 as the GET for a source above the caller's ceiling or one that does not exist, leave the source and every row around it unchanged, and apply the caller's identity to the embedded trace. The preview that a project move returns before `confirm_label_hide` also counted every derived row that names the source, including the ones above the caller's ceiling, so a trusted key could learn how many confidential rows hang off a source it may read, and whether any do; the count now covers only the rows the caller may read, and a source whose dependants are all above the ceiling moves with the answer a source with none gets. The owner and an unbound admin key are unchanged and see the exact count. Read-only, proposal and project-bound keys keep HTTP 403, and source regeneration stays refused to every key but the owner and an unbound admin. The routes keep the operator gate before the check, so only the owner and unbound trusted or admin keys reach it. The SQLite install has no HTTP route for these verbs. A refused call that the operator gate answers with HTTP 403 still records the gate's own policy event, as before; the HTTP 404 answers record nothing. Graph neighborhood is not covered by this change; the rule that fences it is described in the paragraph on redacted memories, and it keeps an edge that starts at a source above the caller's ceiling out of the answer.

Unreleased (on main, not in v0.20.0): belief review and graph edge review now apply the caller's limits, like the source routes above. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/beliefs/{id}/review` on a belief whose memory is above its sensitivity ceiling, and `POST /v0/vnext/graph/edges/{id}/review` on a graph edge that joins such a memory, because neither route took the key into account after the operator gate. The belief answer held the whole belief, its claim included, and the edge answer held the whole edge, its explanation included, which is made from the text of the rows the edge joins. Both calls also changed the stored row: the key could retire, challenge, reinforce or supersede the belief, and accept or reject the edge. The exposure covers disclosure and unauthorized modification. The route code is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. It was found by calling every door that takes a row id with the id of each kind of row a key may not read, which is the check behind the next paragraph. Now both routes answer the same HTTP 404 they give for a missing id when the belief's memory is above the caller's limits, when the belief it would be replaced by is, when either end of the edge is, and when an end of the edge no longer exists, and they change nothing. A missing belief or edge, and an id that is not a well-formed id, now answers HTTP 404 for every caller, where it raised a server error. The owner and an unbound admin key are unchanged. Read-only, proposal and project-bound keys keep the HTTP 403 of the operator gate. The graph neighborhood route lists only the edges whose ends the key may read, by the rule in the paragraph on redacted memories.

Unreleased (on main, not in v0.20.0): the event feeds follow the rows they name. The workspace `recent_events` and `agent_activity`, the context tree and the dogfooding view show an event, and the workspace event count counts it, only when the caller may read every labelled row the event names: the row it is about, the two ends of a graph edge it is about (an entity end has no label), and the ids in its payload (`source_id`, `source_ids`, `memory_id`, `candidate_memory_ids`, `replacement_memory_id`, `artifact_id`, `belief_id`, `project_id` and the other fields that hold the id of a labelled row). An id that a client sent and the event repeats (the id of a project in capitals, or with spaces round it) is read as the row it names, and text that is not the id of a stored row cannot be shown to be readable, so it hides the event. A chunk of a source has no label, so its `source_chunk.created` event takes the label of the source its payload names, and a chunk event that names no source, or one that is not stored, is not shown to a caller with limits. An edge with an end of another kind, or an end that is not stored, cannot be shown to be readable and is not shown to a caller with limits either. Until this change every caller was shown these events, one per chunk, with the id of a source above the ceiling of the key, and the event count included them. The owner and an unbound admin key are not limited and still see them. The ids of rows without a label (an entity, a task, a scheduler run, a provenance link, a revision) are not judged, and the `changes` that a `memory.updated` or `project.updated` event copies from a row list the same ids as the row (the `superseded_by` of a corrected memory is one), which the next paragraph describes. A test captures a confidential source through the API, reads the workspace as an unbound trusted key, and checks that no event names the source or its chunks and that the count grows only by the events that name none of its rows; a second test lists every event type the code writes, follows each payload through the variables and helper functions that build it, and fails when a new target type or a new id field is not classified.

Unreleased (on main, not in v0.20.0): rows a key can read may list in their metadata the ids of rows it cannot read, and that stays so until v0.21.0. This is a known exception, not a way of meeting the requirement to filter hidden ids. The ids sit in the lists a producer writes (`candidate_memory_ids`, `derived_from`, `input_summary`, `source_ids`, `memory_ids`, `source_refs`, `stale_marked_memory_ids` and the per-item fields of connection and contradiction reports), in the consolidation lists `cluster_member_ids` and `member_ids`, and in the `content_markdown` that prints them. Beside a member id a consolidation candidate stores that member's status, its update time and a 16-character digest of its title, text, summary and value (`member_snapshots`), and a roll-up proposal stores its topic label and scores; none of these is the member's text. A readable report names a row it cannot read in two cases. The report does not depend on the row, as with the candidate memory a weekly synthesis makes and names, so the owner can make the candidate confidential after the fact. Or the row was taken out of reads after the report was made, as with an archived source. A report that depends on a row is stored at least as strict as that row, so an input made confidential makes the report confidential too, and the report stops being readable. The artifact get and artifact trace routes return these lists as stored to any key whose limits admit the report, a read-only, project-scoped or project-bound key included. The artifact list, source trace, workspace and project dashboard are operator routes and return them to the owner, an unbound admin key and an unbound trusted key. The detail modes of `alice_explain` and `alice_memory_review` return them for a derived memory, such as a project update that lists the sources it was made from, and the list modes of the other memory tools return none of them. The memory audit route (`GET /v0/vnext/memories/{id}/audit`) returns the same lists for a readable derived memory as stored: `consolidation.cluster_member_ids`, `derived_from.memories`, `source_refs` and `value.rollup.member_ids` on the memory, the same fields in its revisions (`previous_value` and `new_value`), and the same fields in the `changes` of its events, so the ids of archived members stand there too. A derived memory that recorded a redacted memory as a member is read by the owner and an unbound admin key only. A memory made from a captured source also keeps the `source_id`, the `source_event_ids` (the source and its chunk) and the `capture_content_hash` it was made with after the source is archived. The hash is the SHA-256 of the source's whole captured text with its project scope. It is not the text, but it tells a caller who holds a text whether it is the one the source had. The detail mode of `alice_memory_review` and the memory audit return these three fields, and the workspace returns them in its event feed, in the `changes` that the events of the memory copied from its metadata, where it also names an archived source by the `target_id` of the source's own events. `alice_explain` returns them while the source can be read and answers the memory of an archived source as unavailable. The scheduler's run records, in the workspace (`scheduler.recent_runs` and `scheduler.last_success_by_workflow`) and in the dogfooding view (`last_successful_scheduler_run`), carry the `artifact_id` of the report a run made, also after that report was made confidential. The ids are random UUIDs, or a `source:` or `memory:` reference to one, with no name, path or title in them. They reveal that the row exists and how a report links to it. They grant no access. A key with limits that names such an id to a read, explain, history, trace, export, review, correct, manage, archive, delete, assign or cite door is answered exactly as for a missing id: the same status and body, or the same tool error, and no stored row changes. Two answers show a little more, and they belong to this exception. The recall, context-pack, resume and recent-decisions tools take the id as query text and show nothing of the row, but a query is also read for dates, so their results are not compared with a missing id's. And a memory commit whose `source_refs` names an id under a prefix other than `source:` (such as `artifact:`) has that entry left out of its answer when the id names a source the key cannot read, which tells a key whether an id it already holds names such a source and nothing more. Withholding the ids from the lists is tracked for v0.21.0. Ids are not the only thing a report keeps. A report is written once and keeps the words and values it was made with, so the words of a row that was archived or redacted after the report was made stay in it. The `content_markdown` of a daily brief, a weekly synthesis, an open-loop review and a project update prints the lines of the rows it used. The `explanation` of a connection holds the title and shared terms of a source, the `quote_new` of a contradiction holds its text, and the `suggested_current_state` of a project update holds its claim. A roll-up card keeps the text, label and amounts of every memory it rolled up (`value.rollup.instances`), and a consolidation candidate keeps the 16-character digest of each member's title, text, summary and value as it was when the candidate was made (`member_snapshots`). Redacting a memory scrubs the memory, its revisions, its events, its quoted provenance and the project update artifacts coupled to it, and does not rewrite the reports and cards that printed or copied it, so a redacted memory's text stays in them. A key reads the words of an archived row as it read them in the report: a report is stored at least as strict as the rows it used, so the key could read the row when the report was made, and archiving restricts nothing. The words of a redacted memory are not read that way: a report that recorded a redacted memory is read by the owner and an unbound admin key only (see the paragraph on redacted memories), so no other key reads them. That is containment and not removal, and removing the words is planned for v0.21.0. The words of archived rows are a known exception, not a way of meeting the requirement to filter hidden ids, and withholding them for a caller with limits is tracked for v0.21.0 with the ids. Tests run every profile against every door on PostgreSQL through the mounted application, and every tool on SQLite, with each kind of row hidden for each reason: above the ceiling, in a restricted domain, in another project, unverified and archived.

Unreleased (on main, not in v0.20.0): the doors that act on one row by id answer a row above the caller's limits as a row that does not exist. In v0.19.2, in v0.20.0 and on main until now these doors built a policy decision from the labels of the row and, when it blocked, answered HTTP 403 with that decision (a tool answered with the policy error). The decision repeated the row's domain, sensitivity and project scope, named the reason the row was out of reach, and for a key bound to a project carried the id of a project outside its binding, so a key that held an id learned that it named a row and what kind of row. That disclosed labels, not text. The doors are the artifact get, trace, review, feedback, quality-rating and export routes, the project-update review route, the memory audit, review, correct, expire, forget, redact, undo, unexpire and accept-consolidation routes, the open-loop review route, and the tools `alice_memory_review` (detail), `alice_memory_correct`, `alice_memory_manage` and `alice_open_loops` (close, edit, snooze, reopen). For a key with limits (a read-only, proposal, project-scoped or project-bound key, or an unbound trusted key) a row it may not read now gets the status and body of a missing row, or the tool's not-found error, and the call writes what a call on a missing id writes, which is nothing. That includes the policy events and the agent record: a key reads them back in its own policy telemetry, so a count that moved would tell it that the id named a row. The `alice_explain` tool stops at the same point for each row it would expand and keeps its single opaque answer. An archived or redacted memory is read by no door but redact, and it is outside the limits of every key that has any, so a refused redact of one is answered and written exactly as a redact of a missing id is: HTTP 404 or the tool's not-found error, and no policy event and no agent record. A refusal for a row the key may read is recorded and answered as before, and it repeats only labels the key can read. The owner and an unbound admin key are unchanged. A confirmation is named by its token and not by the id of a row, so a refused confirm keeps its refusal. A memory audit whose replacement chain holds a row the key may not read answers as a missing memory, and an undo that names a successor the key may not read answers as a successor that does not exist. Tests call each of these doors with every kind of hidden row for every profile and compare the answer, and every row each call adds to or removes from a stored table (the event log and the agent records included), with those of a missing id, and read the key's own telemetry before and after.

Unreleased (on main, not in v0.20.0): `POST /v0/vnext/open-loops` holds `project_id` to the caller's project binding. In v0.19.2, in v0.20.0 and on main until now a key bound to one project could file an open loop under a project outside its binding by naming it in `project_id`, because only the request's `project_scope` was judged, and a `project_id` that named no project was a database error (HTTP 500). A project outside the binding, a project that does not exist and an id that is not well formed now all answer HTTP 404 with `{"detail": "vNext project was not found"}` and write nothing. The owner and a key with no binding may file a loop under any stored project.

Unreleased (on main, not in v0.20.0): the vector stage of recall and of the context pack does not yet refill after hiding rows. It takes the nearest vectors first and drops the ones the caller may not read afterwards, so with an embeddings endpoint configured and a query that shares no word with the stored text, a restricted caller can get fewer results than exist, down to none, when rows it may not read are the nearest. Nothing the caller may not read is shown. The full-text stage does refill until its limit is met. Refilling the vector stage is tracked for v0.21.0.

Unreleased (on main, not in v0.20.0): SQLite retirement uses the saved-quote reader's reference rules. Repeated JSON object keys are decoded with the last value retained, and quote subtrees are omitted by that reader. Retirement can consequently retain a loop that an older raw JSON scan would blank. The product does not write those two forms, but an imported or hand-edited row can contain them.

Unreleased (on main, not in v0.20.0): capture overhead has only a few percentage points of headroom below the 15 percent budget. The earlier relabel measurements scale at roughly 2.4 ms per dependant over the measured sizes. Repeat those measurements on a quiet machine before tagging; the read budgets measure a separate path.

Unreleased (on main, not in v0.20.0): memory full-text retrieval refills after effective admission until its limit is met or candidates are exhausted. A legacy adapter that cannot prove exhaustion within 16,384 rows returns a completeness error. Consolidation clustering and staleness sweeps can still under-fill when hidden or shared rows consume their candidate window; their defaults are 2,000 embedded memories and 500 staleness rows. Complete effective-label counts use the full population.

Unreleased (on main, not in v0.20.0): open-loop metadata withholding follows canonical saved-quote parsing for source ids. Its wider pass is source-only: irregular or non-ASCII memory-prefixed ids inside longer text, `alice://sources/` whitespace forms and equivalent imported spellings can retain the id. The product does not write these forms. Unknown trace ids and the loop's free-text columns remain as stored. At 20,000 loops the canonical reverse lookup costs about ten times the earlier scan in the external fixture; SQL text prefiltering is deferred because it must retain JSON escapes and every canonical parser spelling.

Unreleased (on main, not in v0.20.0): redacting a memory now restricts reports and derived rows built from it to the owner and an unbound admin key until they are regenerated without it. In v0.19.2, in v0.20.0 and on main until now, redaction replaced the memory's text and left the reports and cards made from it as they were. A daily brief, weekly synthesis, project update, connection report, contradiction report, consolidation report, roll-up card, weekly candidate, promoted copy or project state keeps the words it copied (the printed lines, the `quote_new` of a contradiction, the titles and shared terms of a connection, the text, label and amounts of each roll-up instance, and the digest of each consolidation member), and every key whose limits admitted the report read those words. This is temporary access containment, not removal: the text stays in those reports and the owner and an unbound admin key can still read it. Full removal of redacted text from reports is planned for v0.21.0. A derived row that recorded a redacted row as an input is now unverified, with the reason `input_redacted`, exactly as a row with a missing input is, and so is every row built from it. The kernel, the per-origin guard and its shared memos, the reduced rank proof, the bulk count and the SQL prefilters all decide it, and a differential test over random graphs with a redacted row at every depth holds the four paths to one answer. A key with limits is refused the row at every door that returns a report or a memory, and its lists and counts are over the rows it may read. A belief keeps the claim it copied from its memory, so a belief whose backing memory is redacted is read as a derived row with a redacted input is: by the owner and an unbound admin key only. `POST /v0/vnext/beliefs/{belief_id}/review` is refused to a key that may not read the belief, with the answer of a missing belief, and a refused review changes nothing. A graph edge has no label and keeps the explanation it was made with, which can hold the title of a memory redacted since, so `GET /v0/vnext/graph/neighborhood/{target_id}` lists and `POST /v0/vnext/graph/edges/{edge_id}/review` changes an edge for a key with limits only when that key may read every labelled row the edge joins and none of them is redacted; any other edge answers as a missing edge does (the review answers 404), and a refused review changes nothing. A project end that names the project by a name or by an id that finds no project row hides nothing, as an entity end hides nothing; a project row that exists and is not readable still hides the edge. The review route checks the memory, source, belief and entity ends only, so it also refuses an edge whose end is an artifact, an open loop or a project to a key with limits, as it refuses an edge whose end no longer exists, even when that key may read the row and the neighborhood lists the edge. Regenerating a report through its normal route makes a new report that reads no redacted memory and is readable again; the old report stays restricted until it is deleted. Archiving keeps reports' historical content and does not restrict them: an archived memory or source is not redacted, and a report built from one is read as before. `alicebot vnext doctor`, `alice-memory doctor` and `labels check` count these rows as unverified and say to regenerate or delete the reports built from a redacted memory, because `labels repair` cannot fix them.

Unreleased (on main, not in v0.20.0): thirteen operator routes and one legacy tool now apply the caller's limits. The first paragraph above says the five corrected screens and two readers do not establish that every operator route observes the same ceiling. A sweep of every `/v0/vnext` route found these, each reachable by an unbound `trusted_local_agent` key (ceiling `public`, `internal`, `private`, `unknown`) and identical in v0.19.2 and v0.20.0, so none is a regression of this set. `GET /v0/vnext/memories/recent-commits` and the legacy tool `alice_vnext_recent_memory_commits` listed every commit with its text, title and metadata, and counted it: an admin key committed a memory with sensitivity `confidential`, and the trusted key read it back with HTTP 200. `GET /v0/vnext/context-tree` and `POST /v0/vnext/open-loops/extract` read the sensitivities and domains of the request as a grant, so asking for `confidential` listed confidential projects, sources, open loops and artifacts, and made open loops from confidential sources and returned them. `GET /v0/vnext/settings/brain-charter`, and the `brain_charter` and `tasks` of `GET /v0/vnext/workspace`, returned a charter and queued tasks above the ceiling with their text. `GET /v0/vnext/connectors/{connector_name}/status` listed a confidential source with its title and raw text in `recent_captures`. The connector health block named the last captured item (its source id and its external id, which for a file is its path) and the cursor of the connector (also the path of the last imported file) on `GET /v0/vnext/connectors/{connector_name}/status`, `GET /v0/vnext/connectors`, `GET /v0/vnext/connectors/health`, `GET /v0/vnext/workspace`, `GET /v0/vnext/dogfooding`, `GET /v0/vnext/doctor` and `POST /v0/vnext/doctor/run`, and the same cursors were in the answer of `POST /v0/vnext/connectors/{connector_name}/sync`, in the failed syncs listed by the connector status, and in the event feed of `GET /v0/vnext/workspace`, whose `connector.state_updated`, `connector.sync_started`, `connector.sync_completed` and `connector.sync_failed` events record `cursor_value`, `previous_cursor` and `sync_cursor`: after one confidential import the trusted key read the path of the file there, and after any later sync, its own included, the path the sync started from. `PUT /v0/vnext/settings/brain-charter` replaced a confidential charter the key could not read. The exposure covers disclosure, and for the charter unauthorized modification. Now each route lists, counts and returns only what the caller may read, judged on effective labels, and the owner and an unbound admin key are shown what they were. The recent-commits count covers only the commits the caller may read, so a trusted key cannot learn how many confidential commits exist, and a listed commit loses the saved quote of a source the caller may not read. A charter above the ceiling answers as no charter, and a key that cannot read the stored charter is refused HTTP 403 when it tries to replace it: no charter row changes and the policy event of the refusal is recorded, and the refusal tells the key that a charter above its ceiling exists, because the read answers as no charter in the same state. The read of the stored charter and the save run under one lock, so a charter classified between them is not replaced. The last captured item and the cursors, in the health block, in the sync answer, in the failed syncs and in the four connector events of the workspace feed, are shown to a key only when it may read the source they come from, and are `null` otherwise; an event with a cursor that is not shown is copied, the stored event is not edited, and the event count does not change. A permanent test runs one probe for every `/v0/vnext` route against a vault with hidden rows, and the probe table must list exactly the routes of the application. Known limits that the sweep found and this change does not close: the failure list of the connector status shows the id the importer gave to an item that failed to import, such as a file path, and that item was never stored as a row, so it has no label to judge; a connector keeps one cursor and skips an item at or below it, counting it in `skipped_count`, so a key that syncs can learn whether an item it sent sorts below a cursor it may not read; the workspace event feed still lists the id of a queued task, a person and the charter above the ceiling in the `target_id` of their creation events (`agent.task_created`, `queue.task_enqueued`, `task.created`, `person.created`, `brain_charter.upserted`), though the lists leave the task and the charter out: the event guard judges events about a source, memory, open loop, artifact, project or belief and not about those three (the paragraph on the event feeds above counts a task among the rows without a label, which it is not), and the events hold the id and the names of the fields and no text, so the key learns that a row with that id exists and when it was written, and nothing about what it holds, and the sweep holds it as an expected failure that must start passing when those events are judged; and the legacy `/v0` routes that stay mounted (`/v0/memories`, `/v0/memories/review-queue`, `/v0/open-loops`, `/v0/patterns`, `/v0/playbooks` and others) take no agent key and list rows whatever their label while `APP_ENV` is `development` or `test`, which is the default of a local install, and answer HTTP 404 in any other environment, so a key with limits is no more limited there than a request with no key.

Unreleased (on main, not in v0.20.0): two operator routes that answered HTTP 500 now answer. `POST /v0/vnext/projects` answers HTTP 409 for a slug in use. The answer is the same for the owner, an admin key and a key with limits, and the same whether the project that has the slug is readable or not, so it carries no id, name, label or status of that project. It still tells a key with a ceiling that some project it may not read has the slug, because a slug is unique in the vault and a create cannot succeed without saying so. A key can use that to test whether a hidden project has a slug it guesses, and learns nothing else about the project. It could do that before, because the route answered HTTP 500 for a slug in use and HTTP 201 for a free one. `POST /v0/vnext/queue/process-next` failed for every caller in v0.19.2 and v0.20.0, so no key claimed a task through it. It works now, and an unbound `trusted_local_agent` key claims only a task whose domain and sensitivity it may read. The claim skips a task above the ceiling without locking or changing it, and a queue with nothing else pending answers `idle`, as an empty queue does. Without that limit the fix would have let the trusted key run a confidential task and read its task id and the id of the artifact made from it. The owner and an unbound admin key claim the oldest task.
