# Draft security note: derived labels

Unreleased (on main, not in v0.20.0): the derived-label fixes tighten recorded-input inserts, restricted report inputs, exact reads, operator lists, and repair. This draft is for review before a release is tagged.

Unreleased (on main, not in v0.20.0): source GET keeps the operator gate: only the owner and unbound trusted or admin keys reach the lookup; other profiles and project-bound keys receive 403. Behind that gate, source GET and legacy `alice_vnext_review_items` apply the caller's domain, sensitivity and locked project fence, including effective labels of recorded inputs. Graph neighborhood still returns edge explanations outside that ceiling; that behavior predates this set. Doctor's aggregate derived-label check counts are new in this set, absent from v0.20.0 and baseline main 48873b03, and remain outside the caller's sensitivity ceiling and visible to trusted keys. The owner should review that new count exposure separately before tagging. The five corrected screens and these two readers do not establish that every operator route observes the same ceiling.

Unreleased (on main, not in v0.20.0): source review and delete now apply the caller's limits, with the source GET. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/sources/{id}/review` (the actions review, update, assign_project and archive) and `DELETE /v0/vnext/sources/{id}` on a source above its sensitivity ceiling and read the whole source (its title and `metadata_json.raw_text`), and could also change it without authority: rename it, assign it to a project, archive it or delete it. The review answer also embedded a trace that carried the text of memories, artifacts and open loops above the ceiling. The exposure covers disclosure, unauthorized modification and unauthorized deletion. It is the same one the source GET closed, reachable one verb away, and it is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. Now both routes answer the same HTTP 404 as the GET for a source above the caller's ceiling or one that does not exist, leave the source and every row around it unchanged, and apply the caller's identity to the embedded trace. The preview that a project move returns before `confirm_label_hide` also counted every derived row that names the source, including the ones above the caller's ceiling, so a trusted key could learn how many confidential rows hang off a source it may read, and whether any do; the count now covers only the rows the caller may read, and a source whose dependants are all above the ceiling moves with the answer a source with none gets. The owner and an unbound admin key are unchanged and see the exact count. Read-only, proposal and project-bound keys keep HTTP 403, and source regeneration stays refused to every key but the owner and an unbound admin. The routes keep the operator gate before the check, so only the owner and unbound trusted or admin keys reach it. The SQLite install has no HTTP route for these verbs. A refused call that the operator gate answers with HTTP 403 still records the gate's own policy event, as before; the HTTP 404 answers record nothing. Graph neighborhood is not covered by this change and keeps the limit named above: it applies the operator gate and no label fence, and returns the stored explanation of edges that start at a source above the caller's ceiling.

Unreleased (on main, not in v0.20.0): belief review and graph edge review now apply the caller's limits, like the source routes above. Before this change an unbound `trusted_local_agent` key could call `POST /v0/vnext/beliefs/{id}/review` on a belief whose memory is above its sensitivity ceiling, and `POST /v0/vnext/graph/edges/{id}/review` on a graph edge that joins such a memory, because neither route took the key into account after the operator gate. The belief answer held the whole belief, its claim included, and the edge answer held the whole edge, its explanation included, which is made from the text of the rows the edge joins. Both calls also changed the stored row: the key could retire, challenge, reinforce or supersede the belief, and accept or reject the edge. The exposure covers disclosure and unauthorized modification. The route code is identical in v0.19.2 and v0.20.0, so it is not a regression of this set. It was found by calling every door that takes a row id with the id of each kind of row a key may not read, which is the check behind the next paragraph. Now both routes answer the same HTTP 404 they give for a missing id when the belief's memory is above the caller's limits, when the belief it would be replaced by is, when either end of the edge is, and when an end of the edge no longer exists, and they change nothing. A missing belief or edge now answers HTTP 404 for every caller, where it raised a server error. The owner and an unbound admin key are unchanged. Read-only, proposal and project-bound keys keep the HTTP 403 of the operator gate. The graph neighborhood route still returns the edges of any id with their explanations, which is the graph-edge limit named elsewhere in this note.

Unreleased (on main, not in v0.20.0): rows a key can read may list in their metadata the ids of rows it cannot read, and that stays so until v0.21.0. This is a known exception, not a way of meeting the requirement to filter hidden ids. The ids sit in the lists a producer writes (`candidate_memory_ids`, `derived_from`, `input_summary`, `source_ids`, `memory_ids`, `source_refs`, `stale_marked_memory_ids` and the per-item fields of connection and contradiction reports), in the consolidation lists `cluster_member_ids` and `member_ids`, and in the `content_markdown` that prints them. Beside a member id a consolidation candidate stores that member's status, its update time and a 16-character digest of its title, text, summary and value (`member_snapshots`), and a roll-up proposal stores its topic label and scores; none of these is the member's text. A readable report names a row it cannot read in two cases. The report does not depend on the row, as with the candidate memory a weekly synthesis makes and names, so the owner can make the candidate confidential after the fact. Or the row was taken out of reads after the report was made, as with an archived source. A report that depends on a row is stored at least as strict as that row, so an input made confidential makes the report confidential too, and the report stops being readable. The artifact get and artifact trace routes return these lists as stored to any key whose limits admit the report, a read-only, project-scoped or project-bound key included. The artifact list, source trace, workspace and project dashboard are operator routes and return them to the owner, an unbound admin key and an unbound trusted key. The memory tools return none of them. The ids are random UUIDs, or a `source:` or `memory:` reference to one, with no name, path or title in them. They reveal that the row exists and how a report links to it. They grant no access. A call that names such an id to a read, explain, review, correct, manage, archive, delete or assign door is either answered exactly as a missing id is answered or refused with the policy refusal that any row above the caller's limits gets (HTTP 403 with the policy decision, or the tool's policy error). The refusal confirms that the row exists and can repeat its domain, sensitivity and project scope. Neither answer shows the row's title, text, summary, raw text, chunk or claim, and neither changes a stored row. Withholding the ids from the lists, and answering every call that names a hidden id as a missing one, is tracked for v0.21.0. The report's own text can still quote an input as it was when the report was made, so a report keeps the words of a source that was archived later. Tests run every profile against every door on PostgreSQL through the mounted application, and every tool on SQLite, with each kind of row hidden for each reason: above the ceiling, in a restricted domain, in another project, unverified and archived.

Unreleased (on main, not in v0.20.0): the vector stage of recall and of the context pack does not yet refill after hiding rows. It takes the nearest vectors first and drops the ones the caller may not read afterwards, so with an embeddings endpoint configured and a query that shares no word with the stored text, a restricted caller can get fewer results than exist, down to none, when rows it may not read are the nearest. Nothing the caller may not read is shown. The full-text stage does refill until its limit is met. Refilling the vector stage is tracked for v0.21.0.

Unreleased (on main, not in v0.20.0): SQLite retirement uses the saved-quote reader's reference rules. Repeated JSON object keys are decoded with the last value retained, and quote subtrees are omitted by that reader. Retirement can consequently retain a loop that an older raw JSON scan would blank. The product does not write those two forms, but an imported or hand-edited row can contain them.

Unreleased (on main, not in v0.20.0): capture overhead has only a few percentage points of headroom below the 15 percent budget. The earlier relabel measurements scale at roughly 2.4 ms per dependant over the measured sizes. Repeat those measurements on a quiet machine before tagging; the read budgets measure a separate path.

Unreleased (on main, not in v0.20.0): memory full-text retrieval refills after effective admission until its limit is met or candidates are exhausted. A legacy adapter that cannot prove exhaustion within 16,384 rows returns a completeness error. Consolidation clustering and staleness sweeps can still under-fill when hidden or shared rows consume their candidate window; their defaults are 2,000 embedded memories and 500 staleness rows. Complete effective-label counts use the full population.

Unreleased (on main, not in v0.20.0): open-loop metadata withholding follows canonical saved-quote parsing for source ids. Its wider pass is source-only: irregular or non-ASCII memory-prefixed ids inside longer text, `alice://sources/` whitespace forms and equivalent imported spellings can retain the id. The product does not write these forms. Unknown trace ids and the loop's free-text columns remain as stored. At 20,000 loops the canonical reverse lookup costs about ten times the earlier scan in the external fixture; SQL text prefiltering is deferred because it must retain JSON escapes and every canonical parser spelling.
