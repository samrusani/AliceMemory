# Alice v0.9.2 Release Notes

`v0.9.2` is a security-hardening release. Its contents are finalized here; it
reaches PyPI only through the gated procedure in
[`RELEASING.md`](../../RELEASING.md).

## Highlights

### Project-bound authorization

- A project-bound agent key now inherits its project when a read omits an
  explicit filter. It may narrow that scope, but it cannot widen or bypass it.
- Recall, context packs, explain, review queues, resume, recent decisions, and
  lifecycle operations authorize the persisted resource rather than trusting
  caller-supplied project metadata.
- Review mutations recheck a locked target immediately before applying the
  change. Read-only and proposal-only profiles cannot perform lifecycle
  mutations.
- All 70 `/v0/vnext` routes authenticate at one central boundary. Routes
  without resource-aware project policy fail closed for project-bound keys,
  and mutations without local policy fail closed for read-only/proposal-only
  profiles.
- A key-bound MCP server exposes only the eleven policy-complete core tools;
  legacy tools are neither listed nor callable even if the legacy flag is set.

The affected-version summary and interim guidance are in the
[project-scope security-note draft](v0.9.2-project-scope-security-note-draft.md).
That draft remains internal until a fixed release is available.

> **Update (2026-10-04):** v0.9.2 was published on 2026-07-12. The draft note linked above stayed in this folder and is kept as a historical record.

### Backup, migration, and lifecycle integrity

- SQLite export/import now uses a versioned, checksummed envelope; a consistent
  private snapshot; bounded reads; secure atomic publication; exact collision
  checks; foreign-key-closed portable records; and database/WAL/SHM/journal
  same-file, symlink, hard-link, truncation, and tamper defenses.
- Migration `20260510_0067` safely suspends and restores the append-only
  revision trigger while backfilling an existing data-bearing database.
- Migration `20260711_0083` makes commit and confirmation identifiers unique
  per user. Existing duplicate rows keep their memory content and history;
  later duplicates relinquish only the ambiguous lookup identifier and record
  the canonical row in metadata.
- Corrections cannot revive retired memories. Content changes refresh fact
  keys and embeddings, expire stale derived entity edges, and relink current
  entities. Consolidation acceptance rejects stale member snapshots.

### Retrieval and resource bounds

- Project, person, and time filters are hard filters across every emitted
  context-pack section. Multi-project memories retain canonical scope arrays
  and match by overlap; out-of-scope source references, source-derived dates,
  capture hashes, and chunks are removed before serialization.
- Service limits are authoritative: at most 50 requested items, 50,000 tokens,
  50 scope values, and a time window of `all` or `1d` through `3650d`.
- Budget reports include supplemental content and use fixed-point accounting so
  the disclosed serialized estimate equals the final response size estimate.
- Stored vectors carry provider, model, version, and content signatures.
  Incompatible, unsigned, or stale-content vectors are excluded until the
  reindex command rebuilds them. Project-update reviews also refresh fact keys,
  embeddings, entities, and derived edges.
- Consolidation is bounded to 2,000 memories, a 16 MB float32 similarity
  matrix, and 1,999,000 unique comparisons.

### Web and release engineering

- The web app moves to patched Next.js and React versions. Generic console live
  mode is loopback-only; hosted bearer panels separately allow validated HTTPS.
  URLs/errors are credential-safe, request deadlines are endpoint-specific,
  fixture writes stay local, and vNext adds inline confirm/edit/reject controls.
- Wheels and source distributions now include Alembic and public-eval runtime
  resources. Isolated artifact smokes exercise all four entrypoints and a real
  SQLite commit-to-recall flow.
- Publication now requires a clean exact `origin/main` commit, an annotated
  exact tag, finalized changelog/release notes, successful required checks on
  that SHA, one-time artifact construction, checksums across the job handoff,
  a repository-control attestation, and a protected PyPI environment.
- Benchmark documentation keeps the historical 79.4% LongMemEval result but
  removes unsupported causal and scaling claims. No new paid benchmark score
  is claimed for this patch.

> **Correction (2026-10-01):** The 79.4% result named above has a known issue.
> In the LongMemEval_s data the id of every evidence session starts with
> `answer_`, and the harness showed the reader model each session's id, so the

## Upgrade from v0.9.1

1. Stop Alice writers and record the current release and source SHA.
2. Follow the [backup and restore guide](../alpha/backup-and-restore.md). Restore
   the backup into a disposable target and verify representative memories
   before changing the live database.
3. Install the exact `v0.9.2` artifact only after it is published and its hash
   matches the release manifest.
4. PostgreSQL: run `alembic -c apps/api/alembic.ini upgrade head`, then verify
   that Alembic reports `20260711_0083` as the single head.
5. SQLite: start Alice once to run the in-place schema bootstrap, then verify
   capture, review/correction, recall, and a fresh export.
6. If embeddings are configured, run `alicebot vnext memories
   backfill-embeddings` for PostgreSQL or `alice-memory reindex-embeddings` for
   SQLite. The command rebuilds missing and incompatible vectors.
7. Rotate project-bound agent keys and inspect recent policy/audit events for
   unexpected cross-project activity.

## Rollback

Prefer restoring the pre-upgrade backup into a new database and pointing the
previous application release at that restored target.

Alembic can downgrade `0083` to `0082`, but that downgrade only restores the
old non-unique indexes and removes the derived-edge trigger. It intentionally
does not recreate ambiguous commit or confirmation identifiers that the
upgrade removed from duplicate rows. Do not assume an application-code
rollback is also a complete data rollback.

If any PyPI file is published, the version is consumed. Diagnose the published
state and prepare a new patch version; never rebuild or reuse `0.9.2` with
different bytes.
