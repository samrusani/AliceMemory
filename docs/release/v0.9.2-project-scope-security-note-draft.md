# Draft security note: v0.9.1 project-bound agent keys

> Historical record (2026-10-04): v0.9.2 was published on 2026-07-12, so the condition in the next paragraph is met. This draft is kept as a record only. The v0.9.2 release notes and CHANGELOG.md are authoritative.

> Internal release draft. Do not publish until the fixed v0.9.2 release is
> available and the final affected-version range has been confirmed.

Alice v0.9.1 does not reliably enforce the project binding on an agent API
key. A bound MCP agent can omit the project filter on some reads and receive
same-user data from other projects. Some lifecycle operations also check a
caller-provided project value instead of the persisted target, which can
permit an agent to mutate a memory outside its bound project. The hard
user/workspace boundary remains in place; the issue is isolation between
projects owned by the same Alice user.

The v0.9.2 candidate makes the key binding the effective default scope for
reads and writes, filters every context-pack content section, authorizes
lifecycle changes against the persisted resource, and prevents read-only or
proposal-only profiles from applying mutations. Adversarial cross-project
tests cover the MCP and HTTP control paths; backend query regressions cover
both PostgreSQL and SQLite.

Until v0.9.2 is available, do not use project-scoped keys as a security
boundary between mutually untrusted agents. Stop the affected agent or use a
separate Alice user/database for each trust boundary. Rotate agent keys after
upgrading and review recent policy/audit events for unexpected cross-project
access.
