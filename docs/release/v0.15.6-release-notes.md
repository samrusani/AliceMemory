# Alice v0.15.6 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.15.6","publication_status":"published","checksums_status":"recorded"} -->

**Take this release if you import notes. `v0.15.5` claimed to fix that and did not.**

There is no schema change, no migration, and no configuration change.

## `alice_capture` was flattening documents before they were chunked

`v0.15.5` added a rule so chunking never packs across a markdown heading. That
rule was correct and it never ran on the path that produced the bug report.

The MCP argument parser collapsed every whitespace run in `raw_text` to a single
space before capture saw it. A file with 17 newlines was stored with 0. Chunking
splits on blank lines, so a flattened document is one paragraph and gets cut on
word count instead, straddling unrelated notes. The heading rule had no
boundaries left to act on.

The user-visible symptom was unchanged from `v0.15.4`: import a quotes library,
search for a quote you know is in it, get nothing back.

`raw_text` now normalises line endings and trims the ends, and touches nothing
inside. Indentation, code blocks and list structure survive.

The change is deliberately narrow. Only `raw_text` moves, because only `raw_text`
reaches the chunker. Titles, identifiers and every other scalar field still
collapse whitespace, and a test pins that so the looser handling does not spread.

This also restores what the tool already promised. `alice_capture` says it keeps
text "verbatim with provenance", and it did not.

Introduced in `v0.12.0`, so it survived every release since.

## Re-import on this version

If you imported notes on `v0.15.5` or earlier, **delete those candidates and
import again on `v0.15.6`.** Do not approve them out of the review queue:
they were extracted from flattened text and are note-spanning by construction, so
approving them stores the problem permanently.

The `v0.15.5` notes and changelog entry now carry corrections saying the same
thing, left in place rather than rewritten.

## What changes for existing data

Nothing is rewritten. There is no re-chunk migration, so content captured before
this release keeps the boundaries it was given.

One consequence worth knowing before you re-import: `content_hash` is computed
from the stored text, and the stored text now differs, so re-capturing a document
you captured earlier creates a **new source** rather than deduping against the
flattened copy. That is correct, since the earlier copy was lossy, but it means a
re-import is not a no-op and you should delete the old sources rather than expect
them to be replaced.

## Known limitations

Unchanged from `v0.15.5`:

- **`/v1` authenticates but does not authorize.** Keep it loopback-only.
- **Importers trust the directory you point them at.**
- **Archived import evidence is decoded text, not a byte image.** CRLF sources
  archive as LF.
- **Tool failures return a single generic code.** Every caller-facing failure
  reports `tool_request_failed` with no detail. A wider error code taxonomy is
  designed and will land later; until then the server log carries the reason.

> Correction, 2026-09-25. This was not accurate when published: the server also reports `tool_not_found` and `tool_execution_failed`. None carries detail.

Known and deliberately not fixed here:

- **`alice_vnext_ingest_agent_output` still collapses whitespace in `content`,**
  which it stores as `content_markdown`. Same cause, different tool. It is on the
  legacy surface, so it exists only when an operator sets
  `ALICE_MCP_LEGACY_TOOLS=1`, and it does not reach the chunker, so there is no
  note-spanning consequence. It is lossy storage of markdown and will be fixed
  separately.
- **An indented `#` line is treated as a heading by the chunker.** CommonMark
  would read a four-space-indented `#` as code, not a heading. It affects notes
  that contain indented code split by blank lines.
