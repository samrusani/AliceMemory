# Alice v0.19.2 Release Notes

**Take this release if you use the Hermes provider, the `/v1` memory
operations route, `alice-memory import` or the session-start hook, or if you
give an agent a key, a project scope or a sensitivity ceiling and expect recall
to honor it. It fixes problems found by an internal security review of v0.19.0.
It adds no tool or command and changes no schema. The tag also carries the
Claude Code marketplace file, which pins v0.19.0 until a change after this
release moves it. See "Claude Code plugin".**

- v0.19.0 can save an assistant reply as your own decision when Hermes turn
  capture is on. Hermes plugin 0.5.1 splits each turn back into roles by line,
  so a reply with a line that starts `User: decision: ...` reaches the server as
  your text. v0.19.2 carries plugin
  0.5.2, which sends the two texts apart. See "Hermes provider".

  `decision: ship X` can become an active Decision. v0.19.2 applies only a user

- v0.19.0 `alice-memory import` restores a stored claim that an agent API key
  wrote a row, as the file states it. An edited and re-signed backup can make a
  row read `verified_by_key` with no key behind it. See "Backup import".
- v0.19.0 import restores credential-shaped text in sources, chunks and other
  records without a word to you, and `alice-memory doctor` misses a token that
  sits only in a chunk. See "Backup import".
- From v0.16.0 through v0.19.0, one stored note that contains `jsonrpc` or
  `Content-Length:` makes the SessionStart hook inject nothing. See "Session
  brief".
- v0.19.0 recall and the context pack name the ids of memories that the
  caller's sensitivity ceiling, domain filter or scope hides. See "Memory ids
  behind the read fence".
- v0.19.0 `alice_recall` and `alice_context_pack` fail with no detail for a long
  query on SQLite. v0.19.2 refuses it and says why.
- v0.19.0 marks `alice_memory_review` destructive, so Codex still asks before it
  runs (the tool is listed with `ALICE_MCP_FULL_TOOLS=1`), and its session-start
  hook creates a vault under the current directory for a relative
  `ALICE_MEMORY_DATA_DIR`.

## What to do after upgrading

1. **Upgrade.** With pip: `pip install -U alice-memory==0.19.2`. With uv, run
   `uvx alice-memory@0.19.2 --version` once; it prints the version the hosts
   get. Restart the hosts afterwards.
2. **Hermes:** the provider is copied into Hermes by its installer and is not in
   the wheel. An existing install keeps plugin 0.5.1 until you run
   `./scripts/install_hermes_alice_memory_provider.py --force` from a v0.19.2
   checkout. A `--symlink` install follows the repository. The installed
   `plugin.yaml` says `version: 0.5.2` for the fixed provider.
3. **Callers of `POST /v1/memory/operations/commit`,** `alicebot mutations` and
   the `alice_memory_mutations_*` tools: a candidate that came from assistant
   text, or that matched a phrase such as "I prefer tabs" and not a prefix, is
   now `review_required`. Read it, then commit it with `include_review_required`,
   or have the user's own text carry an explicit prefix such as `decision:`.
   Memories this route already applied under v0.19.0 are not changed by the
   upgrade.
4. **Backups:** an import now prints `provenance claims restored as unverified:
   N` and, unless you pass `--quarantine`, `credential-shaped text in records
   import does not refuse: N`. Read "Backup import" before you script anything
   that compares `export`, `import`, `export` output, because rows that carried an
   agent key claim now differ.
5. **Clients of `alice_recall` and `alice_context_pack`** on SQLite: handle the
   new error code `invalid_request`, and keep the query to at most 499
   distinct search terms and 40,000 UTF-8 bytes.
6. **Run `alice-memory doctor`** on each SQLite vault. It reads source chunk
   text now, so a source that an earlier version stored with a token only in a
   chunk is flagged after the upgrade. No command removes a stored source on
   SQLite. Rotate each credential it lists.
7. **Claude Code plugin:** the marketplace file pins the v0.19.0 tag commit
   until a change after this release moves it, so the marketplace install runs
   v0.19.0 code and carries none of these fixes. See "Claude Code plugin".

   > **Update (2026-10-02):** v0.20.0 is published, and the marketplace file on `main` now pins the v0.20.0 tag commit, so the marketplace install runs v0.20.0. The copy inside the v0.19.2 tag still pins v0.19.0, so add the marketplace from the repository, not from a checkout of the tag.

8. **Hosts that set `ALICE_MEMORY_DATA_DIR`:** give it an absolute path. For a
   relative value, or the literal `${HOME}/.alice` that a host leaves
   unexpanded, the v0.19.0 hook created an empty vault under the directory the
   host started in and showed `Nothing stored yet.`. v0.19.2 prints one line and
   creates nothing. An empty `memory.db` that v0.19.0 left in such a directory is
   not your vault. Look at it before you delete it, in case something else wrote
   there.

## Hermes provider

Plugin 0.5.2 sends the user text and the assistant text of a turn to
`POST /v0/continuity/captures/candidates` as two separate fields. It never
joins them and splits them back into roles.

- A reply that contains a line starting with `User:` can no longer become an
  auto-saved user decision or hide the real user text.
- A multi-line user message is no longer cut to its first line, and two
  different turns no longer share a dedupe fingerprint.
- Each side is capped at 3,800 characters on its own. Before, the joined text
  was capped once.
- A lone surrogate in either text no longer raises `UnicodeEncodeError` out of
  `sync_turn`. That turn is still not saved: the server answers a request body
  that carries one with HTTP 500, as v0.19.0 does. See "Known limitations".
- When the candidate routes answer HTTP 404, the plugin posts one labelled
  `User:` and `Assistant:` text to `POST /v0/continuity/captures`, which reads
  no roles and derives an object only when the whole text starts with a prefix.

Plugin 0.5.1 shipped in v0.18.0 and v0.19.0. The same version is in v0.14.0
through v0.17.0, where this release did not check the auto-save outcome. The
v0.18.0 statement that only
user-role candidates are auto-saved was false for it. The v0.18.0 release notes
carry dated corrections. The provider is not in the wheel: see step 2 above.

## The /v1 memory operations commit

`POST /v1/memory/operations/commit` applies a candidate without review in
`assist` and `auto` mode only when it came from the user, matched an explicit
prefix such as `decision:` or `preference:`, and scored 0.9 or more.

- A candidate from the assistant, and a phrase match from either role such as
  "I prefer tabs" or "we decided", is stored as `review_required` with the
  reason `assist_mode_review_gate` or `auto_mode_review_gate`. Commit skips it
  unless the request sets `include_review_required`.
- An applied candidate carries the reason `user_explicit_prefix_rule`. In
  v0.19.0 it carried `assist_mode_allowlist_explicit_high_confidence` or
  `auto_mode_allowlist_high_confidence`.
- Commit checks the rule again on a row that was stored as `auto_apply` before
  v0.19.2. A row that fails it is skipped and listed as `review_required` with
  the reason `stored_auto_apply_fails_admission_rule`. The stored row is not
  rewritten, so a list and a replayed generate keep showing `auto_apply` for it
  until it is committed.
- `alicebot mutations` and the `alice_memory_mutations_*` MCP tools run the same
  code.
- This is the rule the `/v0/continuity` capture commit has applied since
  v0.18.0. Both now call one function. The v0.18.0 statement that an assistant
  candidate is queued covered the capture routes and not this one.
- The role is the request field that carried the text, `user_content` or
  `assistant_content`. A caller that puts text in `user_content` is taken at its
  word. See "Known limitations".

In v0.19.0 the policy read no role. In `assist` mode it applied an explicit
candidate of an allowed type at 0.9 or more from either role, and in `auto` mode
any candidate of an allowed type at 0.9 or more.

## Backup import

`alice-memory import` is for your own backups. A backup file is not evidence of
who wrote a row, because the footer is an unkeyed SHA-256: anyone can edit a
record and recompute it.

- **Key claims are restored as unverified.** A stored claim that an agent API
  key wrote a row (an `agent_identity` with `auth` equal to `agent_api_key`, in
  `metadata_json` or `payload_json` of any record, including JSON text the
  readers decode) is restored as `auth: imported_claim`, with the original kept
  as `claimed_auth`. An event row that changed has its `integrity_hash`
  cleared. A note that a key really wrote reads `declared_on_keyless_install`
  after a restore.
- **The receipt counts them.** It prints `provenance claims restored as
  unverified: N` after the per-type lines, every time, counting rows.
- **Readers compare `auth` exactly.** Recall, resume and the context pack no
  longer read a value padded with whitespace as a key claim.
- **Deep nesting is refused.** A `metadata_json` or `payload_json` nested more
  than 256 levels is refused with `restore_failed`, and so is JSON text under an
  `agentic_memory` or `agent_identity` key in one of them, which is decoded and
  held to the same 256 levels. The product writes an identity at most three
  levels down. In v0.19.0 all of these are stored. Text too deep for the decoder
  (about 10,000 levels) is the case that breaks reads there: under
  `agentic_memory` in a memory row it makes `alice_recall` raise, and under
  `agent_identity` in an event row it makes `alice_resume` raise. A column that is itself a JSON text too
  deep for the decoder is also refused and nothing is written, but with the
  generic `alice_memory_failed`, not `restore_failed`. See "Known limitations".
- **`--mode skip` accepts a vault's own export.** It also accepts an existing row
  that equals the file's row as the file gives it, so a vault can import its own
  export. A different row under the same id is still refused.
- **Other records are read and listed.** Import reads every text and
  JSON column of each non-memory record (sources, chunks, revisions, provenance
  links, open loops, entities, relationship events, graph edges and events), and
  in a memory row the columns the memory credential check does not read. It
  prints `credential-shaped text in records import does not refuse: N`, one
  `table id column` line per hit, and a note that import restores them
  unchanged. The count line is printed every time except with `--quarantine`,
  where the receipt keeps its own leftover report instead. It never prints the
  matched text, and it withholds an id that is credential-shaped, holds a
  control character or is over 128 characters. The exit code stays 0. A memory
  row is refused as before when the check finds credential material in its
  title, text, summary, value, metadata, key or project. `alice-memory export`
  lists the same rows on stderr. The reading is the credential floor, which is
  the check a memory row gets, and not the commit door's verdict that the doctor
  uses. A low-entropy key shaped like an AWS access key id in a source chunk is
  therefore flagged by the doctor, and import restores it and lists none.
- **The doctor reads chunk text.** `alice-memory doctor` reads every source chunk
  with the commit door's verdict, as well as the source row and `raw_text`. A
  token that sits only in a chunk is listed under `flagged sources` and
  `flagged source ids`. Chunks of a deleted source are not read. The Postgres
  doctor (`alicebot vnext doctor`) still reads source rows only.

In v0.19.0 and v0.18.0 a row restored from an edited, re-signed backup reads
`verified_by_key` with no key behind it, and so does an `auth` value padded with
whitespace. Sources, chunks and the other records come across with no report.

This changes the export, import, re-export comparison that the disaster recovery
runbook and the backup guide describe. `export`, `import`, `export` is identical
except for rows that carried a key claim, which differ in `auth` and
`claimed_auth` (and in `integrity_hash` for event rows). A second round trip is a
fixed point.

Both reads take time, and how much depends on the vault. On a synthetic export of
43,000 records and 35 MB (4,000 sources, 8,000 chunks of about 1 KB, 30,000
events and 1,000 memories), import went from 5.7 to 9.2 seconds, export from 2.0
to 5.3 and the doctor from 2.4 to 6.2. On a second synthetic vault of about
29,000 records and 75 MB (4,000 sources with one chunk of about 2 KB each, 1,000
memories and 19,000 events), the median of three runs on one development machine
went from 2.1 to 7.3 seconds for export, from 5.1 to 10.5 for import and from 8.9
to 12.5 for the doctor.

## Session brief

The SessionStart hook no longer shows an empty brief when a stored note contains
the text `jsonrpc` or `Content-Length:`.

- The check was left over from when the hook read a child process's output and
  has had no purpose since v0.16.0. It affected v0.16.0 through v0.19.0.
- One note about MCP, LSP or HTTP framing, which any connected agent can write
  with `alice_memory_commit`, made the hook print `{}` (a blank line with
  `--format markdown`) and inject nothing. `alice-memory doctor` still reported
  a healthy brief.
- The plugin duplicate-setup line added in v0.19.0 was dropped by the same check.
- The brief still opens with its frame, and every stored note is still flattened
  onto one JSON-quoted line, so a note cannot be protocol framing.

## Memory ids behind the read fence

A memory id is metadata. `alice_recall` and `alice_context_pack` now apply the
same sensitivity, domain, project, person and time fence to the ids they name as
to the memories they return.

- **The correction label.** `current_memory_id` on a corrected passage is left off
  when that memory, or any memory on the way to the current one, is outside the
  caller's fence, cannot be found, or is past a chain of eight corrections.
  `derived_memory_corrected` stays true, so an agent still does not quote the
  passage as current.
- **Pack pointers.** A context pack drops a memory's `supersedes` and
  `superseded_by` pointer when the row it names is outside the fence, with no
  scope set as well as with one. A pointer to a row that cannot be found is
  dropped only when a scope is set. With no scope it is kept as an id-only
  reference, as in v0.19.0. The pack derives `validity` after it drops the
  pointer, so a memory whose only sign of supersession was a pointer to a row the
  caller cannot read also loses `validity.superseded` in the pack, which recall
  keeps. A memory that a correction superseded has status `superseded` and is not
  among the pack's memories, so this needs a pointer set on a row whose status is
  still active. See "Known limitations".
- **Recall validity.** `validity.superseded_by_memory_id` and
  `validity.supersedes_memory_id` on a result are left off under the same fence.
  `validity.superseded` stays true.
- **Recent changes.** The `target_id` of each entry in a pack's `recent_changes`
  passes the fence. An entry about a memory the caller cannot read is dropped and
  the list is filled from older events. The search for older events stops after
  2,048 events, so a vault whose newest 2,048 events are nearly all hidden from
  the caller gets a shorter list, or none, and the pack is still returned.
- **Supersession context.** In a `context_depth: high` pack, a revision the
  caller cannot read is neither named nor titled, and the walk ends there.
- **The owner is inside the fence too.** With no agent key, the owner runs under
  the default sensitivity ceiling, so a confidential memory's events and
  revisions are left out of the owner's `recent_changes` and `supersession_context`,
  as that memory already is from the owner's search results.

In v0.19.0 each of these names the id whatever the caller may read. The label
and the recall validity ids were added in v0.19.0. The pack pointer, `recent_changes`
and `supersession_context` cases are older than v0.19.0.

One place still names a memory id without the fence: ids copied into a stored
memory's `metadata_json`, which an `alice_context_pack` call with `debug: true`
returns. See "Known limitations".

## Confirming a pending write

`alice_memory_commit` declares `destructiveHint: false`, and the v0.19.0 release
notes said it only adds. That is true of adding a fact. Called with
`confirmation_id` and `confirmation_action`, the same tool updates the one pending
row it names (`needs_review` to `active`, or to `rejected`), writes that row's
revision and events, and updates the caller's agent identity row when the call
carries one. By the approval rule the code records for Codex's default mode,
neither call prompts, so the confirm step relies on the agent asking you, and
Alice cannot tell whether it did. No annotation, route or authorization changed in
this release. The v0.19.0 release notes carry a dated correction, and the threat
model and `docs/alpha/mcp-tools.md` say so.

## Recall and the context pack on SQLite

`alice_recall` and `alice_context_pack` refuse, before they search, a query the
SQLite source search cannot take, and the tool error names the limit.

- A query with more than 499 distinct search terms, or over 40,000 UTF-8 bytes
  (counted as sent and again after case folding), answers `invalid_request` with
  a message such as `query has 1000 distinct search terms; the limit is 499. Use
  a shorter query.` The query is never cut to fit, and it is never repeated in the
  message.
- A search term is an ASCII word of two or more characters that is not a
  stopword. A hyphenated id counts once, and a repeated word counts once. The
  limits are the session brief's, from one shared function.
- `invalid_request` is a new MCP tool error code, and the only one whose message
  is not static. The legacy `alice_vnext_context_pack`,
  `alice_generate_contradictions` and `alice_generate_connections` tools answer
  it too, because the SQLite source search raises it for every caller.
- A context pack with `include_sources` false or `context_depth` `minimal` runs no
  source search and still takes a long query.
- `alice_resume` and `alice_recent_decisions` are not changed, and still fail on a
  query of about 50,000 bytes or more once the vault holds the memories they read.
  See "Known limitations". The Postgres backend is not changed.

In v0.19.0 a query with about 991 or more distinct terms, or one over about
50,000 bytes with a captured source in the vault, answers `tool_execution_failed`
with no detail. A query of 500 to 990 distinct terms, or of 40,001 to about 50,000
bytes, was taken. So was a query of any size over 40,000 bytes when the search
read no source row, which is a vault with no captured source or filters that
exclude every source. v0.19.2 refuses those ranges too, because the limits sit
at about half of what SQLite takes and the check looks at the query alone.

## Review tool hint and the data directory

- `alice_memory_review` sets `readOnlyHint` and no longer sets `destructiveHint`.
  The tool is listed with `ALICE_MCP_FULL_TOOLS=1`: the default server lists three
  tools, `alice_memory_commit`, `alice_recall` and `alice_resume`, so the new hint
  reaches you only with the full tool set. It only lists review items or shows
  one. Every table was snapshotted before and after list and detail calls: with no
  identity nothing changes, with an agent identity only `event_log` and
  `agent_identities` rows change, and with an agent API key the key's last-used
  time changes too, the same rows the read-only tools write. By the approval
  rule as the code records it, Codex's default mode should no longer wait for
  approval before `alice_memory_review`. No test here runs a Codex approval
  prompt. `alice_memory_correct`, `alice_memory_manage` and
  `alice_open_loops` still set `destructiveHint` to true. With the full tool set,
  of the eleven core tools six are now read-only, two are non-destructive and
  three are destructive.
- `alice-memory-session-start` refuses a non-empty `ALICE_MEMORY_DATA_DIR` that is
  not absolute after `~` expansion, when the variable is the value in use. It
  prints `Alice: the data directory "<value>" is not an absolute path; set an
  absolute path.`, in `--format markdown` and in JSON, and exits 0. Nothing is
  created, including for the literal `${HOME}/.alice` that a host leaves
  unexpanded. The value in the line has line breaks and other control characters
  written as escapes and is cut at 200 characters with `...`, for `--data-dir` and
  the variable alike. The variable is the value in use only when there is no
  `--data-dir` and the hook is not running as the Claude Code plugin's hook,
  where it is still ignored. An empty variable is the same as unset.
  `alice-memory brief` and `alice-memory mcp` do not read the variable. In
  v0.19.0 the hook creates the vault under the current directory for a relative
  value.

## Build, CI and tooling

- **The eval no longer depends on the day it runs.** Every retrieval request the
  eval harness issues carries a fixed reference time, the corpus epoch
  `2026-01-01T00:00:00Z`, where it used the wall clock. Retrieval resolves a month
  or day without a year in a query against that time. The correction case
  `correction-005` ranked its replacement first by luck of the date through
  2026-09-30. From 2026-10-01 it ranked second, `replacement_mrr` read 0.9167
  instead of 1.0, and
  `tests/unit/test_release_check.py::test_semantic_eval_report_accepts_one_correction_replacement_miss`
  failed on every branch. The semantic release gate still validated such a report,
  but the numbers it attested depended on the day it ran. No expected score
  changes: every suite metric of the SQLite battery matches the 2026-09-30 run,
  and a test runs all six suites under four process clocks and requires identical
  results. Retrieval is unchanged, so this touches no stored data and no API.
- **The commit author check is exact.** It accepts six addresses and no domain as
  a whole: the owner's GitHub noreply address in its plain and id forms,
  `noreply@github.com`, `cursoragent@cursor.com`, and the Dependabot and
  github-actions bot noreply addresses. A misspelled noreply address fails and
  the failure names the commit. In v0.19.0 the check allows any address at
  `users.noreply.github.com`.
- **The marketplace check adds the marketplace three ways.** The dispatch-only
  Real host CI check adds it from `./` and from the HTTPS clone URL, each into a
  fresh HOME, installs `alice-memory@alicememory` and checks the plugin list for
  its id, enabled state and version. It also tries the `samrusani/AliceMemory`
  shorthand and reports the result without failing the job.
- **Web test toolchain.** `jsdom` moves from 26.1.0 to 30.0.1,
  `@axe-core/playwright` to 4.13.0 and `@playwright/test` to 1.62.1. jsdom 30
  declares Node 22.22.2 or later, which the web test job and the deployment-guide
  smoke job already pin. Four name patterns in
  `apps/web/components/shell-basics.test.tsx` match `\s*` where they matched a
  space, because jsdom 30 reports a span as inline. The component is unchanged.
  The web console is not part of the wheel.
- **Build and workflow pins.** The build backend pin moves from `wheel==0.47.0`
  to `wheel==0.48.0`, and `setuptools` stays at 84.0.0. The CodeQL actions move to
  v4.37.7 and `pnpm/action-setup` to v6.0.10, with the pnpm version still 10.23.0.

## Behaviour changes an integrator will notice

- **Import.** The receipt gains `provenance claims restored as unverified: N`,
  printed every time, and `credential-shaped text in records import does not
  refuse: N`, printed every time except with `--quarantine`. A deeply nested
  record is refused, with `restore_failed` or, for a column that is itself too
  deep a JSON text, `alice_memory_failed`. Rows that carried a key claim differ
  between `export`, `import` and `export`.
- **Doctor and export.** `alice-memory doctor` reads chunk text and takes longer.
  `alice-memory export` lists credential-shaped text in non-memory records on
  stderr and exits 0.
- **MCP errors.** `invalid_request` is a fourth tool error code, with a message
  that names the limit.
- **MCP hints.** `alice_memory_review` declares `readOnlyHint` and not
  `destructiveHint`. It is listed only with `ALICE_MCP_FULL_TOOLS=1`.
- **Recall and the context pack.** `current_memory_id`, `supersedes`,
  `superseded_by`, `validity.superseded_by_memory_id`, `validity.supersedes_memory_id`
  and the `target_id` of a `recent_changes` entry can be absent where v0.19.0
  named an id. `recent_changes` can be shorter than five. For the owner under the
  default ceiling, entries about confidential memories are gone. A pack memory
  can lose `validity.superseded` along with a pointer it drops.
- **The `/v1` memory operations commit.** Assistant candidates and phrase matches
  are `review_required`, with new reason strings. See above.
- **Session-start hook.** A relative or unexpanded `ALICE_MEMORY_DATA_DIR` prints
  one line and exits 0 with nothing created. A note with protocol text no longer
  empties the brief.
- **Hermes.** The provider sends `user_content` and `assistant_content` as
  separate fields.

## Schema and migration

There is no schema change: no new Alembic revision, no SQLite table or column
change, and no new runtime dependency. The only dependency pin that moves in
`pyproject.toml` is the build backend's `wheel`. A v0.19.0 SQLite vault opens on
v0.19.2 as it is. Upgrading does not rewrite stored rows. A source that an
earlier version stored with a credential stays until you remove it. Run
`alice-memory doctor` on SQLite, or `alicebot vnext doctor` on Postgres, to list
those sources. The Postgres doctor reads source rows only.

## What this release does not claim

This release was checked with automated security scanning and internal
adversarial review, findings triaged and fixed. No one outside the project has
audited the code.

The internal review of v0.19.0 recorded twelve findings, DB-001 to DB-012. This
release fixes DB-001 to DB-004 and DB-012, apart from the `metadata_json` copies
named below. DB-007 is a documentation fix: the confirm step still relies on the
agent asking you. DB-005, DB-006, DB-008, DB-009, DB-010 and DB-011 are not fixed.
DB-008 concerns two scheduled CI jobs of this project, the real-host canary and
archive maintenance, which hold issue-write authority while they install packages
that are not pinned to an exact version, and not the package. The others are
listed under "Known limitations".

> **Update (2026-10-02):** DB-005, DB-006, DB-008, DB-009, DB-010 and DB-011 are fixed in v0.20.0, published on 2026-10-02, with the limits its release notes state for each fix. DB-008 is fixed there by giving the canary job and the archive maintenance job `contents: read` only and moving the issue alert into a separate job that checks out nothing and installs nothing. The `metadata_json` id gap named below is fixed there too, which closes DB-012.

The credential check is a pattern check. It misses some formats and refuses some
harmless notes. `docs/memory/promotion-personas.md` lists the gaps. It checks new
writes: it does not clean stored sources, and reads do not filter them. The
checks do not all agree. The memory commit door, source capture, the Markdown and
ChatGPT imports and the SQLite source doctor use the commit door's verdict, which
is the credential floor followed by the commit gate. Backup import refuses a
memory row on the credential floor alone. From this release it also lists what
the floor flags in the other records, without refusing them, so its listing is
narrower than the commit door's verdict and than the doctor. Memory approvals,
review edits and corrections, among others, use the floor alone;
`docs/memory/promotion-personas.md` lists the rest. A low-entropy key shaped like
an AWS access key id is therefore refused by the first group and accepted by the
second: `alice_memory_correct` can store it as an active fact, the session brief
prints it, and `alice-memory import` restores it and lists none. `alice-memory
doctor` reads sources and their chunks, not facts, so it does not flag such a
fact. It does flag the same key in a source chunk, which import restores without
listing it.

Instruction-shaped notes are not refused. No catch rate against instruction
attacks has been measured.

Codex and Claude Code were run against what install and the plugin write only in
CI, on Linux, at the pinned versions (codex-cli 0.158.0 and claude 2.1.281). The
weekly canary is set up to run the same tests at the latest release, and it has
not run the Codex or plugin tests yet. No other version or platform was run. The
Codex hook was run through `codex exec` against a loopback mock, not a real
model.

## Known limitations

Open in the internal security review, not fixed in this release. DB-005, DB-006,
DB-010 and DB-011 concern the optional Postgres stack. The SQLite install,
`alice-memory mcp` and the hook run no HTTP API and no local-folder connector.
DB-009 also covers the embeddings endpoint you configure on SQLite.

- **The HTTP API reads a request body before it checks credentials (DB-006).** The
  middleware that guards `/v0/vnext` parses a JSON body of any size before it
  authenticates. A request body of 262,057 bytes sent from a non-loopback client
  was read in full before the 401. The memory and CPU cost at larger sizes was
  not measured.

> **Update (2026-10-02):** Fixed in v0.20.0 (DB-006). A request body over 4 MiB is refused with HTTP 413 before any layer reads it, and a body nested more than 256 levels is refused with HTTP 422. A keyless request from another peer, or with a `Host` or `Origin` that is not this machine's, is refused before the body is read. A request inside the cap still costs memory and time, and the cap is no rate limit.

- **A keyless API does not check the Host header (DB-005).** With no agent key, a
  request from a loopback client goes through the same steps whether its `Host`
  header says `localhost` or `attacker.invalid`. A hostname that resolves to
  127.0.0.1 therefore reaches the API. A browser attack through that was not
  reproduced.

> **Update (2026-10-02):** Fixed in v0.20.0 (DB-005). A keyless request on `/v0/vnext`, `/v1` or a legacy `/v0` route whose `Host` is not `localhost`, `127.0.0.1`, `::1` or an exact name in `ALICEBOT_ALLOWED_HOSTS` is refused with HTTP 401 `authentication_failed`. The new rule was checked with raw requests and in process, not from a real browser.

- **Provider calls follow redirects (DB-009).** The model provider helper checks the
  configured base URL against the outbound policy once, then follows a redirect
  without checking the target, and sends the `Authorization` header on to it. The
  embeddings client, which reads `ALICE_EMBEDDINGS_BASE_URL` and does not apply
  that policy at all, follows a redirect and sends its key on the same way. Both
  were shown with two local servers, with the base URL check stood in for the
  provider helper. The reranker and fact-key clients use the same standard
  library opener and were not run. The provider URL is set by the operator, and no
  external destination was tried.

> **Update (2026-10-02):** Fixed in v0.20.0 (DB-009). No provider, embeddings, reranker, fact-key, brain, Gmail or Calendar call follows a redirect, so the target is never contacted and no `Authorization` header or key is sent on to it. The provider helpers, response generation, Gmail and Calendar also dial only an address the outbound policy allows. The embeddings, reranker, fact-key and brain clients can still reach a loopback or private address that the operator configured. A provider that redirects must be configured with its final URL.

- **The local-folder scan reads each matching file whole, with no size limit
  (DB-011).** A 2 MiB text file became one scan item with 2,097,152 characters.
  The scan has no per-file, file-count or total limit. No exhaustion threshold was
  measured.

> **Update (2026-10-02):** Fixed in v0.20.0 (DB-011). The scan reads at most 2 MiB of a file, stops at 10,000 files or 64 MiB of text and lists at most 100,000 directory entries. A file over the limit, a file that is not UTF-8 text and a file that cannot be read are skipped on their own and counted in `refused_count`.

- **The local-folder scan can read a file swapped for a link (DB-010).** The
  scan checks that a file is inside the watched folder, then reads it by path. A
  file replaced by a link between the two steps is read from outside the folder.
  This needs someone who can write to the watched folder during a sync.

> **Update (2026-10-02):** Fixed in v0.20.0 (DB-010). The scan opens the watched folder, each directory below it and each file relative to the one before and without following a link, so a file or directory swapped for a link, a FIFO and a device are skipped and counted in `refused_count`. A hard link planted inside the watched folder to a file elsewhere is still read.

Open in the memory tools and the Hermes provider:

- **Memory ids in `metadata_json` are not fenced.** An id copied into a stored
  memory's `metadata_json` is returned by an `alice_context_pack` call with
  `debug: true`, whatever the caller may read, for the memory types the debug
  pack lists in its own sections (checked: decision, procedure and belief
  memories; a project fact or preference was not named). That includes the keyless owner,
  who runs under the default sensitivity ceiling and cannot read a confidential
  memory, and an agent bound to a read-only key. The default pack did not name
  it. It needs a memory the caller cannot read and another memory whose
  `metadata_json` carries its id. This was checked on `alice_recall`,
  `alice_context_pack`, `alice_resume`, `alice_recent_decisions` and
  `alice_open_loops`. The other tools, such as `alice_recent_changes` and
  `alice_timeline`, were not checked for memory ids.

> **Update (2026-10-02):** Fixed in v0.20.0. The context pack removes the id of a memory the caller cannot read from the `metadata_json` of the memories it returns, under the same fence as the memory reads. An id in a column other than `metadata_json`, or one that is not a 36-character UUID, is not looked for.

- **The pack can lose `validity.superseded` for a hidden pointer.** A memory whose
  status is still active and whose only sign of supersession is a
  `superseded_by` pointer to a row the caller cannot read reads as superseded in
  `alice_recall` and with no `validity` in the pack. See "Memory ids behind the
  read fence".

> **Update (2026-10-02):** Fixed in v0.20.0. The context pack keeps `validity.superseded: true` on a memory whose `superseded_by` pointer names a memory the caller cannot read, and names no id, as `alice_recall` does.

- **Confirming a pending write is not a human gate.** See "Confirming a pending
  write".
- **The commit routes trust the role a client sends.** On
  `POST /v0/continuity/captures/commit` and `POST /v1/memory/operations/commit`
  the role is the field that carried the text. A candidate labelled as a user
  explicit prefix is auto-saved.
- **`alice_resume` and `alice_recent_decisions` return `tool_execution_failed`
  for a query of about 50,000 bytes or more.** `alice_resume`, one of the three
  tools the default server lists, fails once the vault holds an active memory of
  any type. `alice_recent_decisions` fails once it holds a stored decision. On an
  empty vault both answered at 60,000 bytes. With one active preference or one
  active project fact, `alice_resume` answered at 49,000 bytes and failed at
  50,000 and at 60,000, while `alice_recent_decisions` answered at all three
  sizes. The check that covers recall does not cover these two.

> **Update (2026-10-02):** Fixed in v0.20.0. `alice_resume` and `alice_recent_decisions` refuse a query of more than 40,000 UTF-8 bytes with `invalid_request` before they read anything, so they no longer return `tool_execution_failed` for a query of about 50,000 bytes or more.

- **A long query is slower than a short one.** Against a vault of 60 memories and
  40 captured sources, `alice_recall` took 0.16 seconds at 499 distinct terms and
  0.03 seconds for a two-word query. On a synthetic vault of 4,000 captured
  sources (one chunk of about 2 KB each), 1,000 memories and 19,000 events, 75 MB,
  the median of three runs on one development machine was 3.7 seconds at 499
  distinct terms and 0.30 seconds for a two-word query. The limit refuses a query
  that SQLite cannot take. It does not stop a query within the limit from taking
  several seconds on a vault with thousands of sources.
- **A column that is itself JSON text too deep for the decoder fails import with a
  generic error.** The import writes nothing and exits 1, with
  `alice_memory_failed` and the message "The alice-memory command could not be
  completed", not `restore_failed`. In v0.19.0 a source, event or memory
  revision row with such a column gave `restore_failed`, and a memory row gave `alice_memory_failed`.

> **Update (2026-10-02):** Fixed in v0.20.0. `alice-memory import` refuses every such case with `restore_failed`, nothing is written, and one line before the error record names the file line, the table and the column. A vault that already holds such text, which an earlier import could store in a memory revision, cannot be exported: `alice-memory export` of it ends with `export_failed`.

- **A turn that carries a lone surrogate is not saved.** The server answers
  `POST /v0/continuity/captures/candidates` with HTTP 500 for a body that carries
  one, the same as v0.19.0. Hermes provider 0.5.2 no longer raises on such a turn,
  and the request it sends fails.

> **Update (2026-10-02):** Fixed in v0.20.0. Every route that takes a POST, PUT, PATCH or DELETE answers a JSON body that carries a lone surrogate with HTTP 422 when the decoder can parse the body, and Hermes provider 0.5.3 replaces the surrogate with U+FFFD, so the turn is saved. The provider is not in the wheel, so reinstall it with `--force`.

  `claude plugin install alice-memory@alicememory` installs plugin 0.19.0, which

> **Update (2026-10-02):** v0.20.0 is published, and the marketplace file on `main` now pins the v0.20.0 tag commit, so the marketplace install runs v0.20.0. The copy inside the v0.19.2 tag still pins v0.19.0, so add the marketplace from the repository, not from a checkout of the tag.

- **A refusal reaches an MCP client as `tool_request_failed`,** with no detail. This

## Why 0.19.2 and not 0.19.1

`v0.19.1` was tagged on the commit that merged the release pull request, and
its publish run then failed at the draft readback. A release script imported the
`alicebot_api` package from inside a function, and the jobs that read back,
finalize, resume and recover a release do not install the package. The workflow
runs from the tag, so the fix cannot reach the tagged commit, and repository
rules protect stable tags against both deletion and update, which is correct.
The tag stays and the number is retired rather than reused. Nothing was
published under it: no PyPI artifact and no published GitHub Release. This
mirrors `v0.13.0` and `v0.15.0`, which are recorded the same way. `v0.19.2`
carries the same product changes as the `v0.19.1` commit and adds the
release-script fix and the tests that keep those jobs free of package imports.
