# Alice v0.20.2 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.20.2","publication_status":"published","checksums_status":"recorded"} -->

**Take this release if you give an agent a key with limits (a read-only,
project-scoped, project-bound or trusted key), run the PostgreSQL stack, keep
reports or summaries that Alice made from your notes, or use the SQLite vault
and want to delete a source. It makes a derived summary, report or copy follow
the labels of the rows it was made from. It makes the operator routes, the event
feeds, the doors that act on one row by id and the readers of saved quotes and
open-loop ids apply the caller's limits. It fixes routes that answered a server
error, closes the four expiry and embedding gaps that the v0.20.0 notes list as
known limitations, and adds SQLite commands to list and delete a source. The
security advisories published with this release describe the problems it fixes.
It adds commands and settings, and it has upgrade steps, because three
PostgreSQL migrations and a one-time SQLite repair change stored labels. See
"What to do after upgrading".**

- v0.20.0 leaves a derived row (a report, summary or copy) at the label it was
  given when it was made, so a public copy of a confidential input can be read.
  v0.20.2 raises it to the labels of its inputs when it is written, when you
  upgrade and when it is read, and treats a row whose inputs cannot be found as
  unverified. See "Derived rows follow their inputs".
- v0.20.0 shows an unbound `trusted_local_agent` key rows above its ceiling
  through the operator routes, among them the memory audit, which returned the
  memory's text and events. v0.20.2 lists, counts and returns only what the key
  may read. See "Rows above a key's limits".
- v0.20.0 answers a request for a row above a key's limits with a policy decision
  that repeats the row's labels. v0.20.2 answers as for a row that does not exist.
- v0.20.0 names to a key the path of a file whose import failed, the quote a
  commit saved of a memory, the ids an open loop keeps and the ids an event
  names, even when the key may not read the row they come from. v0.20.2 withholds
  them from a key that may not read that row.
- v0.20.0 leaves the reports and cards made from a redacted memory readable.
  v0.20.2 restricts them to the owner and an unbound admin key until they are
  regenerated without it. This is containment, not removal.
- v0.20.0 answers HTTP 500 for `POST /v0/vnext/projects` with a slug in use, for
  `POST /v0/vnext/queue/process-next` on PostgreSQL, and when a memory made by
  promoting a report is redacted. v0.20.2 answers HTTP 409, works, and completes.
- v0.20.0 tells an MCP agent `tool_request_failed` for a refusal and for a bug
  alike. v0.20.2 adds `not_permitted`, `not_found` and `precondition_failed`.
- v0.20.0 lets a restricted caller that names no domain read all five held-back
  domains. v0.20.2 holds that request to the caller's profile.
- v0.20.0 lets a key be bound to the project name `~global`. v0.20.2 refuses to
  create such a key and refuses one that is stored.
- v0.20.0 has no SQLite command to list or delete a source. v0.20.2 adds
  `sources list`, `sources delete`, `sources prune --superseded` and
  `import-markdown --supersede`.
- v0.20.0 shows an expired memory in the session brief, `alice_resume` and
  `alice_recent_decisions`, sends its text to the embeddings endpoint for
  clustering, and leaves a promoted memory without a vector. v0.20.2 does none of
  these.
- New and off by default: per-project memory (`alice-memory project` and
  `ALICE_PROJECT_SCOPING`) and the compact result of `alice_memory_commit`
  (`ALICE_MCP_COMMIT_RESULT=compact`).

## What to do after upgrading

1. **Upgrade the copy your hosts run.** A host runs the command that
   `alice-memory install` wrote into its config, which is `uvx alice-memory`
   unless you changed it. A pinned check such as `uvx alice-memory@0.20.2
   --version` does not change what that plain command runs, so upgrade the copy
   it uses:
   - If you installed Alice as a uv tool (`uv tool list` shows `alice-memory`),
     uvx runs that installed copy. Run `uv tool upgrade alice-memory`, or
     `uv tool install alice-memory==0.20.2` if you installed it with a version pin.
   - Otherwise uvx runs the copy in its cache. Run `uvx alice-memory@latest
     --version` once: it refreshes the cache, and the plain `uvx alice-memory` that
     hosts run uses 0.20.2 from then on.
   - If a host entry names a version itself (for example `alice-memory@0.20.0` or
     `alice-memory==0.20.0`), `alice-memory install` keeps it and reports the entry
     as customised. Change the version in that entry to 0.20.2.
   - With pip: `pip install -U alice-memory==0.20.2` in the environment the hosts
     use.

   Then check with the command the hosts run, not a pinned one:
   `uvx alice-memory --version` (or `alice-memory --version` for pip) must print
   0.20.2. Restart the hosts afterwards.
2. **PostgreSQL: run the migrations before you serve requests.** A v0.20.0
   database is at revision `20260721_0094`. The upgrade runs `20261004_0095`,
   `20261005_0096` and `20261011_0097`, in that order. They repair the stored
   labels of derived rows: 0095 settles the domain, 0096 raises the sensitivity,
   the project scope and the project floor, and 0097 repeats the repair for the
   citations the saved-quote reader finds (a memory cited as JSON text, as an
   `alice://memories/` URL, with `urn:uuid:`, with an upper-case prefix or with a
   fragment after the id). A database that goes from 0094 to the head is repaired
   by 0096 and finds nothing to change in 0097. Run them as the documented table
   owner, `alicebot_admin`, which is `NOSUPERUSER NOBYPASSRLS`: each migration
   turns FORCE row level security off on the tables it reads and writes
   (`sources`, `memories`, `open_loops`, `generated_artifacts`, `beliefs`,
   `event_log` and, from 0096, `projects`) inside its own transaction and turns it
   back on before it commits. A failure, including derived rows that record each other
   in a cycle whose labels do not settle within a bounded number of changes, or an
   update that changes no row, rolls the relabels, their audit events and the
   FORCE change back together. Each row that migrations 0096 and 0097 raise gets one
   `memory.labels_raised` event (`open_loop.labels_raised` for an open loop and
   `artifact.labels_raised` for an artifact) that holds the old and new labels and
   no text or ids. The downgrade keeps the repaired labels. A database restored
   at or past 0096, and rows copied into a database already at the head, are not
   repaired by a migration: run `alicebot vnext labels check` after such a
   restore, and `alicebot vnext labels repair` if it lists a row. Until then,
   readers hold such a row to what its inputs require.
3. **SQLite: the first open after the upgrade repairs the vault once.** The open
   pass raises derived memories and open loops to the labels of their inputs and
   stamps the vault with the state key `derived_labels_v4`. Each row it raises gets
   one `memory.labels_raised` event (`open_loop.labels_raised` for an open loop)
   with the cause `repair_v4`. A row the owner had lowered on purpose is raised
   again once. The open pass never stops a vault from opening. After a failed
   repair it can leave the vault open with the completion key unstamped, and the
   read check holds the row it could not repair to what its inputs require. A
   native SQLite backup carries no generated artifacts, so a promoted copy whose
   only recorded input is a missing artifact is unverified.
4. **Check the labels.** `alicebot vnext labels check` (PostgreSQL) and
   `alice-memory labels check` (SQLite) print how many derived rows are below
   their inputs or unverified. Check reads a snapshot and does not upgrade the live
   vault. `labels repair` raises the rows that are below their inputs. An explicit
   repair checks every time, including after the open pass has stamped completion,
   and a failure rolls back the whole repair. `alice-memory doctor` and
   `alicebot vnext doctor` print the same count as a warning, and report a check
   that could not read the store as unavailable, never as zero. A row with a
   missing or redacted input is listed as unverified, and `labels repair` cannot
   fix it: restore the input, or regenerate or delete the report.
5. **What an owner sees after the upgrade.** After the upgrade, a derived row
   whose inputs are confidential is labelled confidential, and a derived row with
   no record is unverified. Either one leaves the owner's default recall, pack and
   resume, like any confidential row did in v0.20.0. The owner still reads it by
   id, with a request that names every sensitivity, and through `labels check`,
   which lists unverified rows. An approved weekly-synthesis memory that v0.20.0
   wrote on PostgreSQL stays in the owner's default recall, pack and resume,
   because the read uses the weekly report that names it in `candidate_memory_ids`,
   and a memory that no report names is unverified. On SQLite there is no report
   table, so a weekly-synthesis memory there can only arrive by import or a direct
   insert; it has no report to name it, stays unverified and is listed by
   `labels check`.
6. **Reports are made again once.** The first run after the upgrade of the
   open-loop review over loops that link a source, or of a consolidation over
   cluster members that cite one, makes one new report, because the run digest now
   covers those sources. A run that names no source keeps the digest it had.
7. **After a restore.** `alice-memory import` repairs the labels of derived
   memories and open loops in the complete staged copy before it publishes the
   restored database, whether the destination is new or was already upgraded. A
   cycle whose labels do not settle, or a relabel that changes no row, stops the
   import with `restore_failed` before publication and writes nothing. Run
   `alice-memory labels check --db PATH` after the restore.
8. **Keys bound to `~global`.** `alicebot agent keys create --project-scope
   '~global'` is refused and stores no key, and a key already stored with that
   binding is refused at every route and tool: HTTP 403, or `not_permitted`. The
   server log, at warning level, names the reason and the commands. Find the key
   with `alicebot agent keys list`, where its `project_scope` reads `~global`,
   revoke it with `alicebot agent keys revoke <id>`, and make a new key bound to
   the name or id of a project. A key that someone bound to a project literally
   named `~global` in v0.20.0 needs a new binding.
9. **Callers of the MCP tools:** handle `not_permitted`, `not_found` and
   `precondition_failed`, and `invalid_request` for a rejected argument. Every
   message is still the fixed sentence `The tool request could not be processed`.
   `alice_memory_commit` refuses a memory whose text is over 20,000 characters
   with `invalid_request` and saves nothing.
10. **Clients that call the HTTP API with a key that has limits:** a row above the
    key's limits now answers HTTP 404, the answer for a row that does not exist,
    where v0.20.0 answered HTTP 403 with a policy decision. JSON that you send to
    a write door nests at most 64 levels and holds no `NaN`, `Infinity`,
    `-Infinity` or number too large for a float.
11. **Hosts.** `alice-memory install` keeps `ALICE_PROJECT_DIR`,
    `ALICE_PROJECT_SCOPING` and `ALICE_MCP_COMMIT_RESULT` in a Hermes, OpenCode
    (JSONC) or Codex entry that you added them to by hand, where v0.20.0 refuses
    the entry on the next run.
12. **Claude Code plugin:** the marketplace file pins the v0.20.0 tag commit until
    a change after this release moves it, so the marketplace install runs v0.20.0
    code and carries none of these fixes. See "Claude Code plugin".

## Derived rows follow their inputs

- **The label of a derived row is decided by one function.** A derived row is a
  report, a summary, a copy or a candidate that Alice made from other rows. Its
  domain, its sensitivity and the projects it requires are the labels of its
  inputs: the most frequent restricted domain among them (alphabetical ties), the
  highest sensitivity, and every project of every input. None of them is lowered.
  v0.20.0 kept the label the row was given when it was made, so a consolidation
  report could be stored below the memories it prints, a copy of a health or
  confidential input could be stored as `unknown` and `public`, and a derived
  summary of restricted inputs could be labelled `unknown`.
- **Writes keep it.** The insert re-reads the inputs inside the write and raises
  the domain, the sensitivity and the project floor. A later metadata write cannot
  drop the marker that makes the row derived or put back an older scope. Raising
  a source or a memory walks the rows derived from it and raises those too. An
  owner edit that would lower a derived row is held at its inputs, and the answer
  names `label_floor_applied`. A relabel that cannot finish answers HTTP 409 with
  the cause `propagation_bound`, `row_changed`, `dependency_cycle`, `lock_order`
  or `database_error`, and a relabel that waits more than 3 seconds for the label
  lock answers HTTP 503 with `Retry-After: 2` and changes nothing.
- **Moving a source to another project** first returns
  `derived_rows_hidden_from_project_keys`, the number of derived rows a
  project-bound key would lose, and writes nothing while that count is nonzero,
  until `confirm_label_hide` is true. The owner or an unbound admin key recovers
  fresh candidates through `POST /v0/vnext/sources/{source_id}/regenerate` and then
  reruns the normal report generation route.
- **Reads check them.** An exact read of a derived artifact, a write that cites a
  derived memory, explain, memory review, redaction and an open-loop update use the
  labels of the row's inputs. A row whose inputs cannot be checked is refused to a
  locked key, and the owner and an unbound admin key still read the stored row.
  Recall, context packs, resume, recent decisions, the session brief, the review
  queue, the open-loop lists and the workspace, dashboard, context tree and
  dogfooding lists drop a loaded row whose effective label is outside the request.
  The artifact list, the source trace, the project list, the dashboard project row
  and the belief state route apply the caller's sensitivity ceiling, including
  titles, ids and counts. The report producers drop an input whose effective label
  is outside the request before it appears in report text.
- **A row is held to every row it cites.** Every id that the saved-quote reader
  finds in a derived row is looked up, in any spelling. A report that quotes a
  confidential memory as JSON text is raised to that memory's labels. A row with
  more than 1,024 strings that the citation reader examines is unverified
  (`too_many_citations`), whatever shape holds them, and a `memory:` or `source:`
  word that holds an id in a spelling the parser cannot take apart leaves the row
  unverified (`unreadable_citation`) when that id names a stored row.
- **A locked key keeps to its binding.** A locked key's consolidation, roll-up,
  staleness sweep and open-loop review keep only inputs whose scope and floor are
  both inside the binding, and each new report and aggregate records
  `derived_from` for the rows it used.
- **The workspace is faster.** The workspace transaction turns PostgreSQL JIT
  compilation off, and the label kernel finds the marker of every named weekly
  candidate in one pass. On a vault of 3,000 sources, 5,000 memories, 500 artifacts,
  400 derived loops and two projects, the admin workspace took 1.2 to 1.3 s before
  this change and takes 0.64 to 0.70 s.

## Rows above a key's limits

- **The operator routes and the legacy tools apply the caller's limits.** In
  v0.19.2 and v0.20.0 an unbound `trusted_local_agent` key, whose ceiling is
  `public`, `internal`, `private` and `unknown`, was shown rows above that ceiling
  by `GET /v0/vnext/memories/recent-commits` and the legacy tool
  `alice_vnext_recent_memory_commits`, `GET /v0/vnext/context-tree`,
  `POST /v0/vnext/open-loops/extract`, `GET /v0/vnext/settings/brain-charter` (and
  `PUT` replaced a charter it could not read), the charter and tasks of the
  workspace and the captures of the connector status, and the connector health
  block, which appears on the connector, workspace, dogfooding and doctor routes,
  named the last captured item and the connector cursor. The memory audit
  (`GET /v0/vnext/memories/{memory_id}/audit`) returned the text and events of a
  memory above that ceiling, and the graph neighborhood and the quality-eval
  comments listed rows above it. Each now lists, counts and
  returns only what the caller may read now. The owner and an unbound `admin_agent` key are
  shown what they were. A permanent test calls every `/v0/vnext` route.
- **Source review and delete, belief review and graph edge review.** A
  `trusted_local_agent` key bound to no project could read a source above its
  ceiling through `POST /v0/vnext/sources/{id}/review` and
  `DELETE /v0/vnext/sources/{id}`, rename it, move it, archive it and delete it,
  and could review a belief or a graph edge that joins a memory above its ceiling.
  These routes now answer HTTP 404, the answer for a missing row, and change
  nothing.
- **The doors that act on one row by id** (the artifact routes, the memory audit,
  review, correct, expire, forget, redact, undo, unexpire and accept-consolidation
  routes, the open-loop review route, and the tools `alice_memory_review`,
  `alice_memory_correct`, `alice_memory_manage` and `alice_open_loops`) answer a row
  above the key's limits as a row that does not exist, and write what a call on a
  missing id writes, which is nothing: no policy event and no agent record.
- **Projects and open loops.** `POST /v0/vnext/open-loops` holds `project_id` to the
  key's binding. `POST /v0/vnext/open-loops/extract` judges every loop it returns,
  a loop found again by its digest included. `POST /v0/vnext/projects/update-candidates`
  and `alice_project_update_candidate` judge the project and every artifact they
  return. The daily brief files a loop under a project only when the caller may read
  it. A call that names no project keeps reading active projects newest first until
  one the caller may read, up to 128 (`READABLE_SCAN_CAP`).
- **The answer of a run that makes a report** is judged on the caller's limits, as
  the read of the report is. The scheduler routes and the generate routes and tools
  answer `artifact: null` or HTTP 404 or `not_found` for a report the caller may not
  read, and `POST /v0/vnext/queue/process-next` leaves `artifact_id` empty for a
  result the caller may not read.
- **Writes that cite a source by id** are held to the caller's read fence:
  `source_refs` of `alice_memory_commit`, the `provenance` of `alice_memory_correct`
  and the `source_id` and `memory_id` of `POST /v0/vnext/open-loops`. A source that
  is missing, deleted, malformed or outside the fence answers `not_found`.
- **Event feeds, traces and saved quotes.** The workspace event feed and event
  count, the source trace and the policy event of an explain of a continuity object
  show a key with limits an event only when it may read every labelled row the event
  names. The connector screens show the path of a failed import, and a cursor, only
  when the key may read the source an import of it made. The quote a commit saved of
  a source or of a memory is shown only to a caller who may read that source or
  memory now. The ids an open loop keeps are withheld from a reader who may not read
  the row they name.
- **A request that names no domain** is held to the caller's profile. A
  `project_scoped_agent`, `read_only_agent` or `memory_proposal_agent` caller reads
  every domain except family, health, spiritual, legal and financial, `unknown`
  included, and a request that names domains narrows that set. The held-back set
  reads the stored label.
- **Recall and the hidden-row bound.** Recall, the context pack and `alice_resume`
  no longer change their answer for a key with limits when a row it may not read is
  added to the vault, until a bound is reached: a read judges at most 128 rows
  (`READABLE_SCAN_CAP`) of a list. Events of a row the key may not read that sit
  inside the five-event window of `recent_changes` in the context pack or in
  `alice_resume` are skipped and older events fill the list, so the list does not
  show that hidden events exist. A null `last_decision` or `next_action` can mean
  that the newest 128 matching rows hold none the key may read.
- **The doctors.** `GET /v0/vnext/doctor` and `POST /v0/vnext/doctor/run` run the
  `flagged_sources` and `derived_labels` checks only for the owner and an unbound
  admin key. A trusted key receives both as `skipped`.

## Redacted memories

- **Reports built from a redacted memory are restricted.** A daily brief, weekly
  synthesis, project update, connection or contradiction report, consolidation
  report, roll-up card, weekly candidate, promoted copy or project state made from
  the memory keeps the words it copied. A derived row that recorded a redacted row
  as an input is unverified, with the reason `input_redacted`, and so is every row
  built from it. The owner and an unbound admin key still read it. Every other key
  is refused it at every door that returns a report or a memory.
- **A belief and a graph edge follow the same rule.** A belief whose backing memory
  is redacted is read by the owner and an unbound admin key only, and
  `GET /v0/vnext/graph/neighborhood/{target_id}` lists, and
  `POST /v0/vnext/graph/edges/{edge_id}/review` changes, an edge for a key with
  limits only when that key may read every labelled row the edge joins and none of
  them is redacted.
- **Regenerating restores access.** A new run of a producer reads no redacted
  memory, so the new report is readable where any other report is. The old report
  stays restricted until it is deleted. Archiving a memory restricts nothing.
- **Redacting a memory made by promoting a report completes.** It failed with a
  server error in v0.19.2 and v0.20.0. The `artifact.promoted_to_memory` event that
  the promotion appended is left as it is, because its payload is the id of the
  memory and no text. The text the copy was made from stays in the report.
- **This is containment, not removal.** The text stays in the reports, and the owner
  and an unbound admin key can still read it. Full removal of redacted text from
  reports is planned for v0.21.0.

> **Correction (2026-10-21):** Full removal of redacted text from reports is no longer scheduled for v0.21.0. It is planned, with no release set.

## Errors and refusals

- **Typed MCP error codes.** `not_permitted` (a policy, the agent's permission
  profile, its key or its project scope refused the call), `not_found` (an id the
  call names does not exist for this caller) and `precondition_failed` (the call is
  allowed but the state forbids it). `invalid_request` also answers a rejected
  argument. The server sends a code only from a closed set of four, chosen from the
  class of the exception and never from its message text.
- **The policy is asked before the state of the row** for `forget`, `undo`,
  `redact`, `confirm`, `alice_memory_commit` with a `confirmation_id`, and the HTTP
  routes that call the same commit service. A refused caller hears `not_permitted`
  whatever the state of the row, and a caller that may not read the row hears
  `not_found`.
- **`~global` is reserved.** It is the name Alice puts in a request to ask for the
  notes that belong to no project. Every tool refuses it as a project, a project
  scope or an identity's project scope, with per-project scoping on or off.
- **A project slug in use** answers HTTP 409 with `{"detail": "vNext project slug is
  already in use"}`, the same for every caller. `POST /v0/vnext/queue/process-next`
  claims the oldest pending task that is due and answers `completed` or `idle`.

## Importers, deletion and backups

- **`sources list`, `sources delete` and `sources prune --superseded` (SQLite).**
  Destructive commands preview and exit 2 unless `--yes` is given. The scrub clears
  source text and labels, provenance quotes, pending candidate copies and revisions,
  source-backed loops and unsupported entity text, closes and blanks every graph edge
  that names the source, and lists every unredacted citing memory. Audit events,
  hashes, retained memory text and earlier copies remain, and the docs give the
  VACUUM and checkpoint commands for unused space and the write-ahead log.
- **`import-markdown --supersede`, `--dry-run` and `--allow-looser-classification`
  (SQLite).** Replacement is off by default. In v0.20.0 an edited file adds another
  live source.
- **A file that fails part way no longer leaves a half-built source.** Each file of a
  Markdown import and each conversation of a ChatGPT import is written inside its own
  savepoint, on SQLite and on PostgreSQL. The receipt counts the failed file in
  `failed_count`, and one `source.import_failed` event is written.
- **Interrupted commands.** A SIGKILL or a power loss could leave a plaintext
  snapshot of the vault in the temporary directory. Every command that makes one now
  removes the folders of processes that are gone first.

## Recall, resume and embeddings

- **Expired memories.** `alice_resume`, `alice_recent_decisions`, the session brief
  and the SessionStart hook leave out an active memory that `alice_memory_manage`
  with `action: expire` closed. Consolidation and the roll-up pass read only
  memories and cards whose window is open, so the text of an expired memory is no
  longer sent to the embeddings endpoint to cluster. A group whose only card expired
  is reported as `expired_card_members_unchanged`.
- **Promoting a reviewed artifact** embeds the memory it creates.
- **Roll-up passes** no longer raise `IntegrityError` when a rejected, stale or
  archived card holds the memory key of a group. The group is reported as
  `existing_card_members_unchanged`.
- **A write that falls on a clock step** no longer fails the `last_seen_at >=
  first_seen_at` check on SQLite.

## Per-project memory (off by default)

- `alice-memory project show` prints which git repository a folder belongs to,
  `project report` counts the vault's notes by project, and `project scoping
  on|off|status` reads and sets a per-project scoping switch. The default is off.
- With scoping on, the SessionStart hook and `alice-memory brief` print a project
  brief, `alice_resume` reads the project's items first, and project briefs no
  longer automatically include global family, health, spiritual, legal or financial
  material. `alice-memory brief` and `sleep-proposals` take `--project-dir PATH` and
  `--scope project|project_only|global|all`.
- With scoping off, every output is what v0.20.0 printed, with one exception: the
  refusal of `~global` as a project name applies with scoping off too.
- Writes do not change in this step, and no table, column or index is added.

## The commit result and the commit limit

- **`ALICE_MCP_COMMIT_RESULT=compact`** makes `alice_memory_commit` answer with the
  memory `id`, the outcome, the `receipt`, the reasons a write was held, and for a
  held write the `confirmation_id` and the proposed text. An unset variable and
  `full` return the v0.20.0 result. The legacy alias, the HTTP routes and the CLI
  always return the full result.
- **`alice_memory_commit` refuses a memory over 20,000 characters** with
  `invalid_request`. The text is counted after runs of whitespace are collapsed to
  one space. The legacy tools `alice_vnext_correct_memory` and
  `alice_vnext_propose_memory` still take text of any length on SQLite.

## Request bodies and stored JSON

- JSON that a caller hands a write door to be stored nests at most 64 levels and
  holds no `NaN`, `Infinity`, `-Infinity` or number too large for a float. Each door
  refuses it in its own words before anything is written. A request body that holds a
  number that is not finite is HTTP 422 of type `finite_number`, and other free JSON
  fields answer HTTP 422 of type `json_too_deep`.
- A stored row nested deeper than the readers walk no longer breaks a read route or a
  read tool for every caller. A read that changes nothing is run once more with every
  stored column cut to 256 levels, and the part below is the string
  `[nested too deeply]`. A request or tool call that may have written is never run
  twice.
- The MCP stdio reader answers a message nested past 256 levels as an invalid request
  and goes on.

## Security

This release was checked with automated security scanning and internal adversarial
review, findings triaged and fixed. No one outside the project has audited the code.
The security advisories published with this release describe the problems below.
This section says what a user sees. Most of the problems are in the optional Postgres
stack or in the rules that decide which rows a key may read, and the SQLite install
runs no HTTP API.

- **A derived row could be read below its inputs.** In v0.20.0 a report, summary or
  copy kept the label it was given when it was made. A key whose ceiling was below
  the inputs could read the report, its quotes and the ids it lists. v0.20.2 raises
  the row to its inputs and checks it on every read. After the upgrade, a derived row
  whose inputs are confidential is labelled confidential, and a derived row with no
  record is unverified.
- **An unbound trusted key could read and change rows above its ceiling** through
  the operator routes (the memory audit among them), through source review and delete, belief review and graph
  edge review, through open-loop filing, extraction and the project update candidate,
  and through the answer of a run that makes a report. Each now applies the caller's
  limits.
- **A refusal told the key what the row was.** The doors that act on one row by id
  answered a row above the key's limits with a policy decision that repeated the row's
  domain, sensitivity and project scope. They now answer as for a missing row.
- **Event feeds and traces named hidden rows.** The workspace event feed, the event
  count, the source trace and the policy event of an explain of a continuity object
  now follow the rows they name.
- **Saved quotes and ids outlived the row's label.** The quote a commit saved of a
  source or of a memory was shown after the row was redacted, archived, relabelled or
  moved. The connector screens named the path of a confidential file whose import
  failed. An open loop returned the ids of sources and memories its reader could not
  read. Each is now withheld from a key that may not read the row.
- **A redacted memory's words stayed readable in reports.** They are now restricted to
  the owner and an unbound admin key until the report is regenerated. This is
  containment, not removal.
- **A restricted caller that named no domain read all five held-back domains.** The
  request is now held to the profile.
- **A snapshot of the vault could outlive a killed command** in the temporary
  directory. Every command that makes one first removes the folders of processes that
  are gone.
- **Dependencies.** The web console's Next.js moves to 16.3.8, which fixes a
  server-side request forgery in image optimization and five lower-severity Next.js
  advisories, and `sharp` moves to 0.35.5.

## Behaviour changes an integrator will notice

- **HTTP.** HTTP 404 for a row above a key's limits, where v0.20.0 answered HTTP 403
  with a policy decision. HTTP 404 for a missing belief or edge and for an id that is
  not well formed, where v0.20.0 raised a server error. HTTP 409 for a project slug in
  use. HTTP 409 with a named cause, or HTTP 503 with `Retry-After: 2`, for a relabel
  that cannot finish. HTTP 422 of type `finite_number` and `json_too_deep`.
- **MCP.** The codes `not_permitted`, `not_found` and `precondition_failed`, and
  `invalid_request` for a rejected argument. `alice_memory_commit` refuses text over
  20,000 characters. `~global` is refused as a project.
- **Reads for a restricted caller.** A request with no `domains` is held to the
  profile. A row whose effective label is outside the request is dropped before the
  limit. A null `last_decision` can mean that the newest 128 rows hold none the key
  may read.
- **Rows.** A derived row can be labelled above the label it had, and a row with no
  record is unverified. Domain fields and policy audit labels change with the
  repaired label. An owner, trusted or admin caller that filters by an unrelated
  domain stops receiving a derived row after its label changes from `unknown` to a
  restricted domain. A new weekly candidate memory stores `input_summary`, which
  explain returns.
- **Events.** `memory.labels_raised`, `open_loop.labels_raised` and
  `artifact.labels_raised`, `scoping.changed` and `source.import_failed` with
  `relative_path` or the conversation index.
- **Commands.** `alice-memory project`, `alice-memory labels`,
  `alicebot vnext labels`, `sources list`, `sources delete`,
  `sources prune --superseded`, `import-markdown --supersede`, `--dry-run` and
  `--allow-looser-classification`, and `--project-dir` and `--scope` on `brief` and
  `sleep-proposals`.
- **Settings.** `ALICE_PROJECT_DIR`, `ALICE_PROJECT_SCOPING` and
  `ALICE_MCP_COMMIT_RESULT`.
- **Doctors.** `derived labels: N below their inputs, M unverified` as a warning.
- **Context pack.** A pack row dropped by effective admission is absent from the
  later stage's excluded counts and warnings. Pack token estimates can rise,
  because derived inserts persist an empty `project_scope` and `project_floor` and
  `derived_from` and `project_floor` add to the estimate.

## Schema and migration

There is no new table, column or index. Three PostgreSQL migrations, `20261004_0095`,
`20261005_0096` and `20261011_0097`, repair the labels of stored rows, and they must run
before serving requests as the NOSUPERUSER NOBYPASSRLS table owner. A SQLite vault is
repaired on its next open and before a restore is published. The repair raises
labels and writes the `labels_raised` events, and it never lowers a label. The
per-project brief adds no table, column or index, so a v0.20.0 binary opens a vault
that the brief has read and a backup restores in both directions.

## What this release does not claim

This release was checked with automated security scanning and internal adversarial
review, findings triaged and fixed. No one outside the project has audited the code.

It does not claim that no hidden id or word is left anywhere: the limits below list what
is known. It does not make the HTTP API safe to expose without a key, a proxy and the
topology in `docs/deployment/single-tenant-self-hosted.md`. Redaction restricts reports
and does not remove the words from them.

## Known limitations

Open in redaction and hidden ids:

- **Redacted words stay in the reports.** Redacting a memory restricts the reports and
  derived rows built from it to the owner and an unbound admin key. The text stays in
  those reports, and removing it is planned for v0.21.0. After a memory is redacted,
  the owner and an unbound admin key read the rows it contained by id, in the artifact
  and project lists, in recent commits and in the dashboard, but not through recall,
  the context pack or the default context tree, which read an unverified row as
  regulated. A request that names every sensitivity lists them.

> **Correction (2026-10-21):** Removing the redacted text from the reports is no longer scheduled for v0.21.0. It is planned, with no release set.

- **An open loop made over a memory keeps what its caller typed.** The title and
  description of a loop made with `POST /v0/vnext/open-loops` stay readable to every
  key that reads the loop after the memory is redacted.
- **Rows a key can read may list the ids of rows it cannot read.** The candidate memory
  a report made, a source archived since, and the ids in `candidate_memory_ids`,
  `derived_from`, `source_ids`, `memory_ids` and `source_refs` stand in the lists. The
  ids grant no access and show that the row exists. This is a known exception, not a
  way of meeting the requirement to filter hidden ids, and withholding them is tracked
  for v0.21.0. The security note names the two answers that show a little more.

> **Update (2026-10-22):** Fixed in v0.21.0 for a key with limits. It is not shown the id of a memory, a source, an artifact or an open loop that it may not read, in an HTTP answer, a tool result or command output. Every string whose whole value is an id is checked, under any field name and at any depth, in any spelling of a UUID and behind a `memory:`, `source:`, `artifact:` or `open_loop:` prefix. A list loses the entry, a field that held one id becomes null, and a count beside a list that lost an entry is recomputed or dropped. Where a prefix says the id names a row, an id the key may not read is withheld whether the row is hidden or does not exist. The owner and an unbound admin key keep every id. An id inside free text, such as the text of a readable memory, is not removed, and an id that names no row at a position the product does not type is shown as written. v0.21.0 does not claim that no hidden id is left in an answer.

- **A report keeps the words it was made with.** The title, text or quote of a row that
  was archived after the report was made stays in the report, in a roll-up card and as
  the digest of a consolidation member. Hiding them is tracked for v0.21.0.

> **Correction (2026-10-21):** Hiding the words of archived rows from the reports is no longer scheduled for v0.21.0. It is planned, with no release set.

- **The memory audit route lists the archived members of a derived memory,** and a
  memory made from a captured source keeps its `source_id`, `source_event_ids` and
  `capture_content_hash` after the source is archived. The scheduler's run records keep
  the `artifact_id` of a report made confidential since. Withholding these is tracked
  for v0.21.0.

> **Correction (2026-10-21):** Withholding `capture_content_hash` is no longer scheduled for v0.21.0. It is planned, with no release set.

> **Update (2026-10-22):** Changed in v0.21.0 for the ids this item lists. A key with limits is not shown the archived members of a derived memory, the `source_id` and `source_event_ids` of a memory, or the `artifact_id` of the scheduler's run records when it may not read the row they name. The owner and an unbound admin key keep every id. The `capture_content_hash` of a memory is still returned after its source is archived, as the correction above records.

- **The vector stage of recall does not refill after hiding rows.** With an embeddings
  endpoint and a query that shares no word with the stored text, a restricted caller can
  get fewer results than exist, down to none. Nothing the caller may not read is shown.
  It is tracked for v0.21.0. The candidate counts of the vector and temporal-anchor
  stages move with hidden rows, the BM25 score of a visible row on SQLite is computed
  over every row of the index, and a full-text query takes longer the more hidden rows
  match it.

> **Update (2026-10-22):** Fixed in v0.21.0. The vector stage of `alice_recall` and of the context pack, and the temporal-anchor stage of the context pack, refill after they drop a row the caller may not read. A key with limits is read once, at 128 rows (`READABLE_SCAN_CAP`), and given the first rows it may read, up to the limit it asked for. The page is full while the hidden rows in front of it number at most 128 minus the rows the stage is asked for. That is 118 hidden rows for `alice_recall` at limit 5, which asks its vector stage for ten rows: the stage returns nine candidates at 119, one at 127 and none from 128. Inside the bound the candidate counts of the two stages no longer move with hidden rows. On SQLite the BM25 score of a visible row is still computed over the whole index, hidden rows included. The owner and an unbound admin key are read as before.

  id of a queued task, a person and the charter above the ceiling in the `target_id` of
  their creation events. A connector keeps one cursor and skips an item at or below it,
  so a key that syncs can learn whether an item it sent sorts below a cursor it may not
  read, and a key that imports a public item at a path it already knows is shown a
  failed import of that same path. The legacy `/v0` routes that stay mounted list rows
  whatever their label while `APP_ENV` is `development` or `test`.
- **The cited-source fence does not cover everything.** Memory proposals and the
  agent-output ingest store their `source_refs` as given, the owner dependency trace

The memory commit, the memory proposal and the agent-output ingest routes, the sync of the `agent_output` connector, their MCP tools and the `--source-ref` flag of `alicebot vnext memories commit` refuse a `source_refs` entry that is an object, a number, a boolean, null, a nested array, a blank string or a string that is the text of a JSON object or array, and write nothing. - **The context pack still names the id of an expired memory** in `recent_changes`,

> **Update (2026-10-22):** Fixed in v0.21.0. The context tree, the workspace lists and `GET /v0/vnext/projects` fill their pages for a key with limits: the list is read once, at 128 rows, and the key is given the first rows it may read, up to the limit it asked for. The page is full while the hidden rows in front of it number at most 128 minus the rows the list is asked for, and short past that bound, which says only that hidden rows fill the window. The owner and an unbound admin key are read as before.

## Why 0.20.2 and not 0.20.1

`v0.20.1` was tagged on the commit that merged the release pull request, and
its publish run then stopped before it built anything. The first publish job
reruns the whole unit suite in one process, and its 35 minute limit was set when
that took a few minutes. CI had since split the same suite into four shard jobs
because it had grown, and the one-process rerun now needs about 54 minutes. The
run reached that limit with every test passing so far. The workflow runs from
the tag, so the fix cannot reach the tagged commit, and repository rules protect
stable tags against both deletion and update, which is correct. The tag stays
and the number is retired rather than reused. Nothing was published under it: no
PyPI artifact and no GitHub Release. This mirrors `v0.13.0`, `v0.15.0` and
`v0.19.1`, which are recorded the same way. `v0.20.2` carries the same product
changes as the `v0.20.1` commit, raises that job's limit to 120 minutes, and adds
a unit test that fails when the limit is below the time CI allows the whole
suite.
