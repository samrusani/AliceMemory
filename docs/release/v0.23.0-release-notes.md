# Alice v0.23.0 Release Notes
<!-- alice-release-state: {"schema_version":"alice_release_document_state_v1","version":"0.23.0","publication_status":"pending","checksums_status":"pending"} -->

**Take this release if you keep a SQLite vault and run agents against it, if you run the
PostgreSQL stack with the self-hosted database owner role, or if a client of the vNext routes
has met an Internal Server Error for an id it sent. The SQLite vault gets agent keys:
`alice-memory keys create`, `keys list` and `keys revoke`. Once a vault holds an active key,
every MCP call needs `ALICE_AGENT_API_KEY`. `alice_recall` returns ten note passages by
default, where it returned eight. Thirteen migrations now complete for the database owner role,
and the vNext routes and tools answer not found, or a normal answer, where they answered a
server error. There is no new tool, setting or migration. See "What to do after upgrading".**

- v0.22.0 had no command that mints an agent key on the SQLite vault. v0.23.0 has three, and a
  vault that holds an active key refuses an MCP call that carries no key. A vault with no key
  behaves as v0.22.0 did.
- v0.22.0 answers HTTP 500 for a value that is not an id at three vNext routes (and HTTP 409 at a
  fourth), for the id of no person at `POST /v0/vnext/open-loops/extract`, and for a memory whose
  source id is in a reference spelling at `POST /v0/vnext/context-packs`. v0.23.0 answers HTTP 404,
  HTTP 404 and a context pack.
- v0.22.0 stopped the self-hosted database owner at revision 0066, or at 0087, on a vault that
  carried data. v0.23.0 completes the upgrade. The head stays `20261011_0097`.

## What to do after upgrading

1. **Upgrade the copy your hosts run** (`uv tool upgrade alice-memory`, or
   `pip install -U alice-memory` in the environment they use), check it with
   `alice-memory --version`, and restart your hosts.
2. **A SQLite vault with no keys needs nothing else.** It behaves as in v0.22.0: an MCP call
   without a key is answered as before, and the brief and the session-start hook print what
   they printed. No migration touches it.
3. **Once you mint a key, every agent host needs one.** `alice-memory keys create --agent-id
   <host> --profile <profile>` prints the raw key once. From then on an MCP call that carries no
   `ALICE_AGENT_API_KEY` is refused, reads included, and the legacy tools are refused too. Set the
   variable in the environment of each host's MCP server, and in the launch environment of the
   host for the session-start hook: the hook is a separate process that reads the variable from
   its own environment, and the `env` map of an MCP server does not reach it. Without the key the
   hook and `alice-memory brief` print nothing and exit 0, so the session starts with no brief.
   Your own hosts need a key too: mint an unbound `admin_agent` key for each.
4. **The commands you run yourself keep running as the owner and take no key**: `import`,
   `export`, `doctor`, `sleep`, `sleep-proposals`, `import-markdown`, `import-chatgpt` and `keys`.
5. **Mint keys again after an import.** The JSONL export drops keys, so an import from an export
   gives a vault with no key. A copy of the vault file taken after a checkpoint keeps its keys.
6. **To return to a vault with no keys,** revoke every key (`alice-memory keys revoke <prefix>`).
   Revoking the last active key makes the vault keyless again. A revoked key is refused on its
   next call and does not count as a key.
7. **PostgreSQL stack: no step.** No migration is added and the revision stays `20261011_0097`.
   A database already at or past the thirteen changed revisions is not touched, because a revision
   that was applied does not run again. If `alembic upgrade head` stopped for the owner role at
   revision 0066 or 0087 with a `NotNullViolation`, run it again with this version.
8. **Claude Code plugin.** The marketplace file on `main` pins the v0.22.0 tag commit until a
   change after this release moves it, so a marketplace install runs v0.22.0 code until then.

## Agent keys on the SQLite vault

v0.22.0 had no command to mint an agent key on the SQLite vault: `alicebot agent keys create`
needs PostgreSQL and refuses a SQLite database. A keyless MCP call read with the owner's standing
whether or not the vault held a key.

**The commands.** `alice-memory keys create --agent-id <id> --profile <profile>` takes the five
profiles of the PostgreSQL command, and `--project <name>` binds the key to one project, with the
same refusals (a blank name, the reserved name `~global`). It prints the raw key once, then a line
saying so. Only the sha256 hash of the key and a short prefix are stored. `alice-memory keys list`
shows prefix, agent id, profile, project, label, created, last used and state, and never a hash or
a raw key (`--json` for records). `alice-memory keys revoke <prefix>` revokes one key, by prefix or
key id.

**What a key is.** In one sentence: keys tell Alice which agent is asking and limit what Alice
returns to it; they do not stop a process that runs as your OS user from reading the vault file. An
agent that can run shell commands as you can open the vault directly. Keeping such an agent away from
your data, and running agents on several machines against one vault, needs the PostgreSQL stack.

**The refusal.** Once the vault holds at least one active key, an MCP call without
`ALICE_AGENT_API_KEY` answers `not_permitted`, the answer a bad key gets, for every core tool and
for the legacy tools. A bad or revoked key answers as it did. Only active keys count. If the count
of keys cannot be read, the call is refused.

**The brief and the hook.** `alice-memory brief` and `alice-memory-session-start` share one rule.
On a vault with an active key they run as the key's agent, from `ALICE_AGENT_API_KEY` in their own
environment, and show only what that key may read. Without a key, or with one that does not
resolve, they print nothing and exit 0. On a vault with no key they print what they printed.

**Not written anywhere.** `alice-memory install` writes no raw key into any file, and no flag takes
the key itself, so a key does not land in shell history. Set it in the environment the host
launches with.

**A known difference.** An unbound `admin_agent` key does not get the evidence of a source that
was archived, which the keyless owner gets. For a memory whose cited source was archived,
`alice_explain` is refused to the key, and `alice_memory_review` and `alice_context_pack` do not carry
the source's id. v0.22.0 gives a key the same. It matters now because a vault with a key refuses
keyless calls, so the owner's agent hosts run as keys.

**Cost.** The changelog records a keyless recall within five percent of v0.22.0 on a vault of
1,340 sources, and a keyed recall about 2.6 percent slower than a keyless one on the same vault.

## Server errors that are now answers

These are on the PostgreSQL stack unless a line says otherwise.

- `GET /v0/vnext/beliefs/{belief_id}/state`, `POST /v0/vnext/open-loops/{loop_id}/review` and
  `GET /v0/vnext/projects/{project_id}/dashboard` answered HTTP 500 for a value that is not an id.
  `POST /v0/vnext/projects/update-candidates/{artifact_id}/review` answered HTTP 409. All four
  answer HTTP 404 now, the answer of a well-formed id that does not exist.
- The MCP tools `alice_explain`, `alice_memory_manage`, `alice_open_loops` (`close`, `edit`,
  `reopen`, `snooze`) and the legacy memory tools answered `tool_execution_failed` for a malformed
  id. They answer `not_found` for a keyless caller and the opaque tool answer for a key-bound one,
  as they do for an unknown id. `alice_belief_review` and `alice_graph_edge_review` answer
  `not_found` for an unknown id too, where they failed the call.
- An id in another accepted spelling (upper case, braces, no hyphens, `urn:uuid:`) is used in
  canonical form. This reaches the SQLite vault: `alice_explain` finds a memory by such a spelling,
  where v0.22.0 answered `not_found`.
- `POST /v0/vnext/open-loops/extract` answered HTTP 500 for a `scope.person_id` that names no
  stored person or is not an id. It answers HTTP 404 `not_found` and writes nothing. The upper
  case id of a real person made a second loop for the same source and candidate in v0.22.0; it
  makes none now. `alice_open_loop_extract` and `alicebot vnext open-loops extract` answer
  `not_found`. The SQLite on-ramp keeps the behaviour it had.
- `POST /v0/vnext/context-packs` and `alice_context_pack` answered HTTP 500 when a stored memory's
  `metadata_json.source_id` held a source id as `urn:uuid:<id>`, `URN:UUID:<id>`, `source:<id>`,
  `uuid:<id>` or `alice://sources/<id>`. They return the pack now. On SQLite, such a memory gets
  the source's event time, where v0.22.0 gave it none.

## Migrations for the self-hosted database owner

From v0.6.0 through v0.22.0, a self-hosted database owner (`LOGIN NOSUPERUSER NOCREATEDB
NOCREATEROLE NOBYPASSRLS`, owning its database) stopped at revision 0066 on a vault that carried
data, with `NotNullViolation: column "revision_number" of relation "memory_revisions" contains
null values`, because the backfill matched no rows under forced row-level security. A vault
with a provider row stopped at 0087, on `config_fingerprint_sha256` of `model_providers`. Other
migrations of the same shape ran and wrote nothing.

Thirteen migration files changed: `20260510_0067`, `20260511_0070`, `20260704_0072`,
`20260704_0076`, `20260704_0077`, `20260711_0083`, `20260712_0084`, `20260713_0085`,
`20260713_0086`, `20260713_0088`, `20260714_0090`, `20260715_0091` and `20260716_0092`. Each now
turns off forced row-level security on the tables its data statements touch, inside its own
transaction, and turns it back on before the transaction commits. No file was added, and the head
is `20261011_0097`, as in v0.22.0. A database that is already at the head is not touched, and an
upgrade from nothing with the new files leaves the schema the old files left: 105 tables, 156
policies and 96 tables with forced row-level security.

## Recall and import on SQLite

- **Recall.** `alice_recall` returns ten note passages by default in passage and vectors mode,
  where it returned eight. Memory results stay at eight. An explicit `limit` is honoured as it was,
  so `limit=8` still returns eight. Document mode, the context pack and the minimal depth are
  unchanged. The changelog measures the answer at about 13,104 bytes against 10,617 for eight
  passages, with the timings within five percent.
- **Import speed.** `alice-memory import-markdown` runs the same import in about 213 s against about
  321 s, about a third less wall clock, on a synthetic folder of 13,400 files (149 MB, 104,797
  chunks), by three interleaved fresh-vault runs per side. These are the changelog's numbers for
  one machine and are not a promise for yours. The stored result is the same: sources, chunks,
  hashes, receipts, refusals, duplicate collapse and dry-run behaviour. The import checks every file
  before it stores anything, and then reads each file only while it imports it, so the folder is not
  held in memory at once (peak memory 535 MB to 480 MB in the same measurement). A file that
  changes between the check and its read is refused as a file that fails the check is, and nothing
  is stored. Capture into a vault with many sources is faster too, because the lookup by content
  hash uses its own index.

## Other changes in the package

- The credential check runs at every place it ran, with the same verdicts. Within one import, a
  repeated identical input gets the verdict it already got.
- `alice-memory install` takes the same flags and writes the same environment values.
- Not in the PyPI package: the bench scripts, the synthetic corpus generator
  (`scripts/generate_markdown_perf_corpus.py`), the CI workflows, and the pages under
  `docs/benchmarks/showcase/` that set out and publish the comparison of passage vectors. A wheel
  and a source distribution built from the tree hold no file from `scripts/` or `apps/web`: the
  wheel has 392 files, the source distribution 400 files and 22 folders.

## Behaviour changes an integrator will notice

- A keyless MCP call is refused once the vault holds an active key. The brief and the hook print
  nothing for a keyless run on such a vault.
- `alice_recall` returns up to ten note passages when it is given no `limit`, up from eight, and
  its answer is about 23 percent larger.
- The routes and tools under "Server errors that are now answers" answer not found, or a pack,
  where they answered HTTP 500, HTTP 409 or `tool_execution_failed`.
- `alice-memory` gains the `keys` command with the sub-commands `create`, `list` and `revoke`.
  No other flag is added.
- No tool is added or removed: the default surface lists 3 tools, the full surface 12, and the
  legacy flags bring it to 74 and 77. No setting is added.

## Security

This release was checked with automated security scanning and internal adversarial
review, findings triaged and fixed. No one outside the project has audited the code.

The change a security-minded reader will care about is the keyless refusal. It is a change of
behaviour, and no advisory is planned for this release. v0.22.0 had no command that mints a key on
the SQLite vault, so a vault made with the product held no key for a keyless call to pass over. The
refusal protects a vault whose owner has minted keys, and it goes no further than keys do: they do
not stop a process that runs as your OS user from reading the vault file.

## What this release does not claim

It does not claim that keys keep an agent away from your data. It does not claim that an unbound
`admin_agent` key reads everything the keyless owner reads: the evidence of an archived source is
the exception above. It does not claim that the vectors answer better. The published comparison of
passage vectors ([results](../benchmarks/showcase/phase1-passage-vectors-results.md)) found that a
whole-question search and an agent's first search find the passage of a fact stated in other words
more often with vectors, and that neither of two model families answered measurably better; the
gemma4 family lost 5 of 46 exact-term questions with vectors. It does not claim that the import
speed holds on another machine or another folder. It does not claim that the thirteen migrations
repair a database that already ran their old bodies as the owner and wrote nothing: those rows stay
as they are.
